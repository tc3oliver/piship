# Architecture

PiShip is an open-source, company-first distribution and governance framework for branded Pi-based coding agents. Pi owns the agent loop, TUI, sessions, tools, model/runtime behavior, and extension execution. PiShip owns the distribution layer: manifest/configuration, pinned runtime, resources, reproducible payload, identity/credential/inference integration, and progressively policy/trust and lifecycle/release. Distribution repositories own their brand and declared resources. Pi source is neither forked nor patched.

The layers arrived in order. The personal distribution core came first (`piship/v1alpha1`). `piship/v1alpha2` added managed access and layered configuration. `piship/v1alpha3` added governance: policy, resource, provider, and project trust, capabilities, governed MCP, an OS sandbox for tool subprocesses, and audit. `piship/v1alpha4` added the production lifecycle: verifiable per-target release artifacts, signed update channels, verified update with atomic activation, rollback, and a migration check for local data ([release](release.md)). The [status page](status.md) records what current `main` supports, the evidence for each area, and how project milestones map to these schemas; see [compatibility](compatibility.md) for the Pi integration contract.

| Change | Home |
| --- | --- |
| Generic agent or runtime behavior | Upstream Pi |
| Manifest, lock, payload, installation, access orchestration | PiShip |
| Identity provider, credential broker, inference gateway | The organization (PiShip integrates, it does not become one) |
| Brand and selected resources | Distribution repository |

`identity`, `credentials`, and `inference` depend only on `contracts` and may not import each other; only `core` connects them, through `IdentitySession`, `CredentialRef`, and `ModelDefinition`. `policy`, `audit`, `sandbox`, and `mcp` are governance leaves: `policy` may import `contracts` and `schema`; `audit` and `sandbox` only `contracts`; `mcp` `contracts` and `sandbox`, so stdio servers spawn through the sandbox. `core` may import `policy` and `audit`; `pi` composes all four; `cli` imports only `core`, `schema`, and `contracts`. `adapter-sdk` may import only `contracts` and `sandbox`, and `adapter-conformance` only `adapter-sdk` ([decision 21](decisions.md)). `scripts/check-boundaries.mjs` enforces these imports and the rule that only `packages/pi` imports Pi. It discovers packages from `packages/*`, rejects relative imports that cross package directories, reports `@piship/*` dependencies a package declares but never imports, reads the pinned Pi version from `compatibility/pi.json`, and allowlists the package imports that core writes into generated launcher source.

## Canonical payload

`piship build` creates `dist/<id>` from package-owned build inputs prepared with `@piship/core`, using `npm ci --omit=dev` and exact locked dependencies, then removes optional packages whose npm lock `os`/`cpu` exclude the target (npm installs them anyway inside a shrinkwrapped dependency such as Pi). It does not infer the PiShip source repository from its module path. The payload contains `node_modules` (including Pi and PiShip), `bin/`, declared `resources/` and adapters, the exact source `piship.yaml` and `piship.lock`, `package-lock.json`, and `metadata/target.json` and `metadata/inventory.json`. The inventory covers the canonical lock and all payload files. The launcher checks the recorded target and integrity before entering Pi and resolves only packages inside this directory. A machine must have Node.js 22.19.0 or newer installed separately. Build-time registry access may be needed; installation and launch do not fetch Node, Pi, or packages. The payload includes upstream package notices. It is the unit that releases wrap unchanged and that updates and rollback switch between ([release](release.md)).

The payload includes `piship.mjs`, so installation and diagnostics need no source checkout. `node <payload>/piship.mjs install <payload|release-dir|archive>` verifies its input (a release is verified with `verify-release` for this target first) and installs it for the current user:

```text
<install-home>/receipts/<id>.json     piship-install/v1 receipt: owned paths, retained releases, active and previous version, channel
<install-home>/apps/<id>/launch.mjs   reads the receipt and imports the active release's launcher
<install-home>/apps/<id>/<version>/   immutable payload per retained release
<install-home>/apps/<id>/.lifecycle.lock   one update, rollback, or uninstall at a time; may be removed by hand when none is running
<bin-home>/<command>                  shim that runs launch.mjs with Node (<command>.cmd on Windows)
```

`<install-home>` defaults to `~/.local/share/piship` and `<bin-home>` to `~/.local/bin`; set `PISHIP_INSTALL_HOME` and `PISHIP_BIN_HOME` to choose other user-writable locations. Add the bin directory to `PATH` yourself; PiShip does not edit shell profiles. Name, command, existing install, and pre-existing state collisions fail. `--use-existing-state` explicitly adopts state during install. `uninstall` removes the receipt, shim, launcher, and every retained payload; `purge <id> --yes` separately deletes the selected state after uninstall, together with the platform secret-store entries that its identity and credential metadata reference. Each deletion is confirmed; a secret that cannot be deleted fails the purge with `SECRET_STORE_UNAVAILABLE` and removes no state, so the metadata still names it and running purge again retries. A receipt written by an earlier PiShip still launches and uninstalls, but update and rollback need a reinstall.

## Lifecycle

A v1alpha4 release is the canonical payload plus release metadata, SBOM, notices, scan result, checksums, and install scripts in one deterministic archive per target. The branded `update` verifies signed channel metadata against keys pinned in the installed lock, downloads and verifies the newest release for the target, runs its launch check and the migration check, snapshots non-secret state, then activates it by atomically replacing the receipt; `launch.mjs` picks up the new active release on its next start. The previous release is retained, and `rollback` switches the receipt back to it after re-verifying it. Only one update or rollback runs at a time, and leftovers of an interrupted one are removed by the next. The active release performs the switch, so its audit, network, and credential handling apply; `piship update <id>` and `piship rollback <id>` delegate to it. The full contract is in [release](release.md).

## Managed launch flow

For a `piship/v1alpha2` payload the branded command:

1. Verifies payload integrity and the pinned Pi version, as in v0.1.
2. Refuses to run if `NODE_TLS_REJECT_UNAUTHORIZED=0`.
3. Resolves the allowlisted `${NAME}` runtime references from the launch environment; a missing value fails with `CONFIG_UNAVAILABLE`.
4. In managed mode, removes ambient credential variables (and proxy variables unless inherited) from the process environment, then applies the proxy and CA policy.
5. Loads the identity session from state, refreshing it when it is about to expire; without one it fails with `IDENTITY_REQUIRED`.
6. Ensures a runtime credential: reuses a valid one, refreshes before expiry, or acquires one from the broker.
7. Builds the effective model catalog (distribution ∩ entitlement ∩ live gateway ∩ user narrowing) and resolves the selected model; it never substitutes another model.
8. Creates a Pi `ModelRuntime` with an in-memory credential store and no `models.json` or `auth.json`, registers one provider named after the app ID, and governs it so only allowed models are visible, selectable, and callable.
9. Publishes the token-free enterprise context for extensions and starts Pi.

`login`, `logout`, `doctor`, `models`, and `config` are branded subcommands handled before Pi starts. Personal `piship/v1alpha1` payloads keep the v0.1 path: Pi-native providers and auth in isolated state.

## Governed launch flow

A `piship/v1alpha3` or `piship/v1alpha4` payload runs the access steps above for its deployment mode, then `GovernanceSession.open` establishes the controls in this order before Pi starts. Any mandatory control that fails stops the launch.

1. Audit: opens the sinks; an unreachable required sink fails with `AUDIT_UNAVAILABLE`.
2. Project: finds the project root and origin remote, classifies the origin, and discovers project resource candidates.
3. Sandbox: when required, builds the declared backend (the platform OS sandbox by default), checks its capabilities against the policy, prepares it, and proves it with a live probe or, for a backend that cannot wrap local processes, an outside check; otherwise fails with `SANDBOX_UNAVAILABLE`. PiShip owns policy and governance; the sandbox backend owns execution isolation ([sandbox backends](sandbox.md)).
4. Policy engine: enforced rules, team adapter rules, project restrictions, distribution defaults, and user rules, with the proven containment.
5. Declared resources: trust class, certified integrity and compatibility, then `*.load` policy; builtin extensions likewise.
6. Project resources: project trust dimension, resource trust, then policy.
7. MCP: authorizes and starts servers and lists their tools.
8. Capabilities and providers: computes the six capability axes and adds effective non-builtin provider extensions.

The selected model is then decided as `model.use`, and Pi starts with only the admitted resources, the governed tools, and PiShip's inline extensions. When the session ends, PiShip records `session.end`, stops MCP servers, removes the session temp directory, and flushes audit; if a required audit sink lost events, the session ends with `AUDIT_UNAVAILABLE`. `doctor`, `policy explain`, and `capabilities` inspect the same state without starting MCP servers or asking for approvals.

Governance uses these public Pi seams:

- `createAgentSession` with `noTools: "builtin"` and `customTools`: governed `read`, `write`, `edit`, and `bash` built with `createReadToolDefinition`, `createWriteToolDefinition`, `createEditToolDefinition`, and `createBashToolDefinition` and their `operations` hooks, plus MCP tools.
- `DefaultResourceLoader`, which receives only admitted instruction, skill, extension, prompt, and theme paths.
- Extension events: `tool_call` (policy and Plan mode, able to block), `user_bash` (governed operations for `!` commands), `before_agent_start` (Plan or Build prompt), `before_provider_request` (model request audit), and `session_start`.
- `registerTool` for `ask_user` and `registerCommand` for `/plan` and `/build`; the extension context's `hasUI`, `ui.confirm`, `ui.select`, `ui.setStatus`, and `ui.notify` for approvals and mode display.

Secrets held in a platform secret store live outside this directory, keyed by distribution ID; `logout` revokes and deletes them, while `purge` deletes only the entries that the identity, runtime credential, and sandbox credential metadata (or their discarded markers) reference, read from the file's text so that a damaged file still names them, without revoking them. Each file records which store holds its references: platform-store references are deleted from the platform store even when `secrets/` holds files, and file-store references go with the state directory. For a file written before the store was recorded, purge assumes the file store when `secrets/` holds any file, and the platform store otherwise. Both confirm every deletion and fail with `SECRET_STORE_UNAVAILABLE`, keeping the metadata that names the secret, when one cannot be deleted. Run `logout` before `purge`. Reinstalling the same distribution ID reuses these paths. Updates and rollbacks never move or rewrite them except as the last column says: the non-mutating migration check (`piship migrate-check`) decides for each class whether it is `safe`, `requires-review`, or `unsupported` for the target release, and an unreadable non-credential class stops the switch rather than being reinterpreted ([update lifecycle](release/update-lifecycle.md#migration-check-and-local-data)). Pi's resource loader disables ambient extension, skill, prompt, theme, and context discovery and receives only declared packaged paths. The working directory remains the user's project; its `.pi` resources are not distribution resources. For v1alpha3 and later, project resources that project trust admits are passed to the loader explicitly. An enforced sandbox denies contained processes read access to the whole state directory.

### Temporary directories

Every temporary directory a PiShip workflow makes is created by one helper in `@piship/contracts`: private (0700), with an ownership marker written before anything else. A `finally`, `dispose()`, or `exit` hook removes it in the normal case; none of them runs after SIGKILL, a machine reset, or power loss, so a later PiShip process removes what a dead owner left. The owner's own removal retries for a moment and, when the directory still cannot be removed (an open handle blocks it on Windows), leaves it for a later sweep instead of failing the operation it belonged to.

| Kind | Name | Where | Made by | Swept |
| --- | --- | --- | --- | --- |
| `sandbox` | `piship-sandbox-XXXXXX` | OS temp directory | a sandbox session (its `tmp` subdirectory is the sandbox's `TMPDIR`) | at every start |
| `probe` | `.piship-probe-XXXXXX` | the session temp directory, and the locations outside the write allowlist the sandbox probe checks | the live sandbox probe | the outside locations at each probe; never the session temp directory, which a contained command writes and which is reclaimed as a whole |
| `verify` | `piship-verify-XXXXXX` | OS temp directory | verification of a release archive | at every start |
| `launch-check` | `piship-launch-check-XXXXXX` | OS temp directory | the candidate's launch check before an update or rollback | at every start |
| `release-test` | `piship-release-test-XXXXXX` | OS temp directory | the required tests of `piship release` | at every start |
| `staging` | `.staging-XXXXXX` | the install home, and `apps/<id>` | install and update | at every start |
| `build` | `.piship-<distribution id>-XXXXXX` | the output directory of `piship build`, `dev`, and `test` | payload assembly (the payload is built in its `payload` subdirectory, so the marker never enters it) | only with `--reclaim-staging` |
| `release` | `.piship-release-<distribution id>-XXXXXX` | `<output>/releases` | `piship release` (the build is assembled in a `.piship-<id>-XXXXXX/payload` staging directory inside it, lands at `<stage>/<id>`, and is then moved to `.release/payload`; the names are short because Windows cannot run an npm install script in a directory longer than 260 characters) | only with `--reclaim-staging` |

The marker is the file `.piship-owner` (0600), one JSON record: `schema` (`piship-temporary-owner/v1`), `kind`, the directory's own `name`, the owner's `pid`, a random `instance` ID, a `host` token (a hash of the host name and, on Linux, the PID namespace), and `created`. The owner refreshes the marker's modification time every 15 minutes while it runs.

A sweep considers a directory only when all of this holds: its name has the exact shape of its kind (the prefix and six random characters); it is a real directory (never a link) of the current user, on the same filesystem as the directory that holds it (a mount point is never entered); its marker is a small regular file of the current user with a valid record that names this directory and this kind; this process does not hold it; and its owner is gone. The owner is gone when its process no longer exists on this host, which is judged at once; otherwise, including when the host token differs (another machine or container sharing the directory) or a process with that ID exists, when the marker was not refreshed for 24 hours. A process ID that an unrelated process took after a crash therefore delays the removal by up to a day. A running owner is not displaced because it refreshes; only a machine that sleeps, or a clock that jumps forward, for more than a day while the owner cannot refresh displaces a live owner's directory, the same trade as the lifecycle lock.

**Which roots are swept.** The marker is plain JSON that any process running as the user can write, and PiShip does not authenticate it (a key a contained command cannot read would have to live in the state directory, which does not exist for `piship build`). A sandboxed command can therefore plant a directory with a forged marker anywhere it may write. So a sweep runs without being asked only in roots a contained command cannot write, and the removal is built so that a forged marker costs its forger nothing it could not delete itself. What a contained command may write is the profile's `writeAllow`: the manifest's `sandbox.filesystem.write.allow` (`workspace`, `tmp`, `~`, or an absolute path) and the session's extra writable paths. Seatbelt denies every other write, and bubblewrap binds `/` read-only, binds only that list writable, and gives the sandbox a private `/tmp` unless `/tmp` itself is listed. Root by root:

- **The OS temp directory** (`piship-*` entries directly in it): swept at every start. A session's `tmp`, the one place contained commands write there, is a level below its `piship-sandbox-*` directory, which they cannot write.
- **The install home and `apps/<id>`** (`.staging-*`): swept at every start. The installed payload is given to the sandbox read-only.
- **The output of `piship build`, `dev`, `test`, and `release`** (`dist/`, `dist/releases`): not swept unless you pass `--reclaim-staging` to `piship build` or `piship release`. These lie in the project, the directory the sandbox is given to write, so a sandboxed agent can write them. The staging of a killed build keeps its marker next to the output it will be renamed into, and the next build or release says how many abandoned ones it found and how to remove them, without naming any path.

Both automatic roots hold only while the manifest does not list them as writable: a manifest that lists `/tmp`, `~`, or the install home makes that root writable to its own sandbox. On a system with a usable `rm` PiShip does not depend on it: the removal below holds either way. Without one (Alpine's BusyBox, Windows) the removal is a path-based walk with a gap no such walk can close, so there these roots carry the safety: `--reclaim-staging` in a `dist/` that sandboxed commands can write, or a sweep of an OS temp directory that the manifest lists as writable, can be steered by a contained command that is still running. Windows has no native sandbox backend, so that case does not arise there.

**Removal** does not trust a directory's name, which a process that can write its parent can swap for a link at any moment. A sweep records each abandoned directory's device and inode, then, for one directory: checks it is still that real directory; for a sandbox session renames its `tmp` (where contained commands write) first, which cuts every path a command that outlived the session has into it; renames the directory to a fresh `.piship-reclaim-*` name in the same parent, which no such path reaches, and requires the entry under that name to be the same real directory, otherwise it stops and removes nothing; and then removes the moved directory, as the single operand, with `rm -rf` (`--one-file-system` on GNU coreutils, `-x` on macOS and the BSDs), found at `/bin/rm`, `/usr/bin/rm`, or NixOS's `/run/current-system/sw/bin/rm`, never through `PATH`. `rm` walks with descriptor-relative calls, so it never follows a link, not even one given as its operand, and a directory swapped for a link while it runs is unlinked, not entered. PiShip uses it only after it proved, once per process on a throwaway tree, that it removes a tree, leaves what a link inside and a link operand point to, and accepts the flag; a candidate that is missing, fails, or proves nothing is skipped for the next, and BusyBox `rm` fails that check. Where there is no such `rm` (Windows, Alpine's BusyBox), a portable walk removes the contents first and the marker last; it never lists a path it has not just examined as a real directory, checks after listing that the directory is still the one it examined (same device and inode) before it acts on any name, never leaves the device, and unlinks a link without following it. What no path-based call can close is the moment between that check and the removal of each entry. That matters only where a sandboxed process can run beside the sweep, which no native sandbox does on Windows. A removal that fails puts the directory back under its name and marker, so the next sweep retries it; one that cannot even be put back, and one a removal left behind when it was killed after the move, keeps its `.piship-reclaim-*` name, and a later sweep removes such a directory, in the same way, once it has not changed for 10 minutes, whether or not its marker survived (`rm` removes in any order).

What is left alone: a directory that only shares a prefix, one with the exact shape but no marker, one with an unreadable, oversized, copied, or forged marker, another user's, a link, a mount point, and a running owner's. A link inside a reclaimed directory is unlinked, never followed. `doctor` says how many abandoned directories resist removal (a count, never a path). Directories made by earlier PiShip versions have no marker and are never removed automatically, however old: they cannot be told from a live older session (a sandbox session can run for days) or from a user's directory of the same shape, and deleting either cannot be undone. Delete them by hand: `piship-sandbox-*`, `piship-verify-*`, `piship-launch-check-*`, and `piship-release-test-*` under the OS temp directory, and `.staging-*` under the install home.

Where it runs: the branded launcher at every start (the OS temp directory, the install home, and `apps/<id>`), `piship release` (the OS temp directory for its tests), archive verification (`verify-release`, `migrate-check`, `install`, `diff` of an archive), install and update (the install home), update and rollback (the launch check), and every sandbox activation (its own kind in the OS temp directory) and probe (the outside locations). `piship build`, `dev`, `test`, and `release` report abandoned staging in their output directory, and remove it only with `--reclaim-staging`.

The sandbox session's marker sits beside its `tmp` directory, not in it: commands the sandbox contains can write only in `tmp`, so they can neither remove the marker (which would make the directory unrecoverable) nor forge one. A process killed in the instant between creating a directory and writing its marker leaves an empty, unmarked directory, which stays.
