# Architecture

PiShip is an open-source, company-first distribution and governance framework for branded Pi-based coding agents. Pi owns the agent loop, TUI, sessions, tools, model/runtime behavior, and extension execution. PiShip owns the distribution layer: manifest/configuration, pinned runtime, resources, reproducible payload, identity/credential/inference integration, and progressively policy/trust and lifecycle/release. Distribution repositories own their brand and declared resources. Pi source is neither forked nor patched.

The layers arrived in order. The personal distribution core came first (`piship/v1alpha1`). `piship/v1alpha2` added managed access and layered configuration. `piship/v1alpha3` added governance: policy, resource, provider, and project trust, capabilities, governed MCP, an OS sandbox for tool subprocesses, and audit. `piship/v1alpha4` added the production lifecycle: verifiable per-target release artifacts, signed update channels, verified update with atomic activation, rollback, and a migration check for local data ([release](release.md)). `piship/v1alpha5` added bootstrap update trust: a root role and a channel role with thresholds, kept by each installation as monotonic state and advanced by a sequential root refresh ([trust root](release/trust-root.md)). `piship/v1alpha6` (v0.9.0) adds Pi 1.x-native governance: tool exposure, Codemode and tool search, model types and virtual models, Pi packages, the data lifecycle and session export, and an enforcement status for every action derived from a runtime seam table ([manifest](manifest.md#v1alpha6-fields)). The [status page](status.md) records what current `main` supports, the evidence for each area, and how project milestones map to these schemas; see [compatibility](compatibility.md) for the Pi integration contract.

| Change | Home |
| --- | --- |
| Generic agent or runtime behavior | Upstream Pi |
| Manifest, lock, payload, installation, access orchestration | PiShip |
| Identity provider, credential broker, inference gateway | The organization (PiShip integrates, it does not become one) |
| Brand and selected resources | Distribution repository |

`identity`, `credentials`, and `inference` depend only on `contracts` and may not import each other; only `core` connects them, through `IdentitySession`, `CredentialRef`, and `ModelDefinition`. `policy`, `audit`, `sandbox`, and `mcp` are governance leaves: `policy` may import `contracts` and `schema`; `audit` and `sandbox` only `contracts`; `mcp` `contracts` and `sandbox`, so stdio servers spawn through the sandbox. `core` may import `policy` and `audit`; `pi` composes all four; `cli` imports only `core`, `schema`, and `contracts`. `adapter-sdk` may import only `contracts` and `sandbox`, and `adapter-conformance` only `adapter-sdk` ([decision 21](decisions.md)). `scripts/check-boundaries.mjs` enforces these imports and the rule that only `packages/pi` imports Pi. It discovers packages from `packages/*`, rejects relative imports that cross package directories, reports `@piship/*` dependencies a package declares but never imports, reads the pinned Pi version from `compatibility/pi.json`, and allowlists the package imports that core writes into generated launcher source.

## Canonical payload

`piship build` creates `dist/<id>` from package-owned build inputs prepared with `@piship/core`, using `npm ci --omit=dev` and exact locked dependencies, then removes optional packages whose npm lock `os`/`cpu` exclude the target (npm installs them anyway inside a shrinkwrapped dependency, as Pi was up to 1.0.0). It does not infer the PiShip source repository from its module path. The payload contains `node_modules` (including Pi and PiShip), `bin/`, declared `resources/` and adapters, `pi-packages/<id>/` for each declared Pi package (vendored with its own `node_modules`), the exact source `piship.yaml` and `piship.lock`, `package-lock.json`, and `metadata/target.json` and `metadata/inventory.json`. The inventory covers the canonical lock and all payload files. The launcher reads the recorded target and distribution lock before entering Pi, without an inventory scan and resolves only packages inside this directory. A machine must have Node.js 22.19.0 or newer installed separately. Build-time registry access may be needed; installation and launch do not fetch Node, Pi, or packages. The payload includes upstream package notices. It is the unit that releases wrap unchanged and that updates and rollback switch between ([release](release.md)).

The payload includes `piship.mjs`, so installation and diagnostics need no source checkout. `node <payload>/piship.mjs install <payload|release-dir|archive>` checks the archive digest and small input metadata and installs it for the current user:

```text
<install-home>/receipts/<id>.json     piship-install/v1 receipt: owned paths, retained releases, active and previous version, channel
<install-home>/apps/<id>/launch.mjs   reads the receipt and imports the active release's launcher
<install-home>/apps/<id>/<version>/   immutable payload per retained release
<install-home>/apps/<id>/.lifecycle.lock   one update, rollback, or uninstall at a time; may be removed by hand when none is running
<bin-home>/<command>                  shim that runs launch.mjs with Node (<command>.cmd on Windows)
```

`<install-home>` defaults to `~/.local/share/piship` and `<bin-home>` to `~/.local/bin`; set `PISHIP_INSTALL_HOME` and `PISHIP_BIN_HOME` to choose other user-writable locations. The state home (`PISHIP_STATE_HOME`, default `~/.piship`), install home, and bin home must be separate directories, none equal to or inside another: uninstall removes `<install-home>/apps/<id>` and purge `<state-home>/<id>` recursively, so an overlap would let uninstall delete state it keeps or purge delete another distribution's command. Install, uninstall, purge, update, rollback, and every launch refuse such a layout with `CONFIG_INVALID` before writing or deleting anything. The check compares real paths (the nearest existing ancestor, resolved), so a symlink or junction alias counts as the same directory, and on macOS and Windows paths that differ only in case do too. Add the bin directory to `PATH` yourself; PiShip does not edit shell profiles. Name, command, existing install, and pre-existing state collisions fail; the one exception is state that `piship test` or `dev` created before the first install, which carries a `piship-test-state/v1` marker and is adopted by that install ([manifest](manifest.md)). A first install runs under a per-distribution lock and a per-command lock, so of two concurrent installs one wins and the other fails. `apps/<id>` appears together with an ownership marker (`.initial-install.json`, `piship-initial-install/v1`) in one rename, and the receipt is the commit point, written before the shim. When a first install is killed at any point, the next install of the same distribution finishes it: before the receipt it moves the marked `apps/<id>` aside and installs again; after it, it writes a missing shim and removes the marker. A directory or shim that PiShip has no receipt or marker for is never removed; the collision error names it so the user can move it aside. `--use-existing-state` explicitly adopts state during install. `uninstall` removes the receipt, shim, launcher, and every retained payload. It removes the command shim only when it is exactly what PiShip wrote. A shim that was changed after install but still runs this install's launcher (a line added to it, say) is recognized as PiShip's shim with edits: uninstall refuses with nothing removed and names the recovery, `piship uninstall <id> --remove-edited-shim` (which also works with `--purge --yes`), after which the distribution installs again. Anything else at the command path (a file that does not run the launcher, a link, a large file) is not PiShip's and is never removed, with or without the flag: the error says to move it aside, after which uninstall goes through and leaves that path alone; `purge <id> --yes` separately deletes the selected state after uninstall, together with the platform secret-store entries that its identity and credential metadata reference. Each deletion is confirmed; a secret that cannot be deleted fails the purge with `SECRET_STORE_UNAVAILABLE` and removes no state, so the metadata still names it and running purge again retries. `uninstall <id> --purge --yes` does both in one command, for a user whose only PiShip is the installed release (`node <install-home>/apps/<id>/<version>/piship.mjs`, which uninstall removes): it deletes the referenced secret-store entries first, under the uninstall's locks and while the release is still installed, then removes the install, then the state. A secret it cannot delete fails it with `SECRET_STORE_UNAVAILABLE` before anything is removed, so the same command can be run again; a live runtime session refuses it as it refuses `uninstall`. Purge revokes nothing, so both refuse, before anything is removed, while the distribution is signed in: run `<command> logout` first ([logout and revocation](security.md#logout-and-revocation)). After a plain `uninstall` with no other PiShip left, `node <release-dir>/payload/piship.mjs purge <id> --yes` from the downloaded release (extracted again if needed) removes the state. A receipt written by an earlier PiShip still launches and uninstalls, but update and rollback need a reinstall. A receipt that cannot be read or fails a check is a `CONFIG_INVALID` error naming the file and the failed check, and, when its paths were recorded under another install or bin home, the `PISHIP_INSTALL_HOME` or `PISHIP_BIN_HOME` value to restore. Uninstall still removes such a distribution and trusts nothing the receipt names: under the current homes it removes `apps/<id>`, the receipt, and the shims whose exact content runs `apps/<id>/launch.mjs`. A command path recorded under another bin home is refused instead, until uninstall runs again with the `PISHIP_BIN_HOME` the error names. Another distribution's damaged receipt does not block an install: it still owns a command its remaining text names, and a shim it wrote is refused as an existing path.

## Lifecycle

A v1alpha4 release is the canonical payload plus release metadata, SBOM, notices, scan result, checksums, and install scripts in one deterministic archive per target. The branded `update` verifies signed channel metadata against keys pinned in the installed lock, downloads the newest archive for the target, checks its signed digest and metadata and the migration check, snapshots non-secret state, then activates it by atomically replacing the receipt; `launch.mjs` picks up the new active release on its next start. The previous release is retained, and `rollback` switches the receipt back to it after checking its target and metadata. Only one update or rollback runs at a time, and leftovers of an interrupted one are removed by the next. The active release performs the switch, so its audit, network, and credential handling apply; `piship update <id>` and `piship rollback <id>` delegate to it, passing each argument unchanged (on Windows Node runs the release's command script directly, never through `cmd.exe`, so a `--from` path with spaces or `& | ^ %` arrives as typed). Full payload verification is explicit (`doctor` or `verify-release`); routine launch, update, and rollback do not detect local payload edits; `piship repair <id> <release>` restores it in PiShip itself from a verified copy of the same release. The full contract is in [release](release.md).

## Managed launch flow

For a `piship/v1alpha2` payload the branded command:

1. Loads the target and distribution lock, then boots the pinned Pi version without a payload scan.
2. Refuses to run if `NODE_TLS_REJECT_UNAUTHORIZED=0`.
3. Resolves the allowlisted `${NAME}` runtime references from the launch environment; a missing value fails with `CONFIG_UNAVAILABLE`.
4. In managed mode, removes ambient credential variables (and proxy variables unless inherited) from the process environment, then applies the proxy and CA policy.
5. Loads the identity session from state, refreshing it when it is about to expire; without one it fails with `IDENTITY_REQUIRED`.
6. Ensures a runtime credential: reuses a valid one, refreshes before expiry, or acquires one from the broker.
7. Builds the effective model catalog (distribution ∩ entitlement ∩ live gateway ∩ user narrowing) and resolves the selected model; it never substitutes another model.
8. Creates a Pi `ModelRuntime` with an in-memory credential store and no `models.json` or `auth.json`, registers one provider named after the app ID, and governs it so only allowed models are visible, selectable, and callable.
9. Publishes the token-free enterprise context for extensions and starts Pi.

`login`, `logout`, `doctor`, `models`, and `config` are branded subcommands handled before Pi starts. Personal `piship/v1alpha1` payloads keep the v0.1 path: Pi-native providers and auth in isolated state.

## Governed launch flow

A `piship/v1alpha3` or later payload runs the access steps above for its deployment mode, then `GovernanceSession.open` establishes the controls in this order before Pi starts. Any mandatory control that fails stops the launch.

1. Audit: opens the sinks; an unreachable required sink fails with `AUDIT_UNAVAILABLE`.
2. Project: finds the project root and origin remote, classifies the origin, and discovers project resource candidates.
3. Sandbox: when required, builds the declared backend (the platform OS sandbox by default), checks its capabilities against the policy, prepares it, and proves it with a live probe or, for a backend that cannot wrap local processes, an outside check; otherwise fails with `SANDBOX_UNAVAILABLE`. PiShip owns policy and governance; the sandbox backend owns execution isolation ([sandbox backends](sandbox.md)).
4. Policy engine: enforced rules, team adapter rules, project restrictions, distribution defaults, and user rules, with the proven containment.
5. Declared resources: trust class, certified integrity and compatibility, then `*.load` policy; builtin extensions likewise.
6. Project resources: project trust dimension, resource trust, then policy.
7. MCP: authorizes and starts servers and lists their tools.
8. Capabilities and providers: computes the six capability axes and adds effective non-builtin provider extensions.

The selected model is then decided as `model.select`, and Pi starts with only the admitted resources, the governed tools, and PiShip's inline extensions. When the session ends, PiShip records `session.end`, stops MCP servers, removes the session temp directory, and flushes audit; if a required audit sink lost events, the session ends with `AUDIT_UNAVAILABLE`. `doctor`, `policy explain`, and `capabilities` inspect the same state without starting MCP servers or asking for approvals.

Governance uses these public Pi seams:

- `createAgentSession` with `noTools: "builtin"`, `customTools`, and `excludeTools` (hidden or denied tools and Pi's ungoverned `grep`, `find`, `ls`, and `powershell`): governed `read`, `write`, `edit`, and `bash` built with `createReadToolDefinition`, `createWriteToolDefinition`, `createEditToolDefinition`, and `createBashToolDefinition` and their `operations` hooks, plus MCP tools. The governed `bash` keeps Pi's definition (schema, prompt text, renderers) but runs PiShip's execute, which matches Pi's results and persists the full output in a session-owned directory ([security](security.md#tools-shell-and-plan-mode)).
- `DefaultResourceLoader`, which receives only admitted instruction, skill, extension, prompt, and theme paths.
- Extension events: `tool_call` (policy and Plan mode, able to block), `user_bash` (governed operations for `!` commands), `before_agent_start` (Plan or Build prompt), `before_provider_request` (model request audit), `tool_execution_start` (tool audit), `agent_start` and `agent_settled` (runtime mutation repair), `model_select`, `session_start`, and `session_shutdown` (the `pi-bash-*.log` files Pi recorded for the session's `!` commands, removed when the session closes).
- `customTools` for `ask_user` (an SDK custom tool, so an extension tool of that name cannot replace it) and `registerCommand` for `/plan`, `/build`, and `/auto`; the extension context's `hasUI`, `ui.confirm`, `ui.select`, `ui.setStatus`, and `ui.notify` for approvals and mode display.

## State

State defaults to `~/.piship/<id>` or `PISHIP_STATE_HOME/<id>`. The state path depends on the distribution ID, so relocation or reinstallation can resume the same session. State is never copied into the payload.

| --- | --- | --- | --- |
| `state.json` | `piship-state/v1` marker: distribution, active version, Pi and PiShip versions; not sensitive | Kept by uninstall; purge deletes it | Rewritten after each update and rollback activation; one that cannot be written then is a notice, not a failed activation, and the next update or rollback repairs it, as it does one that is empty or cannot be parsed |
| `agent/` | Pi config, model metadata, and, for Pi-native auth, Pi's local auth file; sensitive. Also Pi's crash log (`crashes.json`) and Pi's tool directory (`agent/bin`): the bundled `fd` and `rg` the launch copies from the payload, or the ones Pi downloads, because the branded command sets `PI_CODING_AGENT_DIR` to this directory before Pi is imported ([security](security.md#secrets)). Managed runtimes do not write `auth.json` or `models.json`. A package's declared configuration files (`extensions/…/*.json`, from `resources.packages[].agentFiles`) are written here at launch, with `.piship-agent-files.json` recording what PiShip last wrote so a user's edit is kept ([manifest](manifest.md#what-a-package-is-given-environment-and-files)) | Kept by uninstall; selected distribution purge deletes it | Kept in place; never snapshotted |
| `identity/session.json` | Non-secret identity metadata (subject, issuer, display claims, expiry), a secret-store reference, and the store that holds it (`secret_store`: `file` or `system`); no tokens. | `credentials-metadata/sandbox.json` | Non-secret metadata of the stored sandbox credential (`piship-sandbox-credential-metadata/v1`, written by `sandbox login` for a remote sandbox backend that declares `sandbox.credential: stored`): source, kind, generation reference such as `piship:<id>:sandbox#1`, acquisition time, the principal (issuer and subject) that stored it, the endpoint origins it may be sent to, and the store that holds the secret (`secret_store`); no secret. | `migration/snapshots/` | Non-secret pre-update copies of preferences and user policy (`piship-snapshot/v1`); never credentials | The last three completed snapshots kept, by creation sequence, not by time; interrupted ones are removed by the next snapshot; purge deletes them | Built in a staging directory and published by one rename before each update activation |

| Trust and approval decisions | Startup and in-session `ask` answers apply to the current process only and are never written to disk; project trust is recomputed from the manifest and git origin at each launch. The one persisted approval setting is the user's auto mode switch, `config/auto.json` (above), which approves `ask` decisions from the distribution defaults while it is on and the release allows it; it stores no individual answer | Answers are gone when the process exits | Nothing to migrate |
| Audit buffers | In-memory event queue for HTTP sinks; metadata only | Flushed within the close deadline; undelivered optional events are dropped and counted | Nothing to migrate |
| Session temporary files | `piship-sandbox-*` under the OS temp directory, private to one session (0700); may hold tool output. It holds an owner marker and, beside it, the `tmp` directory that is the sandbox's `TMPDIR` | Removed when the session ends and on normal process exit; after SIGKILL or a machine reset, by the next activation or launch once its process is gone ([temporary directories](#temporary-directories)) | Not migrated |
| Atomic-write temporaries | `<file>.p<pid>-<random>.tmp` beside a state file or the install receipt while it is replaced; the new content of that file, so as sensitive as it is (metadata, or a secret for the file secret store). The audit rotation and earlier PiShip versions name it `<file>.<random>.tmp`, and local metrics `metrics.json.<pid>.tmp` | Removed when the write fails. One a killed writer left is removed when the distribution next starts, once its process no longer exists or it is older than ten minutes (a name without a process ID: only by age); `logout` removes every identity, credential, and file-store temporary under the credential and identity locks; the next update or rollback removes the receipt's; purge deletes them | Never read or adopted as state |
| Download and staging data | `.staging-*` under the install home and under `apps/<id>` while an install or update runs, `piship-verify-*` and `piship-launch-check-*` under the OS temp directory during verification and launch checks, and, beside the output of `piship build`, `piship dev`, `piship test`, and `piship release`, `.piship-<id>-*` and `.piship-release-<name>-*` staging (the release tests use `piship-release-test-*` under the OS temp directory) | Removed when the operation finishes; leftovers of a killed run under the install home, `apps/<id>`, and the OS temp directory are removed by the next launch, verification, install, update, or rollback once its process is gone ([temporary directories](#temporary-directories)); staging beside a build's or release's output is removed only when the next `piship build` or `piship release` is given `--reclaim-staging` and is reported otherwise; what is under `apps/<id>` and not named by the receipt is also removed by the next update or rollback, and `doctor` reports it in the meantime | Never activated |
| Checkpoints and agent memory | Not implemented by PiShip; Pi session files under `sessions/` are the only conversation history | — | — |

Secrets held in a platform secret store live outside this directory, keyed by distribution ID; `logout` revokes and deletes them, while `purge` deletes only the entries that the identity, runtime credential, and sandbox credential metadata (or their discarded markers) reference, read from the file's text so that a damaged file still names them, without revoking them. Each file records which store holds its references: platform-store references are deleted from the platform store even when `secrets/` holds files, and file-store references go with the state directory. For a file written before the store was recorded, purge assumes the file store when `secrets/` holds any file, and the platform store otherwise. Both confirm every deletion and fail with `SECRET_STORE_UNAVAILABLE`, keeping the metadata that names the secret, when one cannot be deleted. Run `logout` before `purge`. Reinstalling the same distribution ID reuses these paths. Updates and rollbacks never move or rewrite them except as the last column says: the non-mutating migration check (`piship migrate-check`) decides for each class whether it is `safe`, `requires-review`, or `unsupported` for the target release, and an unreadable non-credential class stops the switch rather than being reinterpreted ([update lifecycle](release/update-lifecycle.md#migration-check-and-local-data)). Pi's resource loader disables ambient extension, skill, prompt, theme, and context discovery and receives only declared packaged paths. The working directory remains the user's project; its `.pi` resources are not distribution resources. For v1alpha3 and later, project resources that project trust admits are passed to the loader explicitly. An enforced sandbox denies contained processes read access to the whole state directory.

### Sessions

A launch (interactive or `--smoke`) continues the project's most recent Pi session in its session directory: the most recently modified `*.jsonl` file whose header names the current directory, the file Pi's `SessionManager.continueRecent()` would choose. PiShip chooses it, checks it, and takes ownership of it before Pi reads it, then opens it with `SessionManager.open()`. `<command> --new-session` (also `--new-session --smoke`) starts a new session without reading the most recent one.

- **Damaged sessions are not resumed.** Pi 1.0.3, like 1.0.2 and 1.0.0, skips a line that does not parse and completes a truncated last record, so it would continue with part of the conversation missing. Before the resume, PiShip reads the file in bounded chunks and requires that every non-blank line is a JSON session entry, that there is exactly one header and it comes first, that entry IDs are unique, that every parent exists and the parent references form no cycle, that compaction, context edit, branch summary, and label references name entries in the file, and that the last record is complete (a complete last record that only lacks its newline is accepted; Pi adds the newline). Version 1 sessions, which have no entry IDs, get only the line and header checks; Pi migrates them as before. A damaged file stops the launch with `CONFIG_UNAVAILABLE`, what is wrong and on which line, the file's path, and `--new-session` as the action. The file is not repaired, moved, or deleted. The acceptance session of `--smoke` (and so `doctor`, `piship test`, and `piship dev --smoke`), which holds no user work, is the exception: a damaged or oversized one is replaced by a new acceptance session with a notice, and the old file is kept.
- **Very large sessions are not resumed automatically.** Pi holds every entry of a session in memory, and compaction does not shrink the file. A most recent session over 64 MiB is not read at all: the launch stops with `CONFIG_UNAVAILABLE`, the file's size and path, and `--new-session` as the action. The limit is fixed. The file is kept across update, rollback, and uninstall, and across logout and launch unless a piship/v1alpha6 `data` section purges or expires sessions.
- **One process writes a session file.** Each launch holds an owner record for the session file it writes, in `.piship-owners/` beside the session files (`piship-session-owner/v1`: process ID, process start identity, host, a random instance ID, and on Linux the boot ID and PID namespace). When the most recent session is owned by another live process, the launch starts a new session and says so, instead of appending to the same file. A record whose process is gone, or whose process ID now belongs to a process with another start identity, is taken over, so a crash does not lock a session; so is a record of this host name written before the host last started (a Linux boot ID that differs), which assumes host names are unique among machines sharing the session directory. A record whose process this process cannot verify is neither live nor gone: one from another host, from another PID namespace (a container that shares the home directory, even under the same host name, or a Linux record from v0.7.0, which named no namespace), or whose process exists but has no start identity to compare (including the macOS start time in the local-time text earlier builds recorded). Such a record is never taken over and never expires: the launch starts a new session, and a `/resume` of that session is refused, each with a notice that says why it cannot be verified and names the record file. When no process on the other host or in the other container uses the session, delete that record and continue the session. This is a limit: PiShip cannot see processes outside its own host and PID namespace, so a crashed owner there leaves a record that only the user can release. The owner refreshes its record every minute. The record follows `/new`, `/resume`, and forks inside the session, and `/resume` of a session another live process owns is refused with a notice. A `/resume` into a session over 64 MiB or a damaged one is refused the same way, before Pi loads it, with the file unchanged, and so is one PiShip could not check (the file is gone, or reading it failed with `EMFILE`, `EIO`, or another error): the notice names the error code, and a check that did not finish never counts as safe; if another process takes the file between that check and the switch, the switch fails and the session is not used. The record is removed when the session ends. Two launches that start at the same moment may each see the other and both start a new session; neither appends to a file the other writes. Sessions in different projects, and the acceptance sessions of `--smoke`, which live in `sessions/acceptance/`, do not affect each other.

### Temporary directories

Every temporary directory a PiShip workflow makes is created by one helper in `@piship/contracts`: private (0700), with an ownership marker written before anything else. A `finally`, `dispose()`, or `exit` hook removes it in the normal case; none of them runs after SIGKILL, a machine reset, or power loss, so a later PiShip process removes what a dead owner left. The owner's own removal retries for a moment and, when the directory still cannot be removed (an open handle blocks it on Windows), leaves it for a later sweep instead of failing the operation it belonged to.

| Kind | Name | Where | Made by | Swept |
| --- | --- | --- | --- | --- |
| `sandbox` | `piship-sandbox-XXXXXX` | OS temp directory | a sandbox session (its `tmp` subdirectory is the sandbox's `TMPDIR`) | at every start |
| `probe` | `.piship-probe-XXXXXX` | the session temp directory, and the locations outside the write allowlist the sandbox probe checks | the live sandbox probe | the outside locations at each probe; never the session temp directory, which a contained command writes and which is reclaimed as a whole |
| `verify` | `piship-verify-XXXXXX` | OS temp directory | verification of a release archive | at every start |
| `launch-check` | `piship-launch-check-XXXXXX` | OS temp directory | the candidate's launch check before an update or rollback | at every start |
| `release-test` | `piship-release-test-XXXXXX` | OS temp directory | the required tests of `piship release` | at every start |
| `staging` | `.staging-XXXXXX` | the install home, and `apps/<id>` | install and update | at every start |
| `build` | `.piship-<distribution id>-XXXXXX` | the output directory of `piship build`, `dev`, and `test` | payload assembly (the payload is built in its `payload` subdirectory, so the marker never enters it) | only with `--reclaim-staging` |
| `release` | `.piship-release-<distribution id>-XXXXXX` | `<output>/releases` | `piship release` (the build is assembled in a `.piship-<id>-XXXXXX/payload` staging directory inside it, lands at `<stage>/<id>`, and is then moved to `.release/payload`; the names are short because Windows cannot run an npm install script in a directory longer than 260 characters) | only with `--reclaim-staging` |

The marker is the file `.piship-owner` (0600), one JSON record: `schema` (`piship-temporary-owner/v1`), `kind`, the directory's own `name`, the owner's `pid`, a random `instance` ID, a `host` token (a hash of the host name and, on Linux, the PID namespace), and `created`. The owner refreshes the marker's modification time every 15 minutes while it runs.

A sweep considers a directory only when all of this holds: its name has the exact shape of its kind (the prefix and six random characters); it is a real directory (never a link) of the current user, on the same filesystem as the directory that holds it (a mount point is never entered); its marker is a small regular file of the current user with a valid record that names this directory and this kind; this process does not hold it; and its owner is gone. The owner is gone when its process no longer exists on this host, which is judged at once; otherwise, including when the host token differs (another machine or container sharing the directory) or a process with that ID exists, when the marker was not refreshed for 24 hours. A process ID that an unrelated process took after a crash therefore delays the removal by up to a day. A running owner is not displaced because it refreshes; only a machine that sleeps, or a clock that jumps forward, for more than a day while the owner cannot refresh displaces a live owner's directory, the same trade as the lifecycle lock.

**Which roots are swept.** The marker is plain JSON that any process running as the user can write, and PiShip does not authenticate it (a key a contained command cannot read would have to live in the state directory, which does not exist for `piship build`). A sandboxed command can therefore plant a directory with a forged marker anywhere it may write. So a sweep runs without being asked only in roots a contained command cannot write, and the removal is built so that a forged marker costs its forger nothing it could not delete itself. What a contained command may write is the profile's `writeAllow`: the manifest's `sandbox.filesystem.write.allow` (`workspace`, `tmp`, `~`, or an absolute path) and the session's extra writable paths. Seatbelt denies every other write, and bubblewrap binds `/` read-only, binds only that list writable, and gives the sandbox a private `/tmp` unless `/tmp` itself is listed. Root by root:

- **The OS temp directory** (`piship-*` entries directly in it): swept at every start. A session's `tmp`, the one place contained commands write there, is a level below its `piship-sandbox-*` directory, which they cannot write.
- **The install home and `apps/<id>`** (`.staging-*`): swept at every start. The installed payload is given to the sandbox read-only.
- **The output of `piship build`, `dev`, `test`, and `release`** (`dist/`, `dist/releases`): not swept unless you pass `--reclaim-staging` to `piship build` or `piship release`. These lie in the project, the directory the sandbox is given to write, so a sandboxed agent can write them. The staging of a killed build keeps its marker next to the output it will be renamed into, and the next build or release says how many abandoned ones it found and how to remove them, without naming any path.

Both automatic roots hold only while the manifest does not list them as writable: a manifest that lists `/tmp`, `~`, or the install home makes that root writable to its own sandbox. On a system with a usable `rm` PiShip does not depend on it: the removal below holds either way. Without one (Alpine's BusyBox, Windows) the removal is a path-based walk with a gap no such walk can close, so there these roots carry the safety: `--reclaim-staging` in a `dist/` that sandboxed commands can write, or a sweep of an OS temp directory that the manifest lists as writable, can be steered by a contained command that is still running. Windows has no native sandbox backend, so that case does not arise there.

**Removal** does not trust a directory's name, which a process that can write its parent can swap for a link at any moment. A sweep records each abandoned directory's device and inode, then, for one directory: checks it is still that real directory; for a sandbox session renames its `tmp` (where contained commands write) first, which cuts every path a command that outlived the session has into it; renames the directory to a fresh `.piship-reclaim-*` name in the same parent, which no such path reaches, and requires the entry under that name to be the same real directory, otherwise it stops and removes nothing; and then removes the moved directory, as the single operand, with `rm -rf` (`--one-file-system` on GNU coreutils, `-x` on macOS and the BSDs), found at `/bin/rm`, `/usr/bin/rm`, or NixOS's `/run/current-system/sw/bin/rm`, never through `PATH`. `rm` walks with descriptor-relative calls, so it never follows a link, not even one given as its operand, and a directory swapped for a link while it runs is unlinked, not entered. PiShip uses it only after it proved, once per process on a throwaway tree, that it removes a tree, leaves what a link inside and a link operand point to, and accepts the flag; a candidate that is missing, fails, or proves nothing is skipped for the next, and BusyBox `rm` fails that check. Where there is no such `rm` (Windows, Alpine's BusyBox), a portable walk removes the contents first and the marker last; it never lists a path it has not just examined as a real directory, checks after listing that the directory is still the one it examined (same device and inode) before it acts on any name, never leaves the device, and unlinks a link without following it. What no path-based call can close is the moment between that check and the removal of each entry. That matters only where a sandboxed process can run beside the sweep, which no native sandbox does on Windows. A removal that fails puts the directory back under its name and marker, so the next sweep retries it; one that cannot even be put back, and one a removal left behind when it was killed after the move, keeps its `.piship-reclaim-*` name, and a later sweep removes such a directory, in the same way, once it has not changed for 10 minutes, whether or not its marker survived (`rm` removes in any order).

What is left alone: a directory that only shares a prefix, one with the exact shape but no marker, one with an unreadable, oversized, copied, or forged marker, another user's, a link, a mount point, and a running owner's. A link inside a reclaimed directory is unlinked, never followed. `doctor` says how many abandoned directories resist removal (a count, never a path). Directories made by earlier PiShip versions have no marker and are never removed automatically, however old: they cannot be told from a live older session (a sandbox session can run for days) or from a user's directory of the same shape, and deleting either cannot be undone. Delete them by hand: `piship-sandbox-*`, `piship-verify-*`, `piship-launch-check-*`, and `piship-release-test-*` under the OS temp directory, and `.staging-*` under the install home.

Where it runs: the branded launcher at every start (the OS temp directory, the install home, and `apps/<id>`), `piship release` (the OS temp directory for its tests), archive verification (`verify-release`, `migrate-check`, `install`, `diff` of an archive), install and update (the install home), update and rollback (the launch check), and every sandbox activation (its own kind in the OS temp directory) and probe (the outside locations). `piship build`, `dev`, `test`, and `release` report abandoned staging in their output directory, and remove it only with `--reclaim-staging`.

**A start does not wait for the sweep.** The launcher's sweep and a sandbox activation's each spend at most 2 seconds starting removals (a removal that has started gets at least one second before it is stopped, so even a short budget makes progress on a large directory). When the time is up, no further removal starts; one that is still running is stopped (`rm` is ended, the portable walk stops before its next directory), and the directory is put back under its name and marker, with whatever was removed by then gone. What is left is removed by later starts, and the launcher says how many directories it left (`doctor` counts what remains). The budget only decides when the work is done, never what is removed: which directories count as abandoned, and every check before and during a removal, are the ones above. Install, update, rollback, verification, and `piship release` sweep without a budget.

The sandbox session's marker sits beside its `tmp` directory, not in it: commands the sandbox contains can write only in `tmp`, so they can neither remove the marker (which would make the directory unrecoverable) nor forge one. A process killed in the instant between creating a directory and writing its marker leaves an empty, unmarked directory, which stays.
