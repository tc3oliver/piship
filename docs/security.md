# Security architecture

Upstream Pi runs the agent. PiShip validates distribution inputs, locks declared resources and package identities, and verifies packaged file hashes before entering Pi. A distribution's extensions are executable code with the user's process privileges. For `piship/v1alpha3` and later distributions PiShip also governs what loads and what tools may do, and can run tool subprocesses and MCP stdio servers inside an OS sandbox (see [Governance](#governance)). The Pi process itself is never sandboxed.

## Payload and state

The installer owns only its receipt, installed payload, and command shim. Existing install, command, and state collisions fail by default. `uninstall` preserves `~/.piship/<id>`; `purge <id> --yes` removes that one distribution's state after uninstall (`uninstall <id> --purge --yes` does both, deleting the secrets before it removes the install; both refuse while the distribution is signed in, so run `<command> logout` first, see [logout and revocation](#logout-and-revocation)), and deletes the platform secret-store entries its identity, runtime credential, and sandbox credential metadata reference, confirming each deletion; a secret it cannot delete fails the purge before any state is removed. The payload is separate from mutable config, sessions, cache, logs, credential metadata, and other runtime data. There is no shared runtime cache.

Temporary directories (a release's extraction, launch-check scratch, sandbox session temp that can hold tool output, build, release, install and update staging) are private (0700), carry an owner marker (process, instance, host, creation time), and are removed when the operation ends. A process killed by SIGKILL, a machine reset, or power loss cannot remove its own, so the next PiShip start removes a directory only when its marker is valid and its owner is gone, or has not refreshed the marker for 24 hours (a machine that sleeps, or a clock that jumps forward, for more than a day while the owner cannot refresh displaces a live owner's directory, and a reused process ID delays a removal by up to that day). It never removes a running process's directory, an unmarked one, a link, another user's directory, or anything across a mount ([temporary directories](architecture.md#temporary-directories)). The marker is not authenticated: a sandboxed command can write one wherever the sandbox lets it write. So the start-up sweeps run only in roots a contained command cannot write (the OS temp directory, the install home, `apps/<id>`), never in the output directory of `piship build` or `piship release`, which lies in the project, unless you pass `--reclaim-staging`; and each removal checks identity, not names: the directory is renamed to a fresh name and verified to be the same real directory, then removed by `rm`, which does not follow a link, so a directory swapped for a link while it is removed is never followed. Without a usable `rm` (Windows, Alpine's BusyBox) a portable walk does the same checks before each listing, and what no path-based call can close is the moment between its check and each removal; there the choice of roots carries the safety, so a sandboxed command that is still running could steer `--reclaim-staging` in a `dist/` it can write, or a sweep of an OS temp directory the manifest lists as writable (Windows has no native sandbox backend, so this does not arise there). Directories made by earlier PiShip versions have no marker and are left for the user to delete.

Pi receives a dedicated agent directory (`<state>/agent`, which also holds Pi's crash log and the tools Pi downloads), user and acceptance session directories, in-memory settings, and a loader with ambient extension, skill, prompt, theme, and context discovery disabled. Only declared resources are packaged. PiShip checks the session file a launch would continue before Pi reads it: a damaged one, or one over 64 MiB, is not resumed (`--new-session` starts a new session and leaves the file alone; the `--smoke` acceptance session, which holds no user work, is replaced by a new one instead), and a session another live process owns is never appended to; an owner on another host or in another PID namespace (a container sharing the home directory) cannot be verified, so its session is neither resumed nor taken over until the user deletes its owner record ([sessions](architecture.md#sessions)). Packaging rejects symlinks in resource roots, nested files, and adapter paths. For v1alpha1 and v1alpha2 distributions, project files remain accessible to Pi tools and trusted extensions, and PiShip does not enforce project trust or tool policy.

The SHA-256 inventory detects accidental or unauthorized file changes only while the inventory itself is trusted. For `piship/v1alpha4` and later releases, signed channel metadata and build provenance establish where an artifact came from ([Releases and updates](#releases-and-updates)). Nothing here is a security boundary against a malicious local user who can rewrite both files and inventory.

## Secrets

- `piship.yaml` and `piship.lock` never hold secrets. The schema rejects secret fields, client secrets, and runtime variables whose names look like secrets. It cannot detect every secret embedded in an otherwise allowed string, so never commit one.
- Identity tokens and runtime credentials are wrapped in `SecretValue`, which prints, serializes, and inspects as `[REDACTED]`. Only an explicit `reveal()` returns the value. Every value held as a `SecretValue` (six characters or longer) is scrubbed from later diagnostics, as is, base64 and base64url-encoded, percent-encoded, and JSON-escaped; a secret encoded together with other bytes (`user:secret` in a Basic credential) is caught only by the token shapes. `PiShipError` messages, actions, and details, launcher and CLI error output (including an error no code path catches, which the launcher prints redacted before it exits with status 1; while Pi's interactive UI runs, Pi's own crash handler prints it and records it in Pi's crash log, which `/bug` attaches to a report, and PiShip redacts the error object in place first: its message, stack, and nested strings such as its `cause`), `config explain`, and `doctor` pass through the same redaction, which also removes common token shapes (`Bearer` and `Basic` credentials, `sk-` keys, JWTs, GitHub, GitLab, Slack, AWS, and Google API tokens, PEM private keys, and secret-named `key=value` pairs). MCP results sent to the model, stderr, and audit events use this one pattern set. In structured values, keys named like a credential (`token`, `apiKey`, `x-api-key`, `apiToken`, `authorization`, `cookie`, `password`, and their spellings) are replaced whatever they hold, bytes are shown as redacted text, and an audit detail key that holds a secret is dropped.
- State files hold only non-secret metadata and secret-store references ([architecture](architecture.md#state)).
- Pi records a failed model request's error text, and the provider diagnostics some providers attach (error messages, stacks, and details), in the session file (`sessions/user/` and `sessions/acceptance/`). PiShip runs both through the same redaction before Pi keeps the message (a `message_end` handler of the built-in `piship-redaction` extension, which Pi runs after the distribution's extensions), so a gateway that echoes the request's Authorization header into its error leaves neither the registered runtime credential nor a bearer shape in that error text, as the session file, the agent state, and the terminal hold it. The status and wording stay, so retries and the credential-rejection check read the redacted text as before. If the redaction itself fails, the error text is replaced whole by `[REDACTED error text]` and the diagnostics are dropped, since Pi would otherwise keep the original message. The distribution's own extensions see the error text before redaction, as they see everything else in the process. A secret the gateway echoes in a form that is neither one of the registered encodings nor a token shape is not recognized.
- A session file is not a secret-free record. What PiShip scrubs before Pi writes it is exactly two things: a failed request's error text and diagnostics (above), and an MCP tool's result, which is redacted and capped before the model, and so Pi, sees it. Everything else Pi records as it is: the user's prompts, the model's output (its text, its thinking, and the arguments of its tool calls), and the results of Pi's built-in tools (a command's output, a file's contents, an edit). PiShip keeps the credentials it holds out of what feeds those: the runtime credential and identity tokens live in memory and the secret store, never in Pi's environment ([managed runtime isolation](#managed-runtime-isolation)), and the sandbox credential never reaches a sandbox command. But a secret that a command prints, a file holds, the user pastes, or the model writes out is kept in the session file verbatim, and so is a credential an in-process extension or an unsandboxed command reads from wherever it is stored. Treat `sessions/` as private project data ([state](architecture.md#state)).
- Pi's crash log is kept in the distribution's state. Pi's interactive crash handler keeps the last few uncaught errors in `crashes.json` in Pi's agent directory. PiShip sets `PI_CODING_AGENT_DIR` to `<state>/agent` on every launch, after a managed launch has removed the inherited `PI_` variables with the other ones, so the file is `<state>/agent/crashes.json` and not under `~/.pi/agent/`. `logout` and `uninstall` keep it with the rest of the state, and `purge` removes it. The in-place redaction of an uncaught error described above has three limits. It is installed at Pi's `session_start`, so an error thrown in the short startup window between Pi registering its crash handler and that event is printed and recorded unredacted. It rewrites strings the error holds in its own properties, and those of the objects it holds, four levels deep; a value held inside a `Headers` or `Map` object on an error property (a failed response's headers, say) is not rewritten. And a thrown primitive, such as a bare string, cannot be changed in place and is printed and recorded as it is.
- PiShip sets Pi's startup and network defaults on every launch. Environment: `PI_SKIP_VERSION_CHECK=1` (no request to pi.dev for the latest Pi version and no "Update Available ... Run `pi update`" notice: a distribution's users have no `pi` command, and Pi changes only with a new distribution release), `PI_TELEMETRY=0`, and `PI_CODING_AGENT_DIR=<state>/agent`. In-memory Pi settings: `enableInstallTelemetry: false`; `lastChangelogVersion` set to the Pi version (the settings store is new on each launch, so without it Pi took every session for a fresh install and sent pi.dev an install report); `quietStartup: true` (no Pi logo, key hints, or resource listing at startup); and `tuiMode: "regular"` (Pi 1.0 starts fullscreen by default; a distribution keeps the terminal's scrollback). Because Pi's agent directory is in the state, the `fd` and `rg` binaries Pi downloads from github.com, when one is neither on `PATH` nor in `<state>/agent/bin/` (at interactive start, and when the agent first uses Pi's find or grep tool), land in the distribution's state, where `purge` removes them; each distribution downloads its own copies. A managed launch also sets `PI_OFFLINE=1`, after it has removed the inherited `PI_` variables ([managed runtime isolation](#managed-runtime-isolation)): Pi then makes no request of its own (no model catalog refresh, no `fd` or `rg` download), so put `fd` and `rg` on `PATH` in a managed distribution for `@` completion and Pi's find and grep tools. A personal distribution does not go offline by itself: `PI_OFFLINE=1` in the shell stops the download and Pi's other network requests there. Four things stay Pi's, and no public Pi switch changes them: the terminal title is still "π" (Pi's `APP_TITLE`), the exit hint still says "To resume this session: pi --session-dir ... --session ..." (the branded command continues the project's most recent session by itself, and `--new-session` starts a new one), Pi still adds its `/bug` hint to a PiShip identity or credential failure in the TUI (#139), and the built-in `/share` command, which is under [Limits](#limits).
- A remote sandbox backend's stored credential (`sandbox.credential: stored`) enters only through `<command> sandbox login`: a no-echo prompt on stderr, or the first line of a piped stdin. There is no command-line flag, environment variable, file, or in-session command for it, so PiShip never puts it in argv, shell history, the model context, or a Pi session file. It is kept in the same secret store as the runtime credential, bound to the principal and to the origins of the sandbox endpoint (and Kubernetes router) it was stored for, and it is never in the manifest, the lock, audit events, `doctor` output, rollback snapshots, or a sandbox command's environment ([sandbox credentials](sandbox.md#credentials)).
- Secrets go to the platform store first: macOS Keychain, Linux Secret Service, or Windows Credential Manager. Secrets reach these tools on standard input, never as command arguments. `storage.provider: system` never silently falls back to a file: an unavailable store fails with `SECRET_STORE_UNAVAILABLE`.
- The file store is an explicit opt-in: owner-only (0700 directory, 0600 files) atomic writes under `<state>/secrets/`. Values are base64url-encoded, not encrypted. A managed manifest must set `acknowledgePlaintext: true` to use it, and `login`, `doctor`, and `config explain` report it as a plaintext fallback.

Unit tests exercise the platform stores through a command-runner double. The live test (`PISHIP_LIVE_SECRET_STORE=1`) runs against the real stores in the `CI` check job on every pull request: macOS Keychain, Windows Credential Manager, and the Linux Secret Service under GNOME Keyring on a private D-Bus session. `managed-clean-machine`, `user-switching` (its `system` variant) and `lifecycle-secret-store` use the live store on every Portable E2E target (`managed` and `headless` use the file store), and the Reference E2E uses the Linux Secret Service. What each tier has shown on which commit is on the [status page](status.md#recorded-evidence).

## Managed runtime isolation

In managed mode the branded command removes ambient credential variables from its own environment before Pi starts, so Pi, its tools, and child processes do not inherit them. This covers names containing `API_KEY`, `ACCESS_KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `CREDENTIAL`, or `AUTH`, and common provider prefixes such as `OPENAI_`, `ANTHROPIC_`, `AWS_`, `AZURE_`, `GOOGLE_CLOUD_`, `GITHUB_TOKEN`, and `PI_`. Declared runtime variables, `SSH_AUTH_SOCK`, and `GPG_AGENT_INFO` are kept. Proxy variables are also removed when `network.proxy.inheritEnvironment` is false. PiShip then sets its own Pi switches (`PI_SKIP_VERSION_CHECK`, `PI_TELEMETRY`, `PI_CODING_AGENT_DIR`, and `PI_OFFLINE`; see [Secrets](#secrets)), so no other inherited `PI_` variable reaches Pi. `--smoke` reports the removed names, never values.

The managed Pi `ModelRuntime` uses an in-memory credential store and no `models.json` or `auth.json`, so personal Pi auth under `~/.pi` or the distribution's `agent/` is not read. PiShip registers one provider, named after the app ID, for the declared gateway. Only allowed models are listed, selectable, authorized, or callable; built-in, environment, file-based, and extension-registered providers receive no credentials; Pi's provider `login` and `setRuntimeApiKey` are refused. A resumed session on a model that is no longer allowed is switched to the resolved model with a visible notice.

Model governance is not containment. Extensions run in-process with the user's privileges: they can read files, spawn processes, and make their own network requests. PiShip does not isolate them from the credential while a request is in flight.

## Network and TLS

PiShip-managed requests (OIDC, broker, gateway probes, Streamable HTTP MCP servers, and HTTP audit sinks) use a managed fetch:

- TLS verification is always on. A launch with `NODE_TLS_REJECT_UNAUTHORIZED=0` fails with `TLS_POLICY_VIOLATION`, and the manifest cannot disable verification.
- Plain HTTP is accepted only for loopback hosts, intended for local fixtures. Endpoint URLs may not embed credentials, query strings, or fragments. The one exception is the update channel of a distribution that sets `updates.transport: http-allowed` ([update transport](#releases-and-updates)); OIDC, the broker, the gateway, MCP servers, audit sinks, and remote sandboxes keep this rule whatever that field says.
- `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` are honored when inherited (either case; a lowercase name wins, and a host in `NO_PROXY` is contacted directly). `network.tls.additionalCA` bundles are added to, never replace, the default roots. A bundle that lacks the server's certificate fails the request; nothing relaxes verification to make it pass, and an `https` endpoint is never retried or redirected over plain HTTP.
- With `network.privateOnly`, only the declared issuer, broker, and gateway hosts, `network.allowHosts`, and, for update commands, the `updates.source` host may be contacted; anything else fails with `NETWORK_DENIED`. OIDC endpoints that discovery returns on other hosts, and Streamable HTTP MCP servers or HTTP audit sinks on other hosts, must be listed in `allowHosts`. Managed mode requires `network.publicFallback: deny`, which turns private-only on for every managed launch; `doctor` shows the effective outbound state and warns about HTTP MCP servers and audit sinks whose hosts are not declared. A sink or server host is never allowed just for being one. The comparison is on the hostname only: the port and scheme are ignored, so a host declared for one endpoint admits every port on it (an audit sink on another port of the gateway's host is allowed), and PiShip does not check that a host is a private address (a public address listed in `allowHosts` is honored). `privateOnly` is a hostname allowlist, not a network boundary.
- Redirects are not followed.

The proxy, CA, and `privateOnly` policy is also applied to the Pi process's default HTTP dispatcher, so Pi's provider requests and extensions' in-process `fetch` calls to undeclared hosts fail too. It does not cover raw sockets or other HTTP clients; it is not an egress firewall. Child processes are not bound by it either: they get the approved network environment below, and only the OS sandbox's `deny` or `allow` network mode limits what they can reach.

Pi's interactive `/bug` command sends a bug report to the Pi developers' report service through that same default dispatcher. The report holds the environment, the model and provider names, the failed turns with their error text, Pi's crash records, and, when the user chooses to include it, the session transcript (`session.jsonl`), which can hold private project content. PiShip cannot turn the command off through Pi's public extension API. Under private-only the upload fails with `NETWORK_DENIED` unless the report service's host is in `allowHosts`, and every managed launch runs private-only. A distribution that runs without private-only (a personal one by default) lets the upload through. This is a question of data governance, not a leaked secret: the transcript and the crash records hold the redacted text described under [Secrets](#secrets). An organization whose transcripts must stay inside it turns `network.privateOnly` on and does not list that host, or blocks the host at its own egress proxy.

### Child process network environment

In a managed distribution, a command the agent runs through the `bash` tool receives the network environment the policy approves and no other. A personal distribution is not restricted: its commands keep the proxy and CA variables of the shell that started it, as before. PiShip derives the approved environment from `network` and the launch environment:

| Variable | A child receives it when |
| --- | --- |
| `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, and their lowercase forms | `network.proxy.inheritEnvironment` is true, with the value PiShip's own clients use. A proxy URL that embeds credentials, is not an `http` or `https` URL, or looks like a credential is withheld, so a child never receives a proxy credential; a child that needs the proxy needs one that takes no credential in its URL |
| `NODE_EXTRA_CA_CERTS` | exactly one `network.tls.additionalCA` bundle is declared. It adds to the default roots; several bundles cannot be expressed as one file and are withheld |
| any other proxy, CA, or TLS-verification variable: `ALL_PROXY`, `FTP_PROXY`, `SOCKS_PROXY`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`, `CURL_HOME`, `WGETRC`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `PIP_PROXY`, `PIP_TRUSTED_HOST`, `PYTHONHTTPSVERIFY`, `GIT_SSL_*`, `GIT_PROXY_COMMAND`, the `GIT_CONFIG_*` family (which can set `http.sslVerify`), the proxy, CA, and strict-SSL settings of npm and yarn (`npm_config_https_proxy`, `npm_config_cafile`, `npm_config_strict_ssl`, and similar), `CARGO_HTTP_PROXY`, `CARGO_HTTP_CAINFO`, `DENO_CERT`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `NODE_TLS_REJECT_UNAUTHORIZED`, and `NODE_OPTIONS` when it holds `--use-openssl-ca`, `--use-system-ca`, `--use-bundled-ca`, `--openssl-*`, `--tls-*`, or `--insecure-http-parser` | never: it is dropped, so a child cannot be told to skip verification or to use a different set of trust roots than the policy declares. This is a list of names, not a scan of values: a credential embedded in the value of some other variable is not detected |

How each kind of child gets it:

- **No enforced sandbox.** The command keeps its environment as before (with credential-looking names already removed in managed mode); only the network variables above are replaced by the approved ones. A user's own `!` command carries no environment from Pi and keeps the process environment. A same-user process can also read the environment the launcher was started with (`/proc/<pid>/environ` on Linux, `ps -E` on macOS), which removing a variable from the running process does not change: only a sandbox with its own process namespace keeps a command from reading it.
- **Enforced local sandbox that allows the network** (`sandbox.network.mode: allow`). Any network variable named in `sandbox.environment.allow` is dropped, and the approved variables are added to the other allowlisted ones. With `deny` there is no network to configure: none are added, and a network variable in the allowlist is dropped too.
- **Remote sandbox backend** (`isolation: remote`, such as E2B and Kubernetes). Never: the proxy address and the CA file name this host, and are meaningless in another one. A network variable in `sandbox.environment.allow` is dropped for a remote backend as well.
- **MCP stdio servers** keep receiving only their declared environment, as before; a variable a server lists in `env.allow` is passed as it is.
- A personal distribution, and a distribution with no network policy (`piship/v1alpha1`), is unchanged.

This is environment hygiene, not enforcement: a child can ignore or unset the variables. The launcher's own process keeps a proxy URL that embeds credentials, because PiShip's clients need it, so any process that inherits the whole environment, such as a user's `!` command, can read it.

## Governance

A `piship/v1alpha3` or later launch opens a governance session before Pi starts (see [architecture](architecture.md#governed-launch-flow)). Every mandatory control that cannot be established fails the launch; nothing silently falls back to an ungoverned run. Every decision names its enforcement plane:

| Plane | Meaning | Actions |
| --- | --- | --- |
| `control-plane` | PiShip decides before the action runs, inside the Pi process | Model use, resource and extension loading, MCP server start and tool calls, tool calls; file access through the governed `read`, `write`, and `edit` tools and shell command gating when no sandbox is enforced |
| `sandbox` | An enforced sandbox backend also contains the action: the OS sandbox proven by a live probe, or a remote or custom backend whose capabilities PiShip checked (the report says `live-probe` or `backend-attested`) | `shell.execute` when the sandbox is enforced; `filesystem.*` only when the backend enforces the path policy (`filesystem-*` planes, as the native sandbox does; a remote backend's `host-filesystem-isolation` does not count); `network.connect` when `network-deny` is enforced |
| `audit-only` | Observed and recorded, not prevented | None against Pi 1.0.x |

A plane is reported as a status: `control-plane`, `sandbox`, and `gateway` are `enforced`; `audit-only` is `audit-only`; an action no plane covers is `unsupported`, neither prevented nor recorded, and never emitted in audit. The runtime seam table (`RUNTIME_SEAMS` in `@piship/policy`) records which actions Pi exposes a seam for; Pi has no capability discovery API, so it is static data proven by the compatibility tests. `policy explain` prints the status and plane for any action and resource. There is no runtime seam for `web.request`, `browser.execute`, `agent.invoke`, or `memory.*`, nor for `network.connect` without an enforced deny sandbox; `policy explain` and `doctor` report them as `unsupported`.

A rule whose `action` names an unsupported action exactly, with effect `deny` or `ask`, is `POLICY_UNENFORCEABLE`: in a managed distribution `validate` fails and the release `policy` gate refuses it, unless `policy.acknowledgeUnenforced` lists it as `"<action>:<resource>"`; `doctor` shows each such rule, acknowledged or not. A personal distribution gets a warning. `policy.default`, `*`, and `<prefix>.*` rules never count. Containment is taken from the manifest: a required sandbox contains the filesystem and shell planes, and the network plane only when `sandbox.network.mode` is `deny`. A non-builtin capability provider whose capability is effective is also decided as `provider.load` (the provider ID) and `extension.load` (`<class>:<path>`) before its extension loads; a denial skips the provider, records `provider.denied`, and makes the capability not effective.

### Policy precedence

For each request the policy engine takes the first matching rule of each layer and applies the strictest effect (`deny` over `ask` over `allow`):

1. Distribution Enforced (`policy.enforced`).
2. Team and project rules (`policy.adapter` and the project's `.piship/policy.json`): narrowing only; their `allow` rules are ignored and reported. Team rules and project rules are matched separately, each taking its own first match, so a team `ask` never hides a project `deny` (and the other way round).
3. Distribution Defaults (`policy.defaults`), or
4. in personal mode, a matching User rule from `<state>/config/policy.json`, which takes the default's place. In managed mode user rules are a narrowing-only layer like step 2: their `allow` rules are ignored and reported (`doctor`, `policy explain`, and a `policy.violation` audit event), and their `ask` and `deny` rules join the strictest-effect comparison.

When nothing matches, `policy.default` applies. A personal user may relax a default but never an enforced rule; a managed user, a team, or a project file can never widen anything. `ask` needs an approval channel: before Pi starts, a y/N prompt on an interactive terminal; during a session, Pi's confirmation dialog. Launches without an interactive terminal or UI (`--smoke`, `--smoke-model`, or standard input that is not a TTY) have no channel, so `ask` resolves to deny. Denials name the policy, rule, and reason.

One exception to "a managed user can never widen anything" is opt-in per distribution: with `policy.userAuto: allowed` (v1alpha5, managed), a user may switch on [auto mode](manifest.md#user-auto-mode), and while it is on an `ask` decided by `policy.defaults` or `policy.default` is approved without a prompt, interactive or headless. The strictest effect is still computed first, so auto mode only turns a final `ask` into an approval: a `deny` from any layer stays a denial, and an `ask` from `policy.enforced`, a team or project rule, or the user's own rules keeps its prompt. It does not relax project trust prompts, the built-in denials (the state directory, git control files), Plan mode, the sandbox, model and MCP allowlists, or audit. What it gives up is the person's per-action confirmation for actions the administrator left to `ask`: an agent following injected instructions can then do whatever those defaults leave at `ask` without anyone confirming it. That is why it is off unless the administrator allows it, why every approval is audited as `policy.auto_approved` and every switch as `policy.auto_enabled` or `policy.auto_disabled`, and why an administrator who wants a prompt kept for specific actions puts that `ask` in `policy.enforced`. The switch is stored in the distribution state, which tools never read or write, bound to the signed-in principal, and applies only while the running release allows it. Switching on is audited before it applies, both with `<command> auto on` and in a session, where `/auto on` delivers the event to the sinks before it switches; a required sink that does not take it leaves auto mode off. Switching off is never blocked by audit: it applies first and is recorded best effort. Someone who can write the state directory can still switch auto mode on by editing `config/auto.json` without either command; a session that starts with it on therefore records `policy.auto_enabled` with `detail.source: state`, so the first session that uses it is audited.

### Tools, shell, and Plan mode

Governed sessions start Pi without its built-in tools and supply governed `read`, `write`, `edit`, and `bash` tools built from Pi's public tool definitions, so Pi's rendering and diff behavior stay upstream. Every tool call is decided as `tool.execute` in Pi's `tool_call` hook. If that decision fails (for example the audit buffer is full), the call is blocked with a sanitized reason and recorded as `tool.denied`; it never runs.

- `read`, `write`, and `edit` run in the Pi process. Each file access is decided on both the path as given and its symlink-resolved target, and the stricter decision wins. The file is then opened at the decided target without following a final symlink, and reads and writes go through that open file only. On Linux the path of the opened file is decided again when it differs; elsewhere the opened file must be the same file (device and inode) as the decided target, or the access fails (`piship.path-changed`), so a symlink or directory swapped in after the decision is not followed. A write that creates a file may leave it empty at the swapped location before this check refuses it. When the sandbox is enforced, its profile is also applied to these in-process tools: read-denied paths are refused and writes must land in a write-allowed path.
- `read` and `edit` load at most 16 MiB of a file. Pi's read tool takes the whole file into memory before it truncates its output, so a larger file (an image included) is refused with an error that names its size and points to `bash` (`sed -n`, `head -c`, `grep -n`) to work on part of it, including an `offset` read into such a file. The size is taken from the opened file, and the read stops one byte past the limit, so a file that grows while it is read is refused too. A named pipe planted in a project is refused at once: files are opened without waiting for a writer, so it cannot hold up the process's file I/O.
- Whatever the policy and sandbox level, these tools never read or write the distribution state directory (`piship.state`), and never write the project's git control files: `.git`, `.git/config`, the `config`, `config.worktree`, and `commondir` of the git directory (and the shared `config` a worktree points to, and the files those configs include), or anything under the `hooks/`, `info/`, `modules/` (submodule git directories), and `worktrees/` (linked-worktree metadata) directories of the git directory and its common directory, or under the directory `core.hooksPath` names in those configs and in the system, global, and environment config git reads (`piship.project.git-config`). These files decide the project's origin, and so its trust class, and what git runs outside any sandbox. An enforced sandbox keeps the same files and trees read-only for shell commands and MCP stdio servers even inside a writable workspace. Without an enforced sandbox, shell commands are not covered by this rule.
- `bash` commands and user `!` commands are decided as `shell.execute`, then run inside the OS sandbox when it is enforced. Without an enforced sandbox they run as Pi would run them, and the decision covers only the command text. A command-text rule is pattern matching, not containment: without a sandbox a permitted command can still read or write any file the user can. An `allow` or `ask` rule such as `git *` is a prefix hint: it does not match a command containing a shell metacharacter (`;`, `&`, `|`, `$`, `` ` ``, `<`, `>`, `(`, `)`, a line break, or cmd.exe's `^` and `%`) unless the rule's pattern spells out that character, so `git status; rm -rf ~` or `git $(id)` falls through to the next rule or `policy.default`. A bare `**` pattern means every command. `deny` rules match regardless.
- A `bash` or `!` command may produce at most 64 MiB of output, inside or outside the sandbox. At the limit PiShip passes one notice (`output exceeded the 64 MiB shell output limit`), stops the command, and kills its process tree; the tool reports no exit code.
- The agent's `bash` tool keeps Pi's definition, display tail, live updates, and result text, but PiShip runs its execute, so the complete output of a truncated command is owned by the session. Like Pi 1.0's, its result also carries `structuredContent`, which codemode scripts receive: `output` (up to 1 MiB, and when the output is longer its first and last 512 KiB), `truncated`, `full_output_path` (only when the output was truncated and saved, so valid only until the session closes), `exit_code`, and `wall_time_seconds`. A non-zero exit returns an `isError: true` result with that content instead of throwing, as Pi 1.0 does. It is written to a private directory, `piship-out-*` in the OS temp directory (mode 0700, files 0600), created on first use and removed with its contents when the session closes. Each file holds at most the 64 MiB limit plus the notice, and never uses the last 256 MiB of free temp space: past that it stops growing and the footer says `Full output (first <size>)`. A write error on that file, a full temp filesystem (`ENOSPC`) included, stops only the copy: the command runs on, the result keeps its tail, the footer says `Full output not saved: <code>` instead of a path, and the session continues. A session that crashed before closing leaves its directory; the next governed session removes it when it is provably abandoned (owned by the same user, mode 0700, and recording a process on this host that no longer runs). That sweep runs on macOS and Linux, not Windows.
- A user's `!` command still runs through Pi, which keeps its streaming and Esc cancel, and Pi still copies its complete output to a `pi-bash-<id>.log` file in the OS temp directory. PiShip removes the files Pi recorded for the session's `!` commands when the session closes (only a regular file with that name, directly in the OS temp directory, owned by the same user), and lowers the command's output budget to the free temp space minus 256 MiB (never below 32 KiB, under which Pi writes no file), stopping the command with a notice at that point. Two gaps remain until Pi exposes the file: a temp filesystem that fills anyway (another writer, or a race with the free-space check) while Pi writes it is not contained, because Pi's write stream has no error handler; and a file is not removed when the process crashes, or when a `!` command ran while the agent was streaming and Pi had not yet recorded it at quit. Closing them needs an upstream Pi option, such as an `output: { dir, maxPersistBytes }` setting in `BashToolOptions` and the `!` executor's options, and an `error` listener in the output accumulator's temp-file stream.
- Plan mode (the builtin `workflow` capability) allows only the `read` and `ask_user` tools. Every other tool (`write`, `edit`, `bash`, MCP tools, and extension-registered tools) is blocked, as are all file writes and user `!` commands, until the user switches with `/build`. Plan mode is a control-plane restriction on tool calls; it does not restrict extension code that runs outside a tool call.
- Pi 0.99 and later add the built-in extensions `builtin:mcp`, `builtin:codemode`, `builtin:tool-search`, and `builtin:llama`. The first three would run tools outside the paths above, but a PiShip session does not load any of them: only Pi's CLI adds them, and PiShip builds the session through the SDK with `noExtensions: true` and its own extension factories. A compatibility test asserts that no `builtin:*` extension loads. A tool that an extension runs through `ctx.executeTool` still emits `tool_call`, which PiShip's policy hook decides. The only MCP servers in a session are the declared ones, started by PiShip ([MCP](#mcp)).
- Exposure (piship/v1alpha6 `runtime.tools.exposure` and each MCP server's `exposure` and `tools`) decides what the model can see; policy still decides every call. A `hidden` tool, a tool the policy denies at session start, and Pi's base tools PiShip does not govern (`grep`, `find`, `ls`, `powershell`) are excluded from the session, so neither the model, a Codemode script, `tool_search`, nor an extension can reach them. An extension tool declared wider than the manifest allows fails the launch (`CONFIG_INVALID`); in managed mode a tool registered after launch is refused (rule `piship.exposure.unresolved`), and Codemode is refused (`POLICY_DENIED`) while a tool it can reach is decided only by the policy default. When enabled, PiShip loads Pi's Codemode (without the script `models` global) and tool search itself.
- Every tool call is recorded as `tool.request` when it starts, with `detail.source` (`top-level`, `codemode`, or `nested` for another extension tool's `ctx.executeTool`), `detail.parent` (the calling tool's call ID), and `detail.exposure`. A call Pi refuses before PiShip's policy hook (an unknown or excluded tool, or arguments that do not validate) is recorded as `tool.denied` with rule `piship.pre-policy` and `detail.error` `not-found` or `invalid-arguments`, never the error text. Approval prompts of concurrent calls open one at a time. The arguments and error text of nested calls that Pi keeps with a tool result are redacted before the session file is written.
- The selected model is decided as `model.select` before the session starts; models the policy denies, or that need approval not yet given, are not offered for switching.
- The physical model that receives a request is decided as `model.dispatch`; without a `model.dispatch` rule for it, `model.select` decides, so a route cannot reach a model a v0.8 `model.use` rule denies. A virtual model (piship/v1alpha6 `models.catalog.<id>.virtual`) is registered only from its declared router while extensions load, at launch and on `/reload`; any other registration fails the launch, and one made later is refused (`POLICY_DENIED`). Every request it routes, from the agent loop, a direct extension call, or a compaction or summary, passes PiShip's model runtime after Pi routes it and before any request is sent: a target outside the declared `routes`, or one `model.dispatch` or the credential's entitlement does not allow, is refused (`MODEL_DENIED`), and each routed request is recorded as `model.dispatch` with `detail.selected`, `detail.dispatched`, and `detail.router`. Classifier and image requests are checked the same way and return an error result instead of failing, as Pi's API does.

### Project trust

PiShip classifies the working project as company, external, or unknown from its git origin remote or path and decides each project item by its trust dimension ([manifest](manifest.md#policy)). Pi's own project discovery stays disabled; only admitted items are handed to Pi's loader. Every candidate is symlink-resolved: a target outside the project root is evaluated as unknown origin, and executable items (skills, agents, hooks, extensions, MCP, providers) that leave the root are denied. A candidate directory is walked (following links that stay inside the root, at most 50,000 entries and 32 levels) and is treated the same way when any link inside it leaves the root, or when it is too large or deep to check; `doctor` names the offending entry or limit. The walk is a check at launch, not a lock: a link created inside the directory after the check is not detected. Instruction `@path` imports must resolve inside the root and are followed at most five levels. A dangling link is reported as denied. This release never loads project agents, hooks (`.pi/settings.json`), or capability providers. Project `.mcp.json` servers are used only in personal `explicit` MCP mode with `mcp.project: allow`, never receive the runtime credential, and cannot replace a declared server.

The origin remote is read from the project's own git configuration, which anyone who can write the checkout controls. A `remote` matcher alone is a claim, not proof: a clone of any repository can declare a company remote. Managed distributions should combine `remote` with `path` in one matcher (both must match), so only checkouts under a managed location count as company projects. The governed file tools refuse to rewrite these git files; an enforced sandbox's write allowlist limits shell commands.

### Certified resources and providers

A certified resource's tree digest is checked against its reviewed `integrity` at lock time and recomputed from the installed payload at launch; a mismatch fails the launch with `INTEGRITY_FAILED`. A certified resource reviewed for another Pi version or platform is not loaded. Certified and non-builtin provider trees with npm install-time scripts or a `binding.gyp` (an implicit `node-gyp rebuild`) are rejected at lock time. Non-builtin capability providers load only when their trust class is allowed and their files match the lock. `user` resources and providers are denied by default in managed mode. Certification is a digest match against reviewed evidence, not a signature.

### Pi packages

PiShip, not Pi, resolves and vendors Pi packages ([manifest](manifest.md#pi-packages-v1alpha6)), and no package code runs while it does. npm runs only with `--ignore-scripts` and a `--git` that refuses to run. Before npm is called, a git or local package's own `dependencies` and `optionalDependencies`, and an npm package's published ones, must be registry versions or semver ranges: npm fetches a git dependency by cloning it and running its `prepare` under that repository's own npm configuration despite `--ignore-scripts`, so a git dependency at that level is refused rather than resolved. A git or local package containing a symlink or a `node_modules` directory is refused before its `package.json` is read, and an installed directory under `node_modules` that the package lockfile does not list fails the lock or build, so no module loads from outside the locked closure. Git content is archived as committed: the repository's `.gitattributes` and the build environment's `core.autocrlf` cannot convert line endings, run filters, or expand `export-subst` or `ident`. The install-script review (including a git or local package root's own scripts or `binding.gyp`) applies at lock and build whether or not the manifest has `lifecycle.release`. A certified package's evidence must match its locked tree digest (and, for npm, its version) at lock and at launch, and its files are not loaded on a Pi version or platform the evidence does not list.

Limits: a git spec deeper in the closure (a dependency's own dependency) becomes visible only when npm resolves it. The refusing `--git` stops a clone, and the lockfile check then refuses the entry, but npm can fetch a hosted-git spec such as `github:owner/repo` as an https tarball without git and prepare it before that check runs. Lock only packages whose closures you have reviewed, in an environment holding no credential the lock does not need. At launch PiShip checks the sha256 of the inventory's entry files only (the extension, skill, prompt, and theme files Pi loads); the modules they import, the package's other files and its vendored `node_modules`, are bound by the tree digest and lockfile at build and are not rechecked per package at launch.

### MCP

MCP servers are declared in the manifest and started by PiShip, not by an extension.

- Each server start is authorized as `mcp.server.start` before anything is spawned or contacted. A denied or failing server is reported; a `required` one fails the launch.
- `initialize` must negotiate a supported protocol version (`2025-06-18`, `2025-03-26`, or `2024-11-05`), and `expectedServerName` must match when declared.
- A tool is offered to the model only when the manifest's `tools` lists admit it and the policy does not always deny `<server>:<tool>`. A denied tool is never offered, and a call to it never reaches the server.
- Every call is authorized again when it happens (manifest lists, then policy with approval for `ask`); an authorization error is a denial. Results are redacted and capped at 256 KiB.
- stdio servers run in the project root with only their allowlisted and fixed environment variables; credential-looking names are stripped. When the sandbox is enforced they run inside it, with the same filesystem, network, and environment profile as tool subprocesses. A backend that cannot contain local processes (the e2b-compatible and Kubernetes backends, and remote custom adapters) refuses them with `SANDBOX_UNAVAILABLE`, so they do not start.
- Streamable HTTP servers use the managed fetch, do not follow redirects, and receive the runtime credential as a bearer only with `credential: runtime`. The runtime credential is issued for the inference gateway, so it is sent only to the origin (scheme, host, and port) of `inference.baseUrl`; a `credential: runtime` server on any other origin fails to start (`MCP_UNHEALTHY`) before the credential is read.

### Audit

Audit is metadata first. Events (`piship-audit/v1`) record the event type, time, principal (issuer and subject, never a token; see [user switching](#user-switching)), session, distribution, and, where relevant, the resource, decision, policy, rule, and enforcement plane. File access is recorded as a path class (`workspace`, `tmp`, `home`, or `other`), shell commands by tool and byte length, and MCP calls by `<server>:<tool>`, outcome, and duration. Prompt, response, command, and source content are recorded only for classes the distribution opts in to under `audit.capture`, and are redacted. The file sink writes `<state>/logs/audit.jsonl` (0600 in a 0700 directory) and rotates it by size: at 10 MiB it becomes `audit.jsonl.1`, and five rotated files are kept, so the oldest local events are deleted after about 60 MiB. A piship/v1alpha6 `data.audit.retention` is a minimum that rotation honors: a rotated file younger than it is kept past the fifth (`audit.jsonl.6` and on), so local audit is then bounded by what is written within the minimum, and the retention sweep at launch and logout deletes rotated files once they are older. The bound is approximate: while another process is rotating, a writer keeps appending past 10 MiB and rotates on a later write. Rotation only renames files, so a process still appending keeps writing into the renamed file and no retained line is lost; ship events to an HTTP sink when they must be kept longer. HTTP sinks POST `piship-audit-batch/v1` batches through the managed fetch; the [integration contract](enterprise-integration.md#audit-collector-piship-audit-batchv1) has the schema. Every event carries a random `id` that a resent batch keeps, so a collector can de-duplicate. Update and rollback activations and refusals are recorded as `runtime.update` and `runtime.rollback` events with versions, channel, key ID, and error code. Where the distribution allows [auto mode](manifest.md#user-auto-mode), each `ask` it approves is recorded as `policy.auto_approved` with the action's own metadata, and each switch as `policy.auto_enabled` or `policy.auto_disabled`. Local counters for denials, startup failures, sandbox level, MCP health, update, check, and rollback outcomes, identity and credential durations, gateway reachability, live catalog fetches, resource and provider load failures, and the running versions are kept in `<state>/logs/metrics.json`; they hold only numbers, times, error codes, and identifiers, never a URL, token, subject, or content.

The retention sweep (a piship/v1alpha6 `data` section) runs at launch and logout and deletes only Pi session files, rotated audit files, and cache files older than their class's declared retention. A session file is deleted only under the sweep's own owner record at launch, so a launch resuming it at the same time keeps it, and rotated audit files only while the sweep holds the audit rotation lock. The declared retention is applied as it is: there is no user retention preference yet, so the bounds the manifest describes (audit a minimum a user may lengthen, the other classes maximums a user may shorten) have no user value to combine with, and a user cannot shorten how long sessions or cache are kept on their machine.

| Sink | Condition | Result |
| --- | --- | --- |
| Required | Cannot be opened (file) or reached (empty-batch probe, HTTP) at launch | Launch fails with `AUDIT_UNAVAILABLE` |
| Required | Delivery fails | Events stay buffered and are retried; governed actions continue |
| Required | Buffer full while delivery keeps failing | New events are dropped and counted; governed actions fail closed with `AUDIT_UNAVAILABLE` until the buffer drains. A model request is a governed action too: it is refused before anything is sent to the gateway, because a prompt can carry workspace content |
| Optional | Cannot be opened, delivery fails, or buffer full | Sink is degraded; affected batches or events are dropped and counted; governed actions continue |
| Optional | Close deadline passes | In-flight delivery is aborted; the batch counts as dropped |
| Required | Events still undelivered when the session or command ends, or dropped earlier | Delivery is retried until the close deadline (5 s). Whatever the sink has not taken is reported, never discarded silently, whenever the session ends through its normal shutdown (Ctrl+D, `/quit`, SIGTERM, SIGHUP, or the end of a command): the session ends with `AUDIT_UNAVAILABLE` (the command exits non-zero). A crash of Pi itself (an uncaught exception, or a lost terminal) skips that shutdown, and the events the sink had not taken are then only in the local file sink, if one is configured, and a launch that is already failing keeps its own error and counts `AUDIT_UNAVAILABLE` among the startup failures `doctor` shows |

A required sink is the whole policy for mandatory audit: events are buffered up to `audit.buffer.maxEvents` while the sink is down, and governed actions fail closed once that buffer is full. There is no separate setting. `doctor` reports each sink's state and delivered, pending, and dropped counts, with an HTTP sink shown by host only. `doctor` gets those counts by opening a governed session as a launch does, so its `session.start`, `policy.loaded`, decision, and `session.end` events reach the sinks under the signed-in principal ([doctor report](manifest.md#doctor-report)). `login`, `logout`, `update`, and `rollback` record their events after the operation, so signing out still works while a company sink is down. With only optional sinks that is best effort (a failure is a warning). With a required sink that cannot be reached or does not take every event, the command fails with `AUDIT_UNAVAILABLE` after the operation, which is not undone; a refused `update` or `rollback` keeps its own error and prints the audit failure.

### Sandbox

PiShip owns policy and governance. The sandbox backend owns execution isolation. The sandbox is activated only when `sandbox.required: true`, through the backend `sandbox.provider` names: the native OS sandbox (the default and the only one described in the rest of this section), a company `custom` adapter, an `e2b-compatible` service such as E2B or CubeSandbox, or `kubernetes-agent-sandbox`. Whatever the backend, PiShip decides each command first, sends only the approved environment (never credential-looking names, and for remote backends never host-bound variables such as `PATH` or `HOME`), uploads no files, sends a credential only as `sandbox.credential` or the adapter module declares it and only to the origins that credential may reach (the inference gateway's for `runtime`, the ones a `stored` credential was stored for), and owns every timeout and cancellation. A backend whose declared capabilities miss a plane the policy needs, that is unavailable, or that fails its check fails the launch with `SANDBOX_UNAVAILABLE`. A report never claims more than the backend enforces: the E2B and Kubernetes backends report `host-filesystem-isolation` (the sandbox cannot reach this host's files), never the `filesystem-*` planes, because they do not apply `sandbox.filesystem` path rules inside the remote sandbox; those rules keep governing PiShip's local file tools. `credential: runtime` reuses the inference runtime credential under its origin rule; `credential: stored` sends a sandbox credential bound to the user and the endpoint origins ([sandbox credentials](sandbox.md#credentials)). For backends PiShip cannot live-probe, isolation is attested by the backend and checked from outside; see [sandbox backends](sandbox.md) for the contract, what each backend receives, and its limits. Their network denial is verified only when the backend declares a network probe that PiShip then reaches from a temporary allow-mode sandbox of the same backend and cannot reach from the session's sandbox; a probe reachable from the denied sandbox fails closed, and in every other case (no probe, as for the E2B backend, a deny-only backend, or a probe the allow-mode sandbox cannot reach) network denial is attested by the backend and reported so in `doctor` ([network denial](sandbox.md#network-denial)).

A remote backend declares whether its sandbox sees the files PiShip's file tools edit: `shared` (a mount), `synchronized` (a backend-owned two-way sync), or `snapshot` (the default, and what the E2B and Kubernetes backends declare). Only `shared` and `synchronized` count as a complete coding-agent workspace, and only after PiShip verified them. A shared or synchronized backend reaches this host's files through the workspace, so it may not claim `host-filesystem-isolation`; it must claim `workspace-confinement` (attested) and `git-control-protection`. Just before the first command that reaches the sandbox, never at activation and never from `doctor`, PiShip writes a random token in a directory it owns (inside the git directory, or a backend-declared directory, which in the working tree is used only for company-origin projects) and has the sandbox read it and answer with another, which shows both directions or lowers the reported mode to what the evidence supports (a warning). The same command tries, without changing anything, to append to the protected git control files and to create a file in the protected git directories; if any attempt succeeds, or the check cannot run, the backend is retired and the command fails with `SANDBOX_UNAVAILABLE`, because a hook written from the sandbox would run outside it with the user's next git command. Renaming those paths is not tried remotely and stays attested. The check is repeated after 30 minutes or when the backend reports a new environment ([workspace](sandbox.md#workspace)).

For the native backend, PiShip selects the platform adapter and runs a live probe inside it: a child must fail to write outside the write allowlist, fail to read denied paths, see only allowed environment variables, and, in `deny` mode, fail to reach an external address and a host loopback listener. The probe also checks `git-control-protection`: a child must fail to write a protected file, create a file in a protected directory, or rename the directory that holds a protected file. That check is reported, not yet required, until it has passed on Linux and macOS CI: a local backend that fails it activates without the plane and with a warning. Only planes the probe proved are reported as enforced. If the adapter is missing or the probe fails, the launch fails with `SANDBOX_UNAVAILABLE`; there is no unsandboxed fallback. The distribution state directory is always read-denied; the installed payload stays readable; `tmp` is a private per-session directory.

### Limits

- The Pi process and in-process extensions are not contained. Company, certified, and user extension code runs with the user's privileges, can read files, spawn processes, and use the network directly, and can bypass Pi's `tool_call` hook and PiShip's governed tools. Trust classes and certification decide what loads; they do not sandbox it.
- Model governance covers every path Pi itself dispatches through, all of which pass the model runtime PiShip builds. Extension code can still call a model provider without it, through Pi's model library or its own requests, with any credential it can read. In managed mode the provider variables of the environment are removed before Pi starts ([managed runtime isolation](#managed-runtime-isolation)), but PiShip does not clear the provider keys Pi's model library knows from the process environment in personal mode, nor any credential an extension reads from elsewhere; `model.dispatch` does not bound such a call. Only `extension.load` and trust decide whether that code runs, and in managed mode the gateway's credential scope still applies to the managed credential.
- Pi's built-in `/share` command uploads the session file as a GitHub gist through the user's own `gh` CLI. `gh` is a child process, outside PiShip's in-process network policy, so `network.privateOnly` does not apply to it, and no public Pi switch turns the command off. A session file holds the user's prompts, the model's output, and tool results ([Secrets](#secrets)), so `/share` is a path by which a session can leave the machine, in managed mode too. An organization whose sessions must stay inside it controls `gh` and github.com at its own endpoint and egress controls; the [production validation protocol](production-validation.md#share-and-public-session-export) makes that a requirement before the first step.
- Session export (`session.export`, [manifest](manifest.md#session-export)) is enforced only where Pi has a seam. `public` is `unsupported`: PiShip closes `/share`'s Radius path (no `radius` credential is issued, and a gateway distribution with the ID `radius` is refused), but not its gist fallback above. `local` (`/export`) is `unsupported` by construction, since the user can read session files under `<state>/sessions`. `support` is `enforced` only where Pi runs offline (`PI_OFFLINE=1`, every managed launch): in personal mode Pi's `/bug` upload is open, so it is `unsupported` there. The lock's `sessionExportStatus` and `doctor` always report all three, whatever the manifest declares.
- Pi exposes no event when the active tool set changes and none when `tool_search` discovers or activates a tool. PiShip keeps hidden and denied tools out of the session (`excludeTools`) and still decides every call at `tool_call`, so a deferred tool is never executed ungoverned; what tool search can list is decided by what PiShip registers.
- The sandbox network contract is `deny` or `allow` only. There are no hostname allowlists at the OS boundary. In `allow` mode, host loopback services and abstract Unix sockets are reachable.
- A remote backend's verified network denial shows that one controlled target is reachable with the network allowed and blocked with it denied, not that every destination is blocked. Attested network denial is the backend's word.
- Filesystem denies are path based. An existing hard link to a denied file in a readable location stays readable.
- There is no seccomp or system-call filtering.
- The workspace check refutes a shared or synchronized claim but cannot prove a mount, and it holds at one point in time: a command that runs in a replaced remote environment before the next check is not checked afterwards. A remote workspace's `sandbox.filesystem` read denies are not enforced inside the sandbox: a read-denied path inside a shared or synchronized workspace is readable by remote commands unless the backend also claims both `filesystem-*` planes. `workspace-confinement` is attested by the backend.
- Git control-file protection covers the project's own git directory and common directory, the submodule git directories and linked-worktree metadata below them, the files those configs include, and the `core.hooksPath` directory named in those configs or in the config git reads besides the repository: the system config (`GIT_CONFIG_SYSTEM`, else `/etc/gitconfig` and the other places a git installation keeps it: Homebrew's, Xcode's, and the Command Line Tools'; a git built with another prefix needs `GIT_CONFIG_SYSTEM` to name its file; none with `GIT_CONFIG_NOSYSTEM`), the global config (`GIT_CONFIG_GLOBAL`, or `~/.gitconfig` and the XDG file), and the `GIT_CONFIG_COUNT` and `GIT_CONFIG_PARAMETERS` (what `git -c` exports) settings of PiShip's own environment; no other file is read. A config that lists more than 64 includes, hooks paths, or settings, a file over 1 MiB, or a `GIT_CONFIG_PARAMETERS` that is not in the format git writes, is followed only in part, and `doctor` reports git control as not verified. The system, global, and environment config, and what they include, are kept read-only for sandboxed commands wherever they lie, which matters when the sandbox may write the directory that holds one (a distribution that allows `~`); PiShip's file tools do not refuse them, so the edit tool can still change the user's `~/.gitconfig`. On Linux (bubblewrap) a control file that does not exist yet (such as `commondir`, `config.worktree`, or an include nobody has created) cannot be guarded, since a mount over a missing file would leave an empty file in the repository and PiShip creates no placeholder files: `doctor` reports git control as not verified, and the sandbox warning names the files, for every regular repository. The sandbox still runs. On macOS (Seatbelt) a missing file is denied and stays verified when the directory above it cannot be swapped (the workspace root, another writable root, or a directory that holds an existing protected path such as `.git`); one in any other directory (an include under a directory of the working tree, a global config whose directory does not exist) is not verified there either, since a command can build the directory elsewhere and rename it into place. The scripts a `core.hooksPath` directory in the working tree calls (husky's `.husky/pre-commit`) are ordinary workspace files, so `doctor` reports git control as not verified there too. So does a protected path reached through a symbolic link in a directory the sandbox may write (an include that is a link, a linked `.git/hooks`, a dotfile-managed `~/.gitconfig` when `~` is writable): protection covers what the link points to, and no backend can hold the link itself in place.
- On Windows, the start of a child that PiShip spawns itself (such as an MCP stdio server) has three known limits, not fixed in v0.7. A child that writes the launcher's startup-failure marker (`PISHIP_WINDOWS_JOB_ERROR`) to its own stderr has that output dropped and its exit reported as a startup failure, because the marker is read from stderr. The Job Object helper is compiled from C# at every child start, which adds startup time to each one. And the request that carries the child's file, arguments, working directory, and approved environment travels base64-encoded in one environment variable of the launcher (`PISHIP_JOB_REQUEST`), so a request larger than Windows allows in one variable (documented as 32,767 characters; not measured here) cannot start the child.
- Machine administrators, and anyone who can modify the installed payload, state, or inventory, can defeat these controls. Governance does not protect against them or against a malicious extension a distribution chose to load.

## Releases and updates

The production lifecycle is described in the [release guide](release.md): the [owner workflow](release/owner-workflow.md), [artifact contract](release/artifact-contract.md), and [update lifecycle](release/update-lifecycle.md). Its trust model:

- **Consumer verification.** `verify-release` checks archive digests, `checksums.txt`, every payload file against the inventory, manifest and lock agreement, `release.json` against the payload, SBOM completeness, notices coverage, and the recorded scan and test results. It proves a release is complete and consistent, not who built it.
- **Update trust.** An installation keeps its current update root (keys with a root role and a channel role, each with a threshold) as installation state, started at a fresh install from the verified release's `updates.trust.bootstrap`. Before every update it fetches newer roots (`root/<N+1>.json`) one version at a time, accepts each only when signed to both the current and the new root-role threshold, and persists it; any fetch failure other than an authoritative 404 stops the update. Release activation, rollback, and release locks never change the installation's root, so a channel signer cannot widen its own authority, and a key a newer root removed stays refused after rollback. A damaged or missing trust state fails closed and is never rebuilt from a release lock.
- **Channel signing.** Channel metadata must carry signatures from the newest root's channel role, at least its threshold of distinct keys (`piship-signature/v1`, with an optional `signatures[]` whose top-level entry keeps v0.7 clients working). It must name its distribution and channel, not have expired, and not have a lower sequence than the client has already accepted, which blocks replay. Each archive is then checked against the SHA-256 and size in the signed entry before extraction, and its version, command, Pi version, and lock digest must match that entry. There is no unsigned or trust-on-first-use mode. Key custody, bootstrap, rotation, emergency revocation, lost-key recovery, and channel hosting are in [release trust root](release/trust-root.md) and the [key runbook](release/key-runbook.md).
- **Build provenance.** The `release-candidate` CI workflow runs only when a maintainer dispatches it, alone or through `Release qualification`, on the exact candidate commit. It builds each target twice on separate runners from fresh checkouts and fails unless `piship reproducibility` finds equal payloads. It creates GitHub artifact attestations (Sigstore keyless signatures bound to the GitHub Actions workflow identity and the ref the run was for) for the first build of each archive. A separate job verifies them with `gh attestation verify --repo --signer-workflow --source-ref`. The same job rejects a tampered archive, a wrong digest, and a modified payload file, `release.json`, or `checksums.txt`. A run dispatched on another branch is attested with that branch's ref (and runs from before v0.5, when the workflow also ran for pull requests, carry `refs/pull/<n>/merge`), so consumers verify with `--source-ref refs/heads/main` to accept only `main` builds ([Build provenance](release/artifact-contract.md#build-provenance)). This is independent of the owner's channel key: provenance says which workflow built an archive, and the channel signature says which releases the owner offers.
- **Update transport.** Update sources must be `https`, plain `http` on a loopback host, or a local directory. A distribution may opt in at build time with `updates.transport: http-allowed` to plain `http` on a private or internal host ([manifest](manifest.md#plain-http-update-channel-v1alpha5)); a public host is refused, and only the host name is judged, so an internal-looking name that DNS maps to a public address is the owner's to prevent. It needs `updates.trust.bootstrap`, and it changes nothing about verification: update integrity never came from the transport, because roots, channel metadata, and archives are checked against the installation's root, its thresholds, the sequence floor, expiry, and signed digests. A network attacker on the plain-HTTP path can therefore withhold or delay updates, which blocking an `https` host also achieves, but cannot forge, alter, or replay them. Releases carry no secrets. Requests use the managed fetch with the distribution's network policy (proxy, CA bundles, and `privateOnly` with its allowed hosts, plus the declared `updates.source` host), follow a redirect only within the source's origin (so never from `https` to plain HTTP), and archive names must be plain `.tar.gz` file names. When a runtime variable is not set in the shell that runs `update` or `rollback`, the policy comes from the manifest alone: the proxy setting, `privateOnly`, and `network.allowHosts` apply as at launch and the hosts of the unresolved endpoints are not added, so the policy is never wider than a launch's, and a `--from` URL on a host it does not allow fails with `NETWORK_DENIED`, and an HTTP audit sink on such a host is refused as it is at launch. A declared CA bundle is never left out: an unset variable in `network.tls.additionalCA` fails with `CONFIG_UNAVAILABLE` naming it, as at launch, before any request. Release content is signature-checked either way. Extraction refuses links, special files, unsafe or reserved names, and oversize archives.
- **Supply-chain gates.** `piship release` refuses locked packages from origins outside `release.sources`, locked packages without a recorded source or `sha512` integrity, unreviewed npm lifecycle scripts, an unsupported Pi pin, policy conflicts, missing certification evidence, and a required sandbox on a target without an adapter. It records an SPDX SBOM and third-party notices, and blocks on `npm audit` findings at or above `release.vulnerabilities.failOn` unless a reviewed exception has not yet expired. A registry signature gate runs `npm audit signatures` over the payload packages: an invalid signature or attestation fails the build, missing signatures are recorded, and a check that cannot run is recorded as `unavailable` rather than failing the build. These gates run only in `piship release`; `piship build`, `dev`, and `test` do not apply them.
- **Activation.** Payloads are immutable per version; the active release is switched by one atomic receipt rename after all verification, launch, and migration checks. Downgrades through `update` are refused; `rollback` only returns to the locally retained, re-verified release.
- **Credentials across versions.** Credentials are never part of a release, snapshot, or rollback. Update and rollback keep credential metadata only when the target can read its schema; otherwise they revoke it where supported, then delete every local secret reference (including orphaned and pending generations) and the metadata, so the target signs in or reacquires. A discarded credential marker is always cleared this way. Every deletion is confirmed by reading the reference back: a secret that cannot be deleted, or that no secret store is available to delete, stops the switch before activation with `SECRET_STORE_UNAVAILABLE` and keeps all metadata, so no release is ever left with a secret that nothing references. The secret store is selected from the lock alone, so a runtime variable that is not set cannot turn this into a silent skip. Rollback therefore cannot restore a credential that `logout` removed or revoked; this is tested for every credential class (identity tokens, the runtime credential, a discarded credential, and the non-secret pending revocation record) across update, rollback, a second update and rollback, and a reinstall over kept state.

Limits: release archives carry no macOS notarization or code signature and no Windows Authenticode signature. Provenance depends on GitHub Actions and the repository's workflow files. A channel host can withhold updates until metadata expires. A stolen channel key stops counting on a client once that client fetches a root that removes it; an attacker who both holds a still-trusted channel key and controls what the client receives from its update source can withhold that root, so the key stays usable against that client until it reaches the authentic source or its current root or the attacker's metadata expires ([security boundary](release/trust-root.md#security-boundary)). Over plain HTTP (`updates.transport: http-allowed`), anyone on the network path can answer `root/<N+1>.json` with a 404 as the source's operator can over HTTPS, so this root-withholding exposure extends from the endpoint operator to the network path; it still does not let them forge or replay metadata. A channel signature also authorizes code: a malicious release a client activated ships the CLI that manages the installation and can rewrite its trust state, so root rotation recovers only installations that have not yet activated a release signed with the compromised key; the others need a reinstall from an archive verified out of band. An installation whose trust originated from v1alpha4 legacy keys (both roles, threshold 1) gives a compromised legacy key root authority as well, so root rotation cannot recover it either; owners should move to a split root and channel bootstrap promptly. The vulnerability verdict is a build-time snapshot. Local workspace packages are linked rather than downloaded, so they are left out of the lock's package list and are covered by the payload inventory and archive digest, not by the source gate or SBOM checksums. Any other locked package without integrity fails the source gate.

## Logout and revocation

`logout` revokes the runtime credential at the broker's revoke endpoint when one is declared, revokes identity refresh and access tokens at the provider's revocation endpoint when discovery advertises one, then deletes local secrets, including any orphaned or pending generations, and metadata. Revocation failures are reported as warnings, and local clearing still happens. Local clearing does not depend on the runtime configuration: when a runtime variable is not set, or a provider cannot be loaded, `logout` warns, contacts nothing, and still deletes the local secrets and confirms it; the runtime credential is recorded as a pending revocation (when the provider could revoke it) and the identity tokens are audited as not revoked, since both may still be valid remotely. A secret that cannot be deleted makes `logout` fail with `SECRET_STORE_UNAVAILABLE` and a message naming what was and was not cleared; its metadata stays so the next login or logout deletes it. `logout` also deletes the stored sandbox credential, which has no remote revocation; `sandbox logout` deletes only that one. Sessions, preferences, and the principal binding are kept. `purge` removes PiShip-owned state files and deletes the secret-store entries its metadata references, confirming each deletion, but it revokes nothing. So while an identity session, a runtime credential, or a stored sandbox credential is present (a discarded marker counts as signed out), `purge` and `uninstall --purge` refuse before deleting anything: run `<command> logout`, which revokes the credential, then `uninstall <id> --purge --yes` (after a plain `uninstall`, `node <release-dir>/payload/bin/<command> logout` runs the same sign-out from the downloaded release, then `purge <id> --yes`). Only with no release left to run `logout`, `--without-logout` purges anyway, deletes the local secrets, and warns that what it held stays live at the identity provider or broker until it expires. A secret it cannot delete fails the purge before any state is removed, so running it again retries. Credentials that PiShip does not manage, such as Pi-native provider auth, may need manual revocation. Update and rollback revoke, best effort, a credential they must clear because the target cannot read it.

## User switching

The user is the principal `(iss, sub)` ([identity](identity.md#principal)). User A's runtime credential is never usable by user B:

- **Bound state.** The runtime credential and its entitlement (the broker's model list) are bound to the principal they were issued to, and checked against the signed-in principal before every use. A credential bound to anyone else, or to nobody, is revoked where supported and deleted, never used. The model selection (`model` and `models.allowed` in `config/preferences.json`) is cleared when the principal changes; other preferences stay. A missing principal binding (state from a release before v0.7) counts as a change unless the stored session is the signing-in principal's, so a user who signs in after the previous user signed out under that release does not inherit the selection. The model catalog is fetched with the current credential at each launch and never cached on disk.
- **Sandbox credential.** The stored sandbox credential is bound the same way: it is used only by the principal that stored it (or, without identity, only while no identity is configured), and only for the endpoint origins it was stored for. `login` as another principal deletes it, confirming the deletion, before the new identity is stored, and a failed deletion fails the login. A launch that finds one bound to anyone else, including after a change of workload principal, deletes it, confirming the deletion, and refuses with `SANDBOX_UNAVAILABLE`; a running session that finds it changed stops using it without deleting anything. `logout`, `sandbox logout`, and `purge` delete it, and an update or rollback to a release that cannot read it deletes it before the switch.
- **Order of a sign-in.** `login` revokes and deletes the previous credential and confirms the deletion before it stores the new identity. On a change of principal it also clears the model selection and the previous identity session (its tokens are revoked at the provider where supported, then deleted and the deletion confirmed) before the new identity is stored. A crash at any point leaves either the previous identity without a credential or the new identity without one, never the new identity with the old credential.
- **Fail closed.** A secret that cannot be deleted, or whose deletion cannot be confirmed (a locked keyring, a store error), fails the login before the new identity is stored, and fails every launch, until the secret store works again. The references stay tracked by a discarded marker that no release reads as a credential, so neither a later launch nor a rollback to an older release can use them.
- **Revocation failures do not block the next user.** A failed broker revocation is shown, audited as `credential.revoke` with `revocation: failed`, and recorded without the secret as a pending revocation that every login checks and `doctor` reports. The local secret is deleted all the same. Because the broker authenticates revocation with the credential itself, PiShip cannot send the revocation again once the secret is deleted: a pending entry is resolved when the credential expires, or by an administrator revoking it at the broker.
- **Rollback.** Snapshots never contain credentials, and rollback never restores one, so it cannot bring back the previous user's credential.
- **Running sessions.** A running session serves the principal it started with. Its first activation (or its `login`) pins the principal, and every later credential use compares the stored credential's bound principal and generation with it: a session never serves its cached secret once another user signed in elsewhere, never renews into a credential issued to someone else, and fails with `IDENTITY_REQUIRED` ("The signed-in user changed; restart the session") instead. An identity refresh must keep the pinned principal, and never refreshes or returns a session another user stored meanwhile (`IDENTITY_INVALID`, "Another identity signed in").
- **Serialized changes.** A sign-in runs from clearing the previous credential to acquiring the new one under the credential lock (`credentials-metadata/inference.json.lock`), clears another principal's sandbox credential under the sandbox credential lock (`credentials-metadata/sandbox.json.lock`), and writes the identity under the identity lock (`identity/session.json.lock`), always in that order; a sign-out takes the same locks in the same order, and an identity refresh takes only the identity lock, so no two of them wait for each other in a cycle. A launch or renewal re-reads the stored identity under the credential lock and stops, touching nothing, when it is no longer the principal it resolved (another sign-in or a sign-out happened meanwhile). The browser part of a sign-in runs before any lock is taken.
- **Sign-out.** `logout` revokes and deletes the runtime credential and the identity tokens and confirms each deletion. Tokens that cannot be deleted leave an identity discarded marker (`piship-identity-discarded/v1`) in place of the session: it names only the references still to delete, no release restores it as a session, and every later command deletes them first and fails closed (`SECRET_STORE_UNAVAILABLE`) until it can, so the signed-out user cannot launch again on the kept tokens. The command reports the failure and exits with an error.
- **Attribution.** Audit events name the principal as one string, the issuer, `#`, then the subject (`principalId` in `@piship/contracts`; `%` and `#` in the issuer are percent-encoded), so two users with the same subject at different issuers are never confused. Email and display name are attributes, never the attribution.

Limits:

- Pi session history is project data owned by Pi. With an identity session it is kept per principal: `sessions/user/<principal digest>/` and `sessions/acceptance/<principal digest>/`, where the digest is 32 hex characters of a SHA-256 over the issuer and subject, so another user signing in on the same OS account does not resume the previous user's sessions, and the same user resumes across logout, login, update, and rollback. A distribution with no identity provider (a personal one) keeps the shared `sessions/user/`. Sessions written directly under `sessions/user/` by an earlier release are not resumed by a signed-in user; purge removes them.
- The principal binding and pending revocations are ordinary files under the state directory: anyone who can modify the state directory can defeat them, as with the rest of the state.
- A release before v0.7 cannot finish a deletion that failed. PiShip's own update and rollback delete the secrets a discarded marker (credential or identity) names before they switch, and stop when they cannot; but an older release that finds a marker anyway (installed over this state some other way) sees an incompatible schema and removes it without deleting those secrets, which are then left in the secret store untracked. They are never used, and `purge` does not find them either; remove them with the platform secret-store tool (entries named `piship:<id>:inference#<n>`, `piship:<id>:sandbox#<n>`, and `piship:<id>:identity#<n>`), or repair the secret store and sign out before rolling back.
- A pending revocation without an expiry never resolves on its own. At most 20 entries are kept; older ones are dropped and only their number is kept and reported.

## Headless and workload runs

A managed distribution with a [workload identity](identity.md#workload-identity-headless-runs) runs with no person, no browser, and no stored login. The headless E2E (`tests/e2e/headless.test.ts`, local fixtures) runs such a distribution with no browser opener allowed, no authorization page and no identity provider request, personal credentials planted around it, key rotation, expiry, and a change of workload principal.

What a headless run proves:

- **No browser.** The adapter's `login` receives an `openUrl` that fails the run; PiShip never prints an authorization URL or starts a browser opener for it, and no process approves an authorization page. The E2E's browser-opener tripwire runs on POSIX only.
- **No ambient personal credential.** Provider keys and other credential-named variables are removed from the environment before any adapter loads ([managed runtime isolation](#managed-runtime-isolation)); Pi's `auth.json` under `~/.pi` or another distribution's state is not used or sent (the headless E2E plants such values and asserts that none reaches a request or a state file); and a missing or failing workload identity fails the run closed, with no fallback to Pi-native or personal credentials.
- **A scoped credential.** The gateway sees only the runtime credential the broker issued to the workload principal, bound to `(iss, sub)` like a person's ([user switching](#user-switching)); the broker sees only the workload token.
- **Expiry and rotation.** A credential is renewed within `refresh.beforeExpiry` with the workload's current token, replaced generations are deleted, and a credential past its expiry that cannot be renewed fails the run (`CREDENTIAL_EXPIRED`, or `IDENTITY_EXPIRED` when the broker rejects the workload token and the adapter has no valid one).
- **Managed policy.** The model allowlist, entitlement, network policy (including for the adapter's own requests through `context.fetch`), and every other managed control apply unchanged.
- **Principal changes.** A run whose workload principal differs from the previous run's never uses the previous principal's credential, entitlement, or model selection, and leaves none of its secrets behind.

What it cannot prove:

- **Who the workload is.** PiShip does not validate a workload token (it checks an ID token only in the built-in OIDC flow): the principal is what the adapter returns, and the adapter is distribution code running with the process's privileges. The broker is the authority that must validate the workload token and bind the credential it issues to that token's subject; a broker that trusts the principal without checking the token grants whatever the adapter claims.
- **That the token source is protected.** A token file, platform endpoint, or metadata service is the workload platform's responsibility; anything that can read it can act as the workload.
- **That the agent cannot read the workload token.** The agent's own tools run as the same user: a prompt-injected `bash` call can read a token file, or a well-known platform path, and use it outside PiShip's policy and audit, and a broad token (a default Kubernetes service account token) also works against other services. Use a token whose audience is the broker only, keep the file outside the workspace and the state directory, mode 0600, and run the agent under a required sandbox whose filesystem policy denies the token path and `<state>/secrets/` (the built-in profiles are not verified to do so). PiShip removes credential-named variables such as `AWS_WEB_IDENTITY_TOKEN_FILE` from the environment before adapters load, so name the token path in a variable the adapter reads that is not one of them.
- **Isolation between workloads finer than the subject.** Credentials, entitlement, and session history are keyed by `(iss, sub)`; workloads with the same subject share them. Two workloads with different subjects must not share a state directory: each activation would revoke the other's credential.
- **That nothing is at rest.** The workload session is held in memory only, but the runtime credential is stored in the configured secret store. A Linux runner without a Secret Service needs the plaintext file store, and there is no memory-only option yet ([headless storage](credentials.md#headless-runs)).
- **Revocation at the end of a job.** A credential stays valid at the gateway until it expires unless the job runs `logout` (which revokes it where the broker supports it) or the broker issues short-lived credentials.
- **Confinement of the adapter.** Like any adapter or extension, the workload adapter is in-process code; PiShip cannot stop it from starting a browser or using other credentials on its own. Loading it is a code-trust decision.

## Guarantees and their limits

Within the enforcement plane each control names, PiShip provides: deterministic loading of only declared and admitted resources; resource, provider, and project trust decisions; model allowlist enforcement in managed mode; MCP governance for declared servers; static version and integrity verification of the payload and releases; storage and process-scoped injection of the credentials PiShip manages; inspectable configuration and explainable policy decisions; metadata-first audit where enabled; an enforcement status for every action that never reports an action without a runtime seam as enforced; activation checks for a required sandbox; and reproducible static builds.

PiShip does not and cannot guarantee:

- protection from a machine administrator or anyone who can modify the installed payload, state, or inventory;
- isolation that the configured sandbox backend does not provide, or native OS isolation on Windows; for a remote or custom backend, the isolation its operator attests;
- that approved third-party code (extensions, providers, MCP servers) is trustworthy; loading it is a code-trust decision;
- the correctness or security of the organization's identity provider, credential broker, inference gateway, upstream model providers, or external MCP servers;
- prevention of every prompt-injection attack; project instructions are model input, not an enforcement mechanism;
- endpoint controls that MDM, EDR, or network infrastructure normally provide.

The two deployment modes have different credential trust models. In a managed gateway profile the organization keeps upstream provider and gateway administration credentials server-side, and the developer machine holds only the scoped runtime credential the broker issues. In personal mode the owner may intentionally keep personal provider credentials on the machine, either delegated to Pi-native auth in the distribution's isolated `agent/` directory or stored through a `local-secret` secret store; PiShip then protects the machine-local copy only as described under [Secrets](#secrets).

## Not covered

PiShip does not contain the Pi process or in-process extensions, enforce hostname-level egress for child processes, filter system calls, or code-sign release artifacts for macOS or Windows. v1alpha1 and v1alpha2 distributions have no tool policy, OS sandbox, MCP governance, or audit log; v1alpha1 to v1alpha3 distributions have no signed update channel. Report vulnerabilities through [SECURITY.md](../SECURITY.md).
