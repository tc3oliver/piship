# Update lifecycle

How an installed distribution trusts channels, updates, rolls back, checks local data, and activates a release atomically. This page is part of the [release guide](../release.md); building and signing are in the [owner workflow](owner-workflow.md), and the archive format in the [artifact contract](artifact-contract.md).

## Channels and signed metadata

A distribution declares its channels in `updates` ([manifest](../manifest.md#lifecycle-fields-v1alpha4)). The names are `stable`, `candidate`, and `dev`; `updates.channel` (default `stable`) is where users start, and `updates.channels` lists the channels users may pick. What each channel carries is the owner's decision. `piship release --channel` records the channel a build is meant for; `sign-channel` may add the same archive to another channel, so a candidate can be promoted without a rebuild, while its `release.json` keeps the original channel.

An update source is a directory, served as static files over HTTPS or read locally, containing:

```text
root/2.json        piship-update-root/v1: the update root after the bootstrap, then 3, 4, ...
root/2.json.sig    piship-signature/v1 envelope, signed by the root role
stable.json        piship-channel/v1 metadata
stable.json.sig    piship-signature/v1 Ed25519 envelope over the exact bytes of stable.json
acmecode-1.1.0-linux-x64.tar.gz
acmecode-1.1.0-darwin-arm64.tar.gz
...
```

The channel metadata names the distribution and channel, a monotonic `sequence`, an `expires` time, and for each release its version, target, archive name, archive SHA-256 and size, Pi and PiShip versions, and lock SHA-256. The owner creates and signs this metadata with `piship sign-channel` ([owner workflow](owner-workflow.md#signing-a-channel)).

Clients accept channel metadata only when its signatures meet the channel role's threshold of the installation's current update root, the metadata names this distribution and channel, it has not expired, and its sequence is not lower than the highest one this installation has already accepted for that channel. The highest accepted sequence is stored in the install receipt, so replaying older signed metadata is refused. Re-sign each channel before it expires; expired metadata stops updates until it is re-signed.

The update root is installation state (`<install home>/trust/<id>.json`): a fresh install starts it from the installed release's bootstrap, and only a verified root refresh advances it. Activating a release, `rollback`, and channel changes never change it, and neither does the lock of a downloaded release, so rolling back never re-trusts a key a newer root removed. A damaged or missing trust state stops `update` until the installation is re-bootstrapped from a verified release ([installation trust state](trust-root.md#installation-trust-state)).

## Updating and rolling back

Users run the branded commands; `piship update <id>` and `piship rollback <id>` run the same commands through the active release:

```bash
acmecode update --check                 # verify what is available; change nothing
acmecode update                         # verify and activate the newest release on the channel
acmecode update --channel candidate     # switch to an allowed channel
acmecode update --from ./channel        # use another directory or URL than updates.source
acmecode update --accept-review         # proceed when the migration check requires review
acmecode rollback                       # return to the retained release
node packages/cli/dist/bin.js migrate-check acmecode <archive|release-dir|payload>
```

`update` needs a release-tracking install of a `piship/v1alpha4` or later release with update trust (a v1alpha5 or v1alpha6 bootstrap, or v1alpha4 keys). It locks the installation against a concurrent update, rollback, or uninstall, repairs a state marker left behind by an interrupted operation, then:

1. Selects the channel: `--channel` must be in `updates.channels` (`POLICY_DENIED` otherwise) and is remembered after an update, not after `--check`; a remembered channel that is no longer allowed falls back to `updates.channel` with a notice.
2. Resolves `updates.source` from the environment, or uses `--from`. The resolved value and `--from` are checked like the manifest: `https`, or `http` on `127.0.0.1`, `localhost`, or `[::1]` (or, when the active release sets `updates.transport: http-allowed`, on a private or internal host; a public one is refused), with no credentials, query string, or fragment; any other scheme is refused with `NETWORK_DENIED`. A local directory from `updates.source` must be absolute; `--from` also accepts a relative one. From a terminal, `update` and `rollback` print one line on stderr as each long step starts (checking the channel, downloading with its size, verifying, switching); `piship build` does the same for installing the runtime packages and assembling the payload. Nothing is printed when stderr is not a terminal; `PISHIP_PROGRESS=1` turns the lines on there and `PISHIP_PROGRESS=0` turns them off. Requests use the managed fetch with the distribution's proxy and CA settings. Plain HTTP needs no CA setting and still goes through the configured proxy. A redirect is followed only within the source's origin (same scheme, host, and port, at most five times); one to another origin, including from `https` to plain HTTP, fails with `UPDATE_FAILED` and is never contacted. HTTP 429 and 5xx answers are retryable, with `Retry-After` reported as `retryAfterMs`. When channel metadata looks expired but the source's HTTP `Date` says it is still valid, the error says this computer's clock is ahead instead of asking the publisher to re-sign. Only the host of the declared `updates.source` is added to a `privateOnly` allow list; a `--from` URL gets no such exception.
3. Refreshes the update root: fetches `root/<N+1>.json` and its signature, requires version N+1 and signatures meeting the current and the new root-role thresholds, persists it, and repeats until the source answers 404 ([root refresh](trust-root.md#root-refresh)). Any other failure stops the update here. The newest root must not have expired at the time recorded when the attempt started.
4. Reads and verifies the signed channel metadata with the newest root's channel role, as above.
5. Picks the newest release for this machine's target. If it equals the active version, reports up to date; if the channel lists no release for this target, reports up to date with a notice; if it is older, refuses the downgrade.
6. Downloads the archive into a staging directory (unless a release this installation retains was built from that exact archive digest, or an earlier attempt's complete download is still kept: neither is fetched again) and checks its size and SHA-256 against the signed entry, then reads the small release metadata for this target and checks that the release matches the signed entry (distribution, command, version, Pi version, lock digest). A release that records its Pi version as unsupported is refused.
7. Runs the migration check against the local state (below). `unsupported` stops the update; `requires-review` stops it unless `--accept-review` is given (a `--check` reports it with a notice instead).
8. With `--check`, stops here and reports the available version, signing key, and migration report. Over the network, a check that finds a newer release does not download the archive unless a retained copy or a kept download can answer it: the signed entry alone says what is available, and the migration check runs when you update, before anything is switched. Nothing is extracted or activated. Newer roots fetched in step 3 are kept: they only ever add what the installation knows.
9. Snapshots non-secret state, then extracts the archive once, directly into its version directory, which nothing references yet, so an interruption leaves only an unreferenced directory. The extraction hashes each file as it writes it, and the digests are compared with the inventory the signed entry binds before the receipt is written; a mismatch fails the update. A retained release of the same version is reused, without a download, when its recorded archive digest equals the signed one and its lock and target still match the entry (otherwise it is replaced by a download), and is never overwritten otherwise. A complete download that fails after its digest check for a reason other than integrity (a migration review, a running session, a full disk) is kept in `apps/<id>/.downloads/` and used by the next attempt after its digest is checked again; a successful update removes it, and `doctor` removes one older than a day. Release and CI smoke evidence replaces a client launch check: the user's first actual launch validates runtime functionality.
10. Clears credential data the target cannot read and switches the active release in one atomic step, the receipt write. Then an installed launcher that this PiShip would write differently is replaced.

After an update, the previous active release is retained for rollback when `updates.rollback` is true in both the old and the new release. The receipt tracks at most two releases: the active one and one retained release. A running launcher holds a version-specific runtime lease, so an older payload stays on disk while a live session still uses its resources. A successful update or rollback then reclaims obsolete versions and the `.retained-*` directories that a replaced or interrupted update set aside, once its lifecycle lock is released and within a budget of 1.5 s; what is left (a release a running session still uses, or what the budget did not reach) is removed by the next update, rollback, or `doctor`, which uses a longer budget. Reclaiming never removes the active version, the rollback target, or a version a live session holds, and a failure to reclaim is a notice, never a failed update. Install and launch never delete a version, and uninstall removes them all. Uninstall refuses while a runtime lease is live; doctor reports live and stale leases, not counting the lease of the launcher doctor itself runs in.

`rollback` switches back to the retained release. It loads that payload's target and metadata without an inventory scan or launch check, requires the same command name, and refuses a retained release newer than the active one (use `update` to move forward again). It runs the same migration check: `unsupported` stops it, and review notices are printed. Sessions, preferences, and user policy stay in place. The release rolled back from is kept as the retained release, but a second rollback is refused because it is newer; `update` downloads it again.

Install and update hash the archive and every file they write during the one extraction and compare them with the signed or bound inventory before the receipt is written, so they do not re-read the payload afterwards. Every launch hashes `piship.lock`, which carries `policy.enforced`, against the digest the receipt recorded. `doctor`, `verify-release`, and a launch of a distribution that sets `runtime.verifyAtLaunch: true` verify the whole inventory; a rollback and a launch without that setting do not. Signed update metadata, target matching, state migration, and atomic receipt activation apply throughout. `piship repair <id> <release>` restores a damaged installation from a fully verified artifact.

Updates and rollbacks record `runtime.update` and `runtime.rollback` audit events (allowed or denied, with versions and the error code, never content) for governed distributions, best effort. An update that reads a non-loopback channel over plain HTTP adds `transport: http`, and so does an `update --check` over plain HTTP, which is recorded as `runtime.update` with `check` set to its outcome (`up-to-date`, `available`, or `failed`). Outcomes are counted in `<state>/logs/metrics.json` as `update:ok`, `check:<code>`, `rollback:<code>`, and so on. `doctor` adds Supply Chain and Update sections: whether the active release was installed from a verified release, the active version, channel and allowed channels, source (a warning, `http (integrity by signature only)`, when it resolves to plain HTTP on a non-loopback host) and an `http-allowed` transport, the installation's update root (version, origin, expiry, channel threshold) or the problem with its trust state, the trusted channel keys with each key's ID and `sha256:` fingerprint, channel keys a newer root removed, the retained release, the last check, leftovers of an interrupted operation, and the lifecycle counters. `doctor` never contacts the update source.

## Migration check and local data

The migration check compares each local data class with the state schemas the target release reads (recorded in its lock and `release.json`; releases built before lock v1alpha4 are assumed to read the v1 schemas). It only reads the state directory, and `piship migrate-check` runs it standalone; it exits 1 on `unsupported`.

| Class | Path under the state directory | Update and rollback |
| --- | --- | --- |
| State marker | `state.json` (`piship-state/v1`) | Rewritten after each update and rollback activation with the distribution, version, Pi, and PiShip versions. One that cannot be written then keeps its previous content, is reported as a notice, and is repaired by the next update or rollback. One that is empty or cannot be parsed (a crash or full disk mid-write) counts as absent: the active release is used and the marker is rewritten |
| Identity session | `identity/session.json` | Credential class: kept when the target reads its schema and uses the same secret store, otherwise cleared with its secret-store entry and reacquired by `login` |
| Runtime credential metadata | `credentials-metadata/inference.json` | Credential class: kept when readable and the secret store stays the same, otherwise cleared with its secret-store entry and reacquired |
| Sandbox credential metadata | `credentials-metadata/sandbox.json` | Credential class: kept when readable and the secret store stays the same; otherwise (every release before it, and always for a discarded marker) its secret is deleted before the switch and the user runs `sandbox login` again |
| Pending credential issuance | `credentials-metadata/pending-issuance.json` | Credential class without a secret: kept when the target reads its schema and the runtime credential is kept, otherwise deleted before the switch; never snapshotted |
| Principal binding | `identity/principal.json` | Kept in place; never snapshotted. An unreadable record counts as a change of principal |
| Pending revocations | `credentials-metadata/revocation-retry.json` | Kept in place; never snapshotted; holds no secret |
| File secret fallback | `secrets/` | Never copied, snapshotted, or restored; a cleared class's own secrets are deleted from it; the directory is removed only when every present class that holds secrets is cleared (always for a change of storage provider), so a kept credential or identity keeps its secrets |
| Preferences | `config/preferences.json` | Kept in place; `unsupported` when the target cannot read its schema; included in the snapshot. An empty or damaged file is `unsupported` and never deleted: the reason names its path, and moving it aside (for example to `preferences.json.damaged`) lets the command go ahead with default preferences |
| User policy rules | `config/policy.json` | Kept in place; included in the snapshot |
| User auto mode | `config/auto.json` | Kept in place, not snapshotted; it applies only while the target release allows `policy.userAuto`, so a stored switch has no effect after an update to a release that does not |
| Pi agent configuration | `agent/` | Owned by Pi and kept in place; Pi-native `auth.json` is a credential and never snapshotted |
| Sessions | `sessions/` | Kept in place; Pi migrates its session files forward. A target with an older Pi than the one that wrote existing sessions `requires-review`. A release whose lock declares `data.sessions.retention` deletes session files past it after each session ends and at `logout`, never one a launch holds |
| Audit and metrics logs | `logs/` | Kept in place; `audit.jsonl` is rotated by size ([state table](../architecture.md)); with `data.audit.retention`, rotation keeps a rotated file younger than that minimum past the usual count, and the sweep deletes rotated files that aged out, never the live `audit.jsonl`; `unsupported` when the target cannot read the newest audit event schema, read from the newest complete event in the newest audit file that has one. A line cut short is skipped and kept in place, never rewritten |
| Cache | `cache/` | Not migrated; safe to delete; a declared `data.cache.retention` sweeps it after each session and at logout |
| Runtime data | `data/` | Kept in place |
| Migration snapshots | `migration/snapshots/` | The last three completed pre-update snapshots |

Verdicts are `safe`, `requires-review`, or `unsupported`; the report shows each class with its action (`keep`, `clear-and-reacquire`, `review`, or `refuse`) and reason. An unreadable file of a schema-versioned non-credential class other than the state marker is `unsupported`: PiShip never reinterprets data under another schema, and never deletes data it cannot rebuild. The reason names the file's full path and the way out: move it aside and run the command again.

Before activating an update, PiShip copies `config/preferences.json` and `config/policy.json` into `<state>/migration/snapshots/<sequence>-<from>-to-<to>/` with a `piship-snapshot/v1` record that lists the credential paths it excluded, the snapshot's creation sequence, and the time. The snapshot is built in a `.staging-p<pid>-*` directory beside the others, its record written last and read back, flushed to disk, and published by one rename, so a snapshot directory is always complete; a failure removes the staging directory and stops the update before activation. The last three completed snapshots are kept, by creation sequence rather than by time, so a clock set back or forward does not change which are the newest. Each snapshot also removes what interrupted ones left: staging directories of a process that no longer exists (or older than ten minutes), and snapshot directories without a valid record. No command restores a snapshot; it is a manual recovery copy.

A change of `credential.storage.provider` between the active and the target release (`file` to `system`, or `system` to `file`) is a credential transition: the other store cannot read a reference the old one holds, so a present identity session and runtime credential are `clear-and-reacquire` with the reason `The secret store changes from <old> to <new>; …`, and the switch prints `<class> was cleared because the secret store changes from <old> to <new>: its secrets were deleted from the <old> store; sign in again`. The switching release, which reads the old store, does the clearing, so the target never looks an old reference up in its own store. `update --check` and `piship migrate-check` report it the same way.

On Linux with the `system` store, a rollback to a release whose lock has no `runtime.stateSchemas.credentialIssuance` (every release before v0.7) is a credential transition too: since v0.7 a Secret Service value over 8000 characters is stored as parts behind a `chunks:<n>:<write>` primary, which an older release would read as the secret, and whose parts its sign-out would leave behind. A present identity session, runtime credential, and stored sandbox credential are `clear-and-reacquire`; the switching release deletes every part, confirms it, and removes the metadata before the switch, and stops before activation when it cannot. The target signs in again ([decision 30](../decisions.md)).

Credentials are never snapshotted, copied into a release, or restored. Rollback switches only the immutable payload, so it cannot bring back a credential that was revoked or cleared: after `logout`, a rolled-back release requires `login` again. When a credential class is cleared because the target cannot read it, the switching release first revokes the runtime credential at the broker's revoke endpoint, best effort, when the distribution declares one (a failure is a notice, and local clearing still happens). It then deletes the local secret-store entries each cleared class references and the metadata file. Identity tokens are cleared only locally: the identity provider's revocation endpoint is not called. Run `logout` first when identity tokens must also be revoked remotely.

## Install layout and atomic activation

```text
<install-home>/                           ~/.local/share/piship or PISHIP_INSTALL_HOME
  receipts/<id>.json                      piship-install/v1 receipt: the only record of the active release
  apps/<id>/launch.mjs                    reads the receipt and starts the active release
  apps/<id>/<version>/                    immutable payloads: active, retained, or leased by a live runtime
  apps/<id>/.runtime-leases/              version-specific runtime process leases
  apps/<id>/.staging-*                    in-progress downloads; marked with their owner, removed by the next operation
  apps/<id>/.lifecycle.lock               one update, rollback, or uninstall at a time (piship-lifecycle-lock/v1)
<bin-home>/<command>                      shim that runs launch.mjs; <command>.cmd on Windows
```

The lifecycle lock names its holder as a runtime lease does: its process ID, its start identity (the boot ID and start time on Linux only: elsewhere reading it starts a process, PowerShell on Windows and `ps` on macOS, so the record carries `null` and a process that must judge it asks then), its start time, its host (a token of the host name and, on Linux, the PID namespace), and a random instance ID. The holder refreshes the lock's modification time every 15 seconds while it runs. The next operation takes the lock over at once when the holder is provably gone: the lock was written on this host and no process has its ID, or the process that has the ID now started at another time (the holder crashed, or the machine or container restarted, and an unrelated process took the ID). The same running holder is never displaced. When the holder cannot be judged that way, the lock's modification time against the wall clock is all the operation has: each command is one attempt in a fresh process, so unlike the credential lock ([credentials](../credentials.md)) it has no earlier observation of the lock to compare with. It then treats the lock as abandoned only after 24 hours without a refresh. That applies to a lock written on another host sharing the install home (its process ID means nothing here, so it is never judged by this host's processes), to a lock written by an earlier PiShip, which holds only a process ID (or a process ID and an instance ID) and is judged by that ID as before, and to a lock whose holder's start time cannot be read. 24 hours is far above the longest step that blocks the refresh (an archive extraction of a large payload on a slow disk) and above the clock corrections and sleeps a running holder sees; only a clock that jumps forward, or a machine that sleeps, for more than a day while the holder cannot refresh displaces a holder judged by the lease. This bound is a decision, not a default to tune per machine. The blocked command fails with `UPDATE_FAILED` (`ROLLBACK_FAILED` for a rollback), `Another update, rollback, or uninstall of <id> is running (process <pid>)`, and an action that names the lock file: `Try again when it finishes; if none is running, remove <install-home>/apps/<id>/.lifecycle.lock`. Remove that file by hand only after confirming that no `update`, `rollback`, or `uninstall` of the distribution is running; PiShip does not remove a lock whose holder looks alive. What the crashed one left (staging directories, payloads the receipt does not name) is reported and reclaimed by `doctor`, within its time budget; the next update or rollback does not wait for it. A holder that lost its lock anyway does not commit: update and rollback check that the lock still names them right before they write the receipt, and when it does not they fail with a retryable error, write nothing, and leave the release directories to the operation that holds the lock now. The check and the write are two steps, so a takeover between them is not caught. A lock whose content cannot be read is judged by its modification time alone (24 hours), and a directory or symlink at its path is never removed. A holder removes only its own lock.

The launcher holds a second lock while it registers a launch, `receipts/.<id>.launch.lock` (the launch gate), and writes a launching marker under `apps/<id>/.runtime-leases/.launching/` until its runtime lease exists; `update`, `rollback`, and `uninstall` take the same gate before they remove release directories. Both records name the launcher the same way as the lifecycle lock, except that a launcher outside Linux records its start time without its start identity, which would cost a process start on every launch; a process that finds the record asks the system for the start time of the process that has the ID only when that ID is in use and is not its own, and compares it within 30 seconds (a first launch on Windows can spend that long loading and scanning `node.exe` before Node's clock starts). The launcher writes its runtime lease itself, with the record `holdRuntimeLease` writes, before the runtime loads, then releases the gate and the launching marker: the gate is held for the milliseconds registration takes, not for a cold load of the runtime. An `update`, `rollback`, or `uninstall` waits for a registering launch when it takes its lock, does its work, and takes the gate again only around the receipt write. A gate is judged as the lifecycle lock is. A launcher that finds the gate held waits half a second, then fails with `A launcher or lifecycle operation for <id> is registering: <path> is held by process <pid>` (`on another host` when it is another host's). `update`, `rollback`, and `uninstall` wait up to three seconds, then fail with a retryable `UPDATE_FAILED` (`ROLLBACK_FAILED` for a rollback) that names the gate and its holder. An error other than a held gate (a read-only or full disk, a permission error) is reported as it is, never as contention.

`piship install <payload|release-dir|archive>` accepts a payload directory as before, or a release, which it extracts once for this target, hashing the archive and each file in the same pass and comparing them with the release's bound inventory before it writes the receipt (a payload directory is hashed while it is copied). `--sha256 <hex>` (an archive only) and `--expect-key sha256:<fingerprint>` (repeatable; each given key must be a channel key of the release's bootstrap) check the values the owner published before anything is installed ([distribution bootstrap](trust-root.md#distribution-bootstrap)). `install.sh` and `install.ps1` inside an extracted release run `install` on it, without a separate `verify-release` pass (run that on the directory for the full verification: checksums, SBOM, notices, and scan results). The receipt records each retained release (version, payload path, install time, and for releases the target, channel, Pi and PiShip versions, lock digest, and archive digest), the active and retained versions, the selected channel (an install starts on `updates.channel`, whatever channel the archive was built for), the highest accepted channel sequences, that the installation keeps update trust state, release keys a v0.7 update retired (older receipts only), and the last check. The update root itself is in `trust/<id>.json`, written at install from the release's bootstrap. Receipt paths must be the owned ones or the receipt is rejected.

Activation atomically replaces the receipt after the archive has been extracted and closed. The receipt and state marker are flushed; the payload is not reopened file by file for fsync. A process interruption leaves the old or new receipt active, but power loss may leave recently extracted files incomplete; restore them with `repair`. Old version directories and abandoned staging are kept off the install, upgrade, and boot critical paths: `doctor` reclaims them within a time budget (keeping the active version and the rollback target) and uninstall removes them. Credential data the target cannot read is cleared just before the switch, so an interruption between those steps can leave the old release active with the user signed out.

A receipt written by an earlier PiShip (without `schema`) is still read, launched, and uninstalled, but `update` and `rollback` need a reinstall: `uninstall`, then `install --use-existing-state`. `uninstall` removes the shim, launcher, every retained release, leftovers, and the receipt, and keeps state.

## Failure policy

Every failure happens before activation and leaves the active release and state unchanged, apart from the highest accepted channel sequence and the last check result, and, where noted, cleared credentials. Once the receipt has switched, the update or rollback reports success, is audited as allowed, and is counted as `ok`, whatever happens next: a state marker that cannot be written then is a notice, and the next update or rollback repairs it.

| Condition | Result |
| --- | --- |
| A release gate or required test fails, or the scan cannot run | `piship release` fails and removes its partial output |
| Archive, checksums, payload, SBOM, notices, or metadata do not verify | `INTEGRITY_FAILED` |
| No update trust, or no update source and no `--from` | `UPDATE_FAILED` |
| A root fetch that fails other than with HTTP 404 (network, TLS, proxy, 5xx, too large), or more than 64 new roots in one attempt (retryable; the accepted ones are kept) | `UPDATE_FAILED` |
| A root without its signature, of another distribution, with the wrong version, or not signed to both root-role thresholds; an expired newest root; a damaged or missing trust state | `INTEGRITY_FAILED` |
| Signatures that miss the channel role's threshold (unknown, removed, or invalid keys do not count), altered metadata, wrong distribution or channel, expired metadata, or a replayed lower sequence | `INTEGRITY_FAILED` |
| Channel not in `updates.channels` | `POLICY_DENIED` |
| `updates.source` variable unset | `CONFIG_UNAVAILABLE` |
| A `network.tls.additionalCA` variable unset in the shell that runs `update` | `CONFIG_UNAVAILABLE` naming the variable, before any request; the declared CA is never left out |
| Plain `http` to a non-loopback source without `updates.transport: http-allowed`, plain `http` to a public host with it, or another scheme | `NETWORK_DENIED` |
| Update source URL with credentials, query, or fragment, or `updates.source` resolving to a relative directory | `CONFIG_INVALID` |
| Downloaded archive differs from its signed entry | `INTEGRITY_FAILED` |
| Older release offered, target Pi recorded unsupported, migration `unsupported`, or `requires-review` without `--accept-review` | `UPDATE_FAILED` |
| Another update, rollback, or uninstall is running, or its lock was taken over before the receipt was written (nothing is committed). A crashed holder whose process ID is now in use looks like a running operation for up to 24 hours; the error names `apps/<id>/.lifecycle.lock`, which may be removed by hand once no lifecycle command is running | `UPDATE_FAILED` or `ROLLBACK_FAILED` (retryable) |
| No retained release, retained release damaged or newer, different command, or migration `unsupported` | `ROLLBACK_FAILED` |

## Known limitations

- Clearing an unreadable credential during update or rollback revokes the runtime credential only where the distribution declares a broker revoke endpoint, and only best effort; identity tokens are cleared locally without remote revocation.
- `update --check` over the network reads only the signed channel entry when it finds a newer release, so it does not preview the migration check or prove the release downloads or extracts; `update` does all of that before it switches. A check against a directory source, a retained release, or a kept download still reports the migration check.
- A migration snapshot has no restore command.
- The channel host is trusted for availability: it can withhold updates until the metadata expires, but it cannot forge, alter, or roll back signed metadata that a client has already seen.
- Verification detects tampering while the verifying PiShip and the pinned keys are trusted; it is not a boundary against a local administrator.
