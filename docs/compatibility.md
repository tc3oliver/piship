# Pi compatibility

`@piship/pi` pins `@earendil-works/pi-coding-agent` to exactly `1.0.3` through its public package entrypoint, and the root `package.json` `overrides` pin Pi's sibling packages exactly ([upgrade to Pi 1.0.3](#upgrade-to-pi-103)). The launcher runs only the pinned version. `compatibility/pi.json` and its copy in `@piship/core` also list `1.0.2`, the Pi of v0.9.0 and v0.9.1, `1.0.0`, the Pi of v0.8.0 and v0.8.1, and `0.87.1`, the Pi of v0.7.1, with the same surface statuses, so a release built on any of them is still recognized. Node.js 22.19.0 or newer is required, and npm 11 or later on the machine that runs `piship lock` for a distribution that declares Pi packages. No other PiShip package may directly depend on or import Pi. The committed npm lock fixes transitive package versions; the distribution lock records their npm integrity values, and a release fails when a downloaded package has none.

`compatibility/pi.json` reports status per surface. The current status of each surface, and the CI runs that back it, are kept in one place: [project status](status.md). This page defines the terms and the Pi integration contract. `candidate` means local public-API and artifact checks pass while the complete target matrix or live evidence remains pending. `supported` requires a branded install, real Pi startup, declared TypeScript extension, safe tool path, session resume, inspection, diagnostics, and uninstall on each advertised OS/CPU target.

`main` pins Pi 1.0.3 since the [upgrade](#upgrade-to-pi-103); the Release qualifications of v0.9.1 and earlier, recorded on this page and on the status page, ran on earlier pins. The production-validation baseline is v0.11.0: tag `v0.11.0` at commit `d4f740f`, with Pi 1.0.3, Node.js 22.19.0 or newer, and the targets `linux-x64`, `darwin-arm64`, and `win32-x64`. [Release qualification run 37538011406](https://github.com/tc3oliver/piship/actions/runs/37538011406) passed on that exact commit, and its nine attested archives are the [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.11.0); it is the first qualification on Pi 1.0.3. Details are on the [status page](status.md#v0110-production-validation-baseline). It replaced v0.9.1, tag `v0.9.1` at commit `a97ba43` on Pi 1.0.2, which stays documented as the [previous baseline](status.md#v091-previous-production-validation-baseline); v0.9.0, tag `v0.9.0` at commit `ff3c382` on the same Pi, v0.8.1, tag `v0.8.1` at commit `d069104` on Pi 1.0.0, v0.8.0, tag `v0.8.0` at commit `8550282` on Pi 1.0.0, and v0.7.1, tag `v0.7.1` at commit `bd4bc09` on Pi 0.87.1, are earlier ones ([v0.9.0](status.md#v090-previous-production-validation-baseline), [v0.8.1](status.md#v081-previous-production-validation-baseline), [v0.8.0](status.md#v080-previous-production-validation-baseline), [v0.7.1](status.md#v071-previous-production-validation-baseline)).

## Managed surface

Managed access (`piship/v1alpha2`) is a **candidate** on Pi 1.0.3, 1.0.2, 1.0.0, and 0.87.1. It is verified on the pinned public API with deterministic local fixtures: a loopback OIDC provider, `http-broker`, and OpenAI-compatible gateway that auto-approve sign-in. Tests cover login, credential acquisition, refresh, gateway rejection and renewal, model governance, streamed text, a tool-call round trip, cancellation, session resume, `config explain`, `doctor`, logout, and the personal `local-secret` and `none` modes. These fixtures prove PiShip's contracts. Beyond them, the Reference E2E runs the AcmeCode reference distribution on Ubuntu against the [enterprise reference stack](../examples/enterprise-reference/README.md): sign-in on a real Keycloak, a credential from the reference broker, and model requests through a real LiteLLM gateway to a deterministic mock upstream. The manual `Live provider` workflow sends one request from AcmeCode through the reference LiteLLM to a real provider; [run 36877709332](https://github.com/tc3oliver/piship/actions/runs/36877709332) passed on `main` at `9e458f0` ([status](status.md#after-v071-on-main)). ## Production lifecycle surface

The v0.4 lifecycle (`piship/v1alpha4`) is implemented on Pi 1.0.3 (and 1.0.2, 1.0.0, and 0.87.1) and recorded as the `lifecycle` surface with status `candidate` in `compatibility/pi.json` ([status](status.md)). `@piship/core` carries a copy of the matrix, and the compatibility suite checks that the two are equal: `piship release` refuses a Pi version that is not in it, records in `release.json` the weakest of the distribution's deployment surface, the `governance` surface when the distribution declares governance, and the `lifecycle` surface (so releases currently record `candidate`), and `update` refuses a release that records its Pi version as unsupported. A Pi upgrade must therefore update `compatibility/pi.json` and that copy together.

Releases are built only for `linux-x64`, `darwin-arm64`, and `win32-x64`. The lifecycle E2E installs a release of the managed demo from its archive with the shipped install script, checks that the release payload matches `piship build` output, signs in against the local fixtures, keeps a session across an update through a signed loopback channel, rejects a tampered archive, altered metadata, and replayed metadata, rolls back and resumes the session, refuses credentials revoked server-side until the user signs in again, confirms no credential remains in state or install directories and that `~/.pi` is untouched, and uninstalls while keeping state. On Windows it runs the demo with the sandbox optional. The lifecycle E2E is part of the nightly and manual Portable E2E. The manually dispatched Release candidate workflow adds per-target reproducibility, fresh-job verification, and attestation checks for the demo, personal example, and developer example, and runs the installed personal and developer releases' offline `--smoke` and `doctor`. Recorded results are on the [status page](status.md#recorded-evidence); see also [supported platforms](release/owner-workflow.md#supported-platforms).

## Public API used

PiShip uses the public SDK entrypoint: `createAgentSessionRuntime`, `createAgentSession`, `DefaultResourceLoader`, `ModelRuntime`, `SessionManager`, `SettingsManager`, `InteractiveMode`, `createReadTool`, `createReadToolDefinition`, `createWriteToolDefinition`, `createEditToolDefinition`, `createBashToolDefinition`, `createLocalBashOperations`, `createCodemodeExtension`, `createToolSearchExtension`, `VERSION`, and the `AgentSession`, `AgentSessionServices`, `CreateAgentSessionRuntimeFactory`, and `InlineExtension` types.

The managed runtime calls `ModelRuntime.create` with an in-memory credential store and no models file, then `ModelRuntime.registerProvider` for the declared gateway. Governance replaces these public methods on the `ModelRuntime` instance PiShip creates: `getModel`, `getModels`, `getAvailable`, `getAvailableSnapshot`, `checkAuth`, `getAuth`, `stream`, `streamSimple`, `complete`, `completeSimple`, `login`, and `setRuntimeApiKey`. An inline `piship-governance` extension listens to `message_end`, to detect credential rejections, and to `model_select`, to update the enterprise context. An inline `piship-redaction` extension, loaded last in every launch, returns a replacement from `message_end` whose provider error text is redacted; Pi keeps and persists the replacement in place of the original message, which the compatibility test checks against a session file on disk. At `session_start` it also prepends an `uncaughtException` listener that redacts the error in place; this relies on Pi's interactive mode registering its own crash handler (with `process.prependListener`, before it binds extensions) and adding no `unhandledRejection` listener, which the compatibility test pins together with a crash record written by that handler. The compatibility test fails if any of these methods disappears, so an upgrade cannot silently bypass governance.

[Bundled search tools](manifest.md#bundled-search-tools-v1alpha6) rely on two behaviors of Pi 1.0.3's tools manager, which Pi's find and grep tools and its `@` completion use, and which `packages/pi/src/compatibility-search-tools.test.ts` pins by running `createFindTool` and `createGrepTool` in a fresh process: `fd` and `rg` are looked up in `<agent dir>/bin` before `PATH`, and that directory is fixed from `PI_CODING_AGENT_DIR` when Pi is imported, not when a tool runs. The launcher therefore loads `@piship/pi/environment`, which imports no Pi package, to set the variable before it imports `@piship/pi`.

Model governance v2 (`model.select`, `model.dispatch`, virtual models) also replaces `resolveModel`, `hasConfiguredAuth` (managed), `registerVirtualModel`, `unregisterVirtualModel`, `classify`, `generateImages`, `streamDeferred`, `fetchDeferred`, `cancelDeferred`, and the type-aware listings (`getModelsOfType`, `getModelOfType`, `getAllModels`, `getAvailableOfType`, `getAllAvailable`). It relies on three Pi 1.0.3 behaviors that `packages/pi/src/compatibility-models.test.ts` pins against a real session: every request with a virtual selection (agent loop, an extension's direct stream, compaction and summaries, the cache warmer's replay) is routed through the instance's `resolveModel` and then sent through its `streamSimple`; a virtual catalog entry has the API `pi-virtual` (Pi exports the constant only as a type, so PiShip matches the value); and an extension's load-time `registerVirtualModel` waits in `LoadExtensionsResult.runtime.pendingVirtualModelRegistrations` with its extension path until the session binds the extensions, so PiShip registers that queue itself after `DefaultResourceLoader.reload()` (as Pi's own `createAgentSessionServices` does) and empties it. A `/reload` keeps a registration the reloaded extensions no longer make, so PiShip removes it.

Governance additionally depends on these public exports and extension hooks: `createAgentSession` options `noTools: "builtin"` and `customTools`; `createReadToolDefinition`, `createWriteToolDefinition`, `createEditToolDefinition`, and `createBashToolDefinition` with their `operations` overrides; `createLocalBashOperations`; `truncateTail`, `formatSize`, and `DEFAULT_MAX_BYTES`, which the governed `bash` execute uses to keep Pi's display tail and footer; the `tool_call`, `user_bash`, `before_agent_start`, `before_provider_request`, `session_start`, and `session_shutdown` events, and the session entries' `bashExecution` messages with their `fullOutputPath`; `registerTool` and `registerCommand`; and the extension context's `hasUI` and `ui` dialogs. Governed tools replace Pi's built-in tools of the same names. The compatibility suite asserts each of these seams individually, so a rename or behavior change fails it first: each tool definition routes file and command access through its `operations` override and nothing else; `createLocalBashOperations` runs a command and reports its exit code; the resource loader loads only the explicit paths when ambient discovery is off; each extension event and registration is delivered in a headless session against the loopback fixture gateway; a `tool_call` block prevents the tool from running; `user_bash` operations are used for `!` commands, and Pi records a `!` command's `pi-bash-<id>.log` path in the session entries that `session_shutdown` hands to extensions; the governed `bash` execute produces the same results (the text, Pi's `structuredContent`, and an `isError` result for a non-zero exit, as Pi 1.0 does), live updates, and failures as Pi's, apart from the saved path and the measured wall time, and runs the command, cwd, timeout, and environment Pi would; a provider registered with an in-memory credential store is listed and then narrowed by PiShip's model governance; and a persisted session resumes through `createAgentSessionRuntime`. The extension context's UI dialogs are checked for presence only, since the suite has no interactive UI.

Exposure, Codemode, tool search, and runtime mutation governance (v0.9) add these public seams: `createCodemodeExtension` (with `models: false`, so scripts get no `models` global) and `createToolSearchExtension`, loaded as inline extensions; the `createAgentSession` option `excludeTools`, with `AgentSession.getAllTools`, `getActiveToolNames`, and `setActiveToolsByName` (because `noTools: "builtin"` makes Pi ignore `defaultTools`); the `cacheWarming` setting, through `SettingsManager.getCacheWarmingMode` and `setCacheWarmingMode`, which PiShip replaces on its in-memory instance, and the `cache_warming_decision` event; and the events `tool_execution_start` and `tool_execution_end` (audit is keyed on them, not on `tool_call`), `before_agent_start` (with `systemPromptOptions`), `context_with_system`, `agent_start`, `agent_settled`, and `turn_end`, from which PiShip re-asserts the prompt and tool set it enforces. `packages/pi/src/compatibility.test.ts` pins them ("runtime mutation governance" and "Codemode, tool search, and exposure under PiShip governance").

Session resume works around three gaps of `SessionManager.continueRecent()`, still present in Pi 1.0.3: it resumes a file with a malformed line or a truncated last record without a signal (and appends a newline to the latter), reads a file of any size to its end, and lets two processes append to one file ([sessions](architecture.md#sessions)). PiShip therefore selects the most recent session with the same rule (the newest `*.jsonl` whose header, found in the first MiB, names the project), checks and owns it, and opens it with `SessionManager.open(path, sessionDir, cwd)` or starts one with `SessionManager.create(cwd, sessionDir)`. It relies on the runtime factory being called again with the new `SessionManager` for `/new`, `/resume`, and forks, and on a `session_before_switch` handler cancelling a resume. The compatibility suite asserts each of these, and that `continueRecent` still drops a malformed line and completes a truncated record, so a Pi release that reports damaged sessions itself, loads them lazily, or locks them fails there and the workaround can be retired.

Project trust for extensions that load project configuration themselves, such as pi-code with a project's `.claude/` ([security](security.md#project-configuration-that-an-extension-loads-itself)), adds these public seams: `SettingsManager.inMemory(settings, { projectTrusted })`, whose flag an extension reads as `ExtensionContext.isProjectTrusted()`; `ProjectTrustStore` (`get`, `getEntry`, `set`) at `<agent dir>/trust.json`, which an extension finds with `getAgentDir()` (so `PI_CODING_AGENT_DIR`, set to the distribution's state, decides where); and `hasTrustRequiringProjectResources`, which counts `.pi/mcp.json` and not `.claude/*`. `packages/pi/src/compatibility.test.ts` pins them ("project trust seam"): a real Pi session with an extension that follows pi-code's two steps sees the flag PiShip set and the decision PiShip stored, headless, and a stored approval does not open a project whose flag is false. An in-memory settings manager defaults to a trusted project, which is why PiShip sets the flag itself.

Every launch sets Pi's own startup and network switches, which Pi reads from its settings and environment and not from the SDK options PiShip passes (`packages/pi/src/launch/pi-defaults.ts`; the effects are listed under [Secrets](security.md#secrets)). The environment variables are `PI_SKIP_VERSION_CHECK=1`, `PI_TELEMETRY=0`, `PI_CODING_AGENT_DIR=<state>/agent`, and, for a managed distribution only, `PI_OFFLINE=1`; a managed launch sets them again after it has removed the inherited `PI_` variables. The in-memory settings are `enableInstallTelemetry: false`, `lastChangelogVersion` set to Pi's `VERSION`, `quietStartup: true`, and `tuiMode: "regular"`. A unit test reads the settings back through Pi's `SettingsManager`, and a Pi upgrade re-checks each switch.

There are no Pi private imports or source patches. A future Pi upgrade must update the exact pin, npm lock, matrix, and compatibility tests together, then pass the Portable E2E on every advertised target. A temporary shim needs an owner, an expiry condition (normally the Pi release that makes it unnecessary), a linked upstream issue or pull request when the gap belongs in Pi, and an automated regression test.

Two compatibility shims are registered for Pi 1.0.3; both were re-verified at the upgrades from 0.87.1 to 1.0.0, from 1.0.0 to 1.0.2, and from 1.0.2 to 1.0.3, and kept. Both use only Pi's public exports, but depend on behavior Pi does not document as a contract. Owner for both: the PiShip maintainers. Expiry for both: the next Pi upgrade, which must re-verify each shim and then remove it, keep it with a new expiry, or replace it by a recorded decision. No upstream issue is filed yet; one is linked here when the gap is reported to Pi.

| Dispose hook (`packages/pi/src/commands/dispose-hook.ts`) | Pi ends an interactive session in `InteractiveMode.shutdown()` by awaiting `runtimeHost.dispose()` and then calling `process.exit(0)`, so the governance session must end inside `dispose()`, and a failed teardown can change the exit code only by replacing `process.exit`. | `packages/pi/src/compatibility.test.ts` pins the await-then-exit order in Pi's shipped source |

## Compatibility contract

This section is the stable contract from v0.11.0. The versions of PiShip's own schemas, the migration window, and the platform and Node.js support are in the [support policy](support-policy.md). The sections that follow it ("Upgrade to Pi 1.0.3" and earlier) are the dated record of each upgrade.

### Exact pin policy

- PiShip runs exactly one Pi version at a time. `@piship/pi` depends on `@earendil-works/pi-coding-agent` at that exact version, never a range and never `latest`, and imports only its public package entrypoint. The seven sibling packages (`chord`, `pi-agent-core`, `pi-ai`, `pi-codemode`, `pi-mcp`, `pi-telemetry`, and `pi-tui`) are held at the same exact version by the root `package.json` `overrides`, and `PI_SIBLING_PINS` in `@piship/pi` is the one list the compatibility suite checks them against. The committed `package-lock.json` fixes every transitive package.
- A manifest names its Pi in `runtime.pi`, as an exact version. `validate`, `lock`, and `build` refuse one that is not the pinned version (`Pi <version> is not available in this PiShip build`). The lock and `release.json` record it, and `update` refuses a release that records its Pi as unsupported.
- Only `packages/pi` may import or depend on `@earendil-works/pi-*`. No PiShip code imports a Pi internal or private path, and no part of PiShip patches, forks, or vendors Pi.
- A release keeps running on the Pi it was built with. A newer PiShip does not move an installed release to another Pi: a new Pi version arrives with a new release, installed by `update`.

`compatibility/pi.json`, and its copy in `@piship/core` that the compatibility suite checks for equality, list every Pi version PiShip recognizes and the status of each surface: `personal` `supported`, and `managed`, `governance`, and `lifecycle` `candidate` for every listed version today (the terms are defined at the top of this page). A release is recognized while its Pi is in the matrix, so a version stays listed after it stops being the pin. The status of a surface is evidence, and it is never carried to a new Pi version without saying so: a surface "carried over" from an earlier Pi is recorded as carried over, with the evidence that is still pending.

### Upgrading Pi

A Pi upgrade is its own change, with its own section on this page, and follows these steps:

1. Read upstream's changelog and compare the public `.d.ts` files of every package PiShip imports. List what changed for an export, event, or option PiShip uses, and what changed in behavior (defaults, files Pi writes, environment variables it reads, network requests it makes).
2. Move the exact pin: `packages/pi/package.json`, the root `overrides`, and `PI_SIBLING_PINS`. Regenerate `package-lock.json` and review every changed package: its version, `resolved`, and `integrity` (the release gate refuses a package without one), whether it has a lifecycle script (`REVIEWED_INSTALL_SCRIPTS` names the reviewed ones), and `npm audit`.
3. Add the version to `compatibility/pi.json` and to the copy in `@piship/core`, keeping every earlier entry so releases built on them are still recognized. Set each surface to what the evidence supports, and say where a status is carried over.
4. Run `npm run test:compatibility` and the unit tier. The compatibility suite asserts each seam individually, so a renamed export or a changed behavior fails there first. A failure is fixed in `packages/pi` with a regression test, or upstream; the pin does not move past a failing seam.
5. Write the "Upgrade to Pi X" section: matrix, packaging and sibling pin, lock and dependencies, install scripts, API diff, and each behavior change with what a distribution owner or user must do about it.
6. Run Release qualification on the exact release commit. No release states a Pi version as qualified before that run has passed, and the [status page](status.md) records it.
7. Distribution owners then set `runtime.pi` to the new pin, add the new version to the `pi` list of each `certified` resource they reviewed, run `piship validate`, `piship lock`, and `piship diff` against the previous lock, and rebuild ([agent setup](agent-setup.md#9-upgrade-an-existing-distribution)).

### Upstream seams

A seam is a public Pi API, event, or option that PiShip depends on to govern a session. The compatibility suite asserts each seam against the pinned Pi, and the runtime seam table (`RUNTIME_SEAMS` in `@piship/policy`) records, for each governed action, whether Pi exposes a seam that can prevent it. The table is static data because Pi has no capability discovery API, and the suite proves it.

- An action without a seam is reported `unsupported` and never `enforced`; a managed rule that denies or asks for it is refused unless the owner acknowledges it ([enforcement status](manifest.md#enforcement-status)).
- A missing or awkward seam is worked around only in `packages/pi`, through public exports, and every workaround has a regression test that fails when the seam changes. The workaround is listed in the table under "Public API used" above.
- A generic runtime improvement is proposed upstream in Pi, not carried here. When upstream adds a seam, the table changes only after the compatibility suite proves it on the pinned Pi.

### Unsupported semantics

These are outside the contract, in any PiShip release: a Pi version outside the matrix; a Pi private or internal path; Pi's built-in extensions (`builtin:*`) in a PiShip session; Pi's own `models.json`, `auth.json`, extension discovery, and `~/.pi` in a managed distribution; running Pi's interactive `/bug`, `/share`, or `/export` as a governed action (their gaps are under [Limits](security.md#limits)); and every action without a runtime seam (`web.request`, `browser.execute`, `agent.invoke`, `memory.*`, and `network.connect` without an enforced deny sandbox). Pi packages are supported as vendored, locked closures; a package that loads code or files outside its locked closure at run time is not.

## Upgrade to Pi 1.0.3

The pin moved from 1.0.2 to 1.0.3, reviewed on 2026-10-05. v0.9.0 and v0.9.1 stay on 1.0.2, so v0.9.1 was the production-validation baseline until v0.11.0, which ships on 1.0.3, replaced it ([baseline](status.md#v0110-production-validation-baseline)). Release qualification [run 37538011406](https://github.com/tc3oliver/piship/actions/runs/37538011406) on v0.11.0 is the first on 1.0.3. The upgrade checked and changed:

- **Matrix.** `compatibility/pi.json` and the copy in `@piship/core` list 1.0.3 beside 1.0.2, 1.0.0, and 0.87.1, with `personal` `supported` and `managed`, `governance`, and `lifecycle` `candidate`, the statuses of 1.0.2. The surfaces are carried over from 1.0.2, not earned again: the evidence for them is the compatibility suite and unit tier on 1.0.3, and the installed E2E of every target recorded in the Release qualification of [v0.11.0](status.md#v0110).
- **Packaging and the sibling pin.** Pi 1.0.3 still ships no `npm-shrinkwrap.json` and declares the same seven sibling packages (`chord`, `pi-agent-core`, `pi-ai`, `pi-codemode`, `pi-mcp`, `pi-telemetry`, and `pi-tui`, all `@earendil-works`) with `^1.0.3`. The root `package.json` `overrides` and `PI_SIBLING_PINS` in `@piship/pi` hold them at exactly 1.0.3, and the compatibility suite asserts the overrides, the npm lock, and the installed packages against that list as before.
- **Lock and dependencies.** Every third-party dependency Pi and its siblings declare is pinned to the same version as in 1.0.2 (`quickjs-wasi` 3.6.2, `brace-expansion` 5.0.12, `@anthropic-ai/sdk` 0.129.0, and the rest), so regenerating `package-lock.json` changed only the eight `@earendil-works` entries: their `version`, `resolved`, and `integrity` (each sha512 is the value the registry publishes), and the sibling ranges inside them. No transitive package moved, so the review of the 1.0.2 lock regeneration still stands. `npm audit` reports no vulnerabilities, with or without `--omit=dev` (2026-10-05).
- **Install scripts.** Unchanged: none of the eight Pi packages has a lifecycle script, and `REVIEWED_INSTALL_SCRIPTS` still names `@google/genai` 2.21.0, `esbuild` 0.28.2, and `protobufjs` 7.6.6, the same versions with the same reviewed scripts.
- **What changed in the packages.** The `chord`, `pi-agent-core`, `pi-codemode`, and `pi-telemetry` tarballs differ from 1.0.2 only in `package.json`; `pi-mcp` also in its changelog; `pi-tui` in its default keybindings; `pi-ai` and `pi-coding-agent` in the items below.
- **API.** The diff of the `.d.ts` files from 1.0.2 has no change to an export PiShip uses. The public changes are the `azure-openai-responses` provider renamed to `azure` in `pi-ai`'s `KnownProvider` and its provider modules, and the default keys in `pi-tui` and `pi-coding-agent` (see Azure and Keys below); the rest are helpers PiShip does not use (`refreshStoredOAuthCredential` in `pi-ai`, `detectInstallChange` in `pi-coding-agent`'s config module) and private members of `InteractiveMode`. The session manager and settings manager declarations are byte-identical to 1.0.2, and `CURRENT_SESSION_VERSION` stays 3. Both shims, the `continueRecent` assertions, and the compatibility test that no `builtin:*` extension loads pass unchanged.
- **Azure provider id (upstream breaking change).** Pi renamed the Azure provider from `azure-openai-responses` to `azure` and renamed its key in `auth.json`, `models.json`, and `settings.json`; the `AZURE_OPENAI_*` environment variables are unchanged. PiShip has no reference to either id. A managed launch is not affected, because it uses an in-memory credential store and no models file. A personal distribution reads Pi's own files under `<state>/agent`, so a user who signed in to Azure under 1.0.2 renames the key there or signs in again, and a personal manifest whose `models.allowed` names `azure-openai-responses/<model>` must name `azure/<model>`. PiShip does not migrate them. PiShip resumes the latest session automatically; a session that names the old provider falls back to another model and loses its prompt cache. Set `models.default` to the renamed model and include it in `models.allowed`.
- **Keys.** `Home` and `End` now always move the editor cursor to the start or end of the line, and the fullscreen transcript's top and bottom moved to `Ctrl+Home` and `Ctrl+End`. PiShip starts Pi in regular, not fullscreen, mode and defines no keybinding, so only the editor behavior is visible.
- **Output files.** Pi now creates every output file through one helper. A `!` command's full output keeps its name, `pi-bash-<16 hex>.log`, and its directory, the OS temp directory, so the compatibility test of that name and PiShip's cleanup of the files Pi recorded for the session still apply; the files are now created readable by the user only and exclusively (an existing path is never reused). Codemode's `image()` also saves each image it returns to a `pi-codemode-<hex>` file with the image's extension in the same directory and names the path in the result, like codemode's existing `.txt` file for long output. These files are Pi's own output, outside the filesystem policy that governs tool calls, and PiShip neither lists nor removes the codemode ones, as for the text files in 1.0.2.
- **Redaction and the crash handler.** The compatibility test of the interactive crash handler passes: Pi still prepends its `uncaughtException` listener before it binds extensions, adds no `unhandledRejection` listener, and writes its crash record from that handler, so `piship-redaction`'s own prepended listener still redacts the error before Pi prints or records it. Two Pi changes touch that handler. An error from a dead terminal (`EIO`, `EPIPE`, `ENOTCONN`, and now `ENOTTY`) exits with status 129 without a crash record, and `stdin` gets the same error listener as `stdout` and `stderr`, which rethrows any other error to the `uncaughtException` path. The first records nothing, and the second reaches the `uncaughtException` path where PiShip's listener already runs first.
- **Live install changes.** In the interactive error path, Pi 1.0.3 calls `detectInstallChange` and asks the person to restart when the payload package metadata was replaced or removed during the session.
- **Credentials.** Pi 1.0.3 persists a rotated OAuth refresh token even when the request that started the refresh was cancelled. PiShip's managed runtime holds the broker's credential in an in-memory store and no Pi sign-in, so this reaches only a personal distribution's own Pi sign-in.
- **Search tools, sessions, and models.** The tools manager and the session and settings managers are unchanged, so the search tool, session resume, and Pi defaults seams pass as before. The model runtime changes only in how it refreshes OAuth credentials, and the generated model catalog changes for Azure, Amazon Bedrock, OpenCode Go, OpenRouter, and Vercel AI Gateway; the model governance seams the compatibility suite pins pass unchanged.

## Upgrade to Pi 1.0.0

The pin moved from 0.87.1 to 1.0.0 ([#176](https://github.com/tc3oliver/piship/issues/176) is resolved). v0.7.1 stays on 0.87.1; v0.8.0 and v0.8.1, the latter the [previous baseline](status.md#v081-previous-production-validation-baseline), are on 1.0.0. The upgrade checked and changed:

- **Matrix.** `compatibility/pi.json` and the copy in `@piship/core` list 1.0.0 beside 0.87.1, each with `personal` `supported` and `managed`, `governance`, and `lifecycle` `candidate`. 0.87.1 stays so that releases built on it are still recognized; the launcher runs only the pinned 1.0.0. The Release qualifications of v0.8.0 and v0.8.1 ran on 1.0.0; the earlier ones on the [status page](status.md#recorded-evidence) ran on 0.87.1.
- **Redaction map (#176).** `AssistantMessage.thinkingLevel`, new in Pi 1.0 and optional, is the Pi thinking level the agent loop requested. It is classified `metadata` in `packages/pi/src/launch/redaction.ts`, beside `providerThinkingLevel`.
- **Built-in extensions.** Pi 0.99 and 1.0 add the built-in extensions `builtin:mcp`, `builtin:codemode`, `builtin:tool-search`, and `builtin:llama`. They are not loaded in PiShip sessions: only Pi's CLI adds them. PiShip builds sessions through the SDK with `noExtensions: true` and its own extension factories, and a compatibility test asserts that no `builtin:*` extension loads. A tool run through an extension's `ctx.executeTool` still emits `tool_call`, which PiShip's policy hook decides.
- **Shell result.** The governed `bash` follows Pi 1.0's result: it returns Pi's `structuredContent` (`output`, up to 1 MiB, and when it is longer its first and last 512 KiB; `truncated`; `full_output_path` when the output was truncated and saved; `exit_code`; `wall_time_seconds`), which codemode scripts receive, and a non-zero exit returns an `isError: true` result instead of throwing. The full output file still lives in PiShip's session-owned output store ([security](security.md#tools-shell-and-plan-mode)).
- **Pi defaults.** The switches above are new in this upgrade. Without them Pi 1.0 checks pi.dev for a newer version, reports the session to pi.dev as a fresh install (the in-memory settings are new on every launch), writes its crash log and downloads `fd` and `rg` under `~/.pi/agent`, and starts in fullscreen.
- **Lock integrity.** Pi 1.0's `npm-shrinkwrap.json` omits `integrity` for its own seven packages (`chord`, `pi-agent-core`, `pi-ai`, `pi-codemode`, `pi-mcp`, `pi-telemetry`, and `pi-tui` under `@earendil-works`). The npm lock records the registry's published sha512 for them, which `npm ci` verifies, because the release gate refuses a package without integrity ([artifact contract](release/artifact-contract.md#known-limitations)). The next Pi upgrade must re-check this.
- **Dependencies.** `brace-expansion` is still 5.0.9 in Pi 1.0.0's shrinkwrap, so the reviewed exception of [#129](https://github.com/tc3oliver/piship/issues/129) applied unchanged until the [upgrade to Pi 1.0.2](#upgrade-to-pi-102) removed it.
