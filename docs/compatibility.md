# Pi compatibility

`@piship/pi` pins `@earendil-works/pi-coding-agent` to exactly `1.0.0` through its public package entrypoint. The launcher runs only the pinned version. `compatibility/pi.json` and its copy in `@piship/core` also list `0.87.1`, the Pi of v0.7.1, with the same surface statuses, so a release built on it is still recognized. Node.js 22.19.0 or newer is required. No other PiShip package may directly depend on or import Pi. The committed npm lock fixes transitive package versions; the distribution lock records their npm integrity values, and a release fails when a downloaded package has none.

`compatibility/pi.json` reports status per surface. The current status of each surface, and the CI runs that back it, are kept in one place: [project status](status.md). This page defines the terms and the Pi integration contract. `candidate` means local public-API and artifact checks pass while the complete target matrix or live evidence remains pending. `supported` requires a branded install, real Pi startup, declared TypeScript extension, safe tool path, session resume, inspection, diagnostics, and uninstall on each advertised OS/CPU target.

The production-validation baseline is v0.8.1: tag `v0.8.1` at commit `d069104`, with Pi 1.0.0, Node.js 22.19.0 or newer, and the targets `linux-x64`, `darwin-arm64`, and `win32-x64`. [Release qualification run 37127974973](https://github.com/tc3oliver/piship/actions/runs/37127974973) passed on that exact commit, and its six attested archives are the [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.8.1). Details are on the [status page](status.md#v081-production-validation-baseline). It replaced v0.8.0, tag `v0.8.0` at commit `8550282` on the same Pi, which stays documented as the [previous baseline](status.md#v080-previous-production-validation-baseline); v0.7.1, tag `v0.7.1` at commit `bd4bc09` on Pi 0.87.1, is an [earlier one](status.md#v071-previous-production-validation-baseline).

## Personal surface

`compatibility/pi.json` marks Pi 1.0.0 (and 0.87.1) **supported for the portable personal surface** on Ubuntu x64, macOS arm64, and Windows x64 with Node 22.19.0. The surface was first qualified by a [three-target run](https://github.com/tc3oliver/piship/actions/runs/36345041538) of build, installed E2E, and public-API compatibility for the v0.1 `piship/v1alpha1` personal example; a local macOS arm64 PTY run also opened the real interactive TUI. The personal example has since moved to `piship/v1alpha5`, and its installed E2E is now part of the nightly and manual Portable E2E rather than a pull request gate; the [status page](status.md#recorded-evidence) records the latest result for the current commit. This status does not claim a live authenticated model request or other CPU architectures.

## Managed surface

Managed access (`piship/v1alpha2`) is a **candidate** on Pi 1.0.0 and 0.87.1. It is verified on the pinned public API with deterministic local fixtures: a loopback OIDC provider, `http-broker`, and OpenAI-compatible gateway that auto-approve sign-in. Tests cover login, credential acquisition, refresh, gateway rejection and renewal, model governance, streamed text, a tool-call round trip, cancellation, session resume, `config explain`, `doctor`, logout, and the personal `local-secret` and `none` modes. These fixtures prove PiShip's contracts. Beyond them, the Reference E2E runs the AcmeCode reference distribution on Ubuntu against the [enterprise reference stack](../examples/enterprise-reference/README.md): sign-in on a real Keycloak, a credential from the reference broker, and model requests through a real LiteLLM gateway to a deterministic mock upstream. The platform secret stores are live in CI: the `CI` check job runs the secret-store test against macOS Keychain, Windows Credential Manager, and the Linux Secret Service (GNOME Keyring) on every pull request, and `managed-clean-machine`, `user-switching` (its `system` variant) and `lifecycle-secret-store` use the live store on every Portable E2E target (`managed` and `headless` use the file store).

Still pending:

- Sign-in at a production identity provider and inference through a production gateway; the reference stack stands in for both.
- A model request to a real model provider in any automated tier. The gateway's upstream in Reference E2E is a mock, and the personal flows send their request to a stand-in model server. The manual `Live provider` workflow sends one request from AcmeCode through the reference LiteLLM to a real provider; [run 36877709332](https://github.com/tc3oliver/piship/actions/runs/36877709332) passed on `main` at `9e458f0` ([status](status.md#after-v071-on-main)). That is manual evidence for the reference stack, not for a company's identity provider or gateway.
- Installed E2E for the managed surface on all three targets is recorded for v0.8.1, tag `v0.8.1` at commit `d069104`, in [Release qualification run 37127974973](https://github.com/tc3oliver/piship/actions/runs/37127974973) ([status](status.md#v081)), not for any later commit; it must be re-run on each release candidate.

## Governance surface

Governance (`piship/v1alpha3` and later) is recorded as the `governance` surface with status **candidate** on Pi 1.0.0 and 0.87.1 in `compatibility/pi.json`: it has CI and Portable E2E evidence on Linux, macOS, and Windows, but no live company services. The end-to-end governance test drives a real Pi session with scripted tool calls from the local fixture gateway and checks Plan mode (only `read` and `ask_user` run; MCP tools are refused before reaching the server), MCP policy in Build mode (a denied tool is never offered or sent), project trust and symlinked instruction imports, certified integrity, user and project rule precedence in `policy explain`, sandboxed Build-mode commands, a required audit sink that fails the launch, and metadata-only audit content.

A release of a distribution that declares governance, which every `piship/v1alpha3` or later manifest does, records the `governance` surface in `release.json` and counts it toward the release's compatibility status. Still missing before `supported`: live company services (identity provider, gateway, audit sink) and a Windows sandbox adapter.

## Production lifecycle surface

The v0.4 lifecycle (`piship/v1alpha4`) is implemented on Pi 1.0.0 (and 0.87.1) and recorded as the `lifecycle` surface with status `candidate` in `compatibility/pi.json` ([status](status.md)). `@piship/core` carries a copy of the matrix, and the compatibility suite checks that the two are equal: `piship release` refuses a Pi version that is not in it, records in `release.json` the weakest of the distribution's deployment surface, the `governance` surface when the distribution declares governance, and the `lifecycle` surface (so releases currently record `candidate`), and `update` refuses a release that records its Pi version as unsupported. A Pi upgrade must therefore update `compatibility/pi.json` and that copy together.

Releases are built only for `linux-x64`, `darwin-arm64`, and `win32-x64`. The lifecycle E2E installs a release of the managed demo from its archive with the shipped install script, checks that the release payload matches `piship build` output, signs in against the local fixtures, keeps a session across an update through a signed loopback channel, rejects a tampered archive, altered metadata, and replayed metadata, rolls back and resumes the session, refuses credentials revoked server-side until the user signs in again, confirms no credential remains in state or install directories and that `~/.pi` is untouched, and uninstalls while keeping state. On Windows it runs the demo with the sandbox optional. The lifecycle E2E is part of the nightly and manual Portable E2E. The manually dispatched Release candidate workflow adds per-target reproducibility, fresh-job verification, and attestation checks for the demo and the personal example, and runs the installed personal release's offline `--smoke` and `doctor`. Recorded results are on the [status page](status.md#recorded-evidence); see also [supported platforms](release/owner-workflow.md#supported-platforms).

## Public API used

PiShip uses the public SDK entrypoint: `createAgentSessionRuntime`, `createAgentSession`, `DefaultResourceLoader`, `ModelRuntime`, `SessionManager`, `SettingsManager`, `InteractiveMode`, `createReadTool`, `createReadToolDefinition`, `createWriteToolDefinition`, `createEditToolDefinition`, `createBashToolDefinition`, `createLocalBashOperations`, `VERSION`, and the `AgentSessionServices`, `CreateAgentSessionRuntimeFactory`, and `InlineExtension` types.

The managed runtime calls `ModelRuntime.create` with an in-memory credential store and no models file, then `ModelRuntime.registerProvider` for the declared gateway. Governance replaces these public methods on the `ModelRuntime` instance PiShip creates: `getModel`, `getModels`, `getAvailable`, `getAvailableSnapshot`, `checkAuth`, `getAuth`, `stream`, `streamSimple`, `complete`, `completeSimple`, `login`, and `setRuntimeApiKey`. An inline `piship-governance` extension listens to `message_end`, to detect credential rejections, and to `model_select`, to update the enterprise context. An inline `piship-redaction` extension, loaded last in every launch, returns a replacement from `message_end` whose provider error text is redacted; Pi keeps and persists the replacement in place of the original message, which the compatibility test checks against a session file on disk. At `session_start` it also prepends an `uncaughtException` listener that redacts the error in place; this relies on Pi's interactive mode registering its own crash handler (with `process.prependListener`, before it binds extensions) and adding no `unhandledRejection` listener, which the compatibility test pins together with a crash record written by that handler. The compatibility test fails if any of these methods disappears, so an upgrade cannot silently bypass governance.

Governance additionally depends on these public exports and extension hooks: `createAgentSession` options `noTools: "builtin"` and `customTools`; `createReadToolDefinition`, `createWriteToolDefinition`, `createEditToolDefinition`, and `createBashToolDefinition` with their `operations` overrides; `createLocalBashOperations`; `truncateTail`, `formatSize`, and `DEFAULT_MAX_BYTES`, which the governed `bash` execute uses to keep Pi's display tail and footer; the `tool_call`, `user_bash`, `before_agent_start`, `before_provider_request`, `session_start`, and `session_shutdown` events, and the session entries' `bashExecution` messages with their `fullOutputPath`; `registerTool` and `registerCommand`; and the extension context's `hasUI` and `ui` dialogs. Governed tools replace Pi's built-in tools of the same names. The compatibility suite asserts each of these seams individually, so a rename or behavior change fails it first: each tool definition routes file and command access through its `operations` override and nothing else; `createLocalBashOperations` runs a command and reports its exit code; the resource loader loads only the explicit paths when ambient discovery is off; each extension event and registration is delivered in a headless session against the loopback fixture gateway; a `tool_call` block prevents the tool from running; `user_bash` operations are used for `!` commands, and Pi records a `!` command's `pi-bash-<id>.log` path in the session entries that `session_shutdown` hands to extensions; the governed `bash` execute produces the same results (the text, Pi's `structuredContent`, and an `isError` result for a non-zero exit, as Pi 1.0 does), live updates, and failures as Pi's, apart from the saved path and the measured wall time, and runs the command, cwd, timeout, and environment Pi would; a provider registered with an in-memory credential store is listed and then narrowed by PiShip's model governance; and a persisted session resumes through `createAgentSessionRuntime`. The extension context's UI dialogs are checked for presence only, since the suite has no interactive UI.

Session resume works around three gaps of Pi 1.0.0's `SessionManager.continueRecent()`: it resumes a file with a malformed line or a truncated last record without a signal (and appends a newline to the latter), reads a file of any size to its end, and lets two processes append to one file ([sessions](architecture.md#sessions)). PiShip therefore selects the most recent session with the same rule (the newest `*.jsonl` whose header, found in the first MiB, names the project), checks and owns it, and opens it with `SessionManager.open(path, sessionDir, cwd)` or starts one with `SessionManager.create(cwd, sessionDir)`. It relies on the runtime factory being called again with the new `SessionManager` for `/new`, `/resume`, and forks, and on a `session_before_switch` handler cancelling a resume. The compatibility suite asserts each of these, and that `continueRecent` still drops a malformed line and completes a truncated record, so a Pi release that reports damaged sessions itself, loads them lazily, or locks them fails there and the workaround can be retired.

Every launch sets Pi's own startup and network switches, which Pi reads from its settings and environment and not from the SDK options PiShip passes (`packages/pi/src/launch/pi-defaults.ts`; the effects are listed under [Secrets](security.md#secrets)). The environment variables are `PI_SKIP_VERSION_CHECK=1`, `PI_TELEMETRY=0`, `PI_CODING_AGENT_DIR=<state>/agent`, and, for a managed distribution only, `PI_OFFLINE=1`; a managed launch sets them again after it has removed the inherited `PI_` variables. The in-memory settings are `enableInstallTelemetry: false`, `lastChangelogVersion` set to Pi's `VERSION`, `quietStartup: true`, and `tuiMode: "regular"`. A unit test reads the settings back through Pi's `SettingsManager`, and a Pi upgrade re-checks each switch.

There are no Pi private imports or source patches. A future Pi upgrade must update the exact pin, npm lock, matrix, and compatibility tests together, then pass the Portable E2E on every advertised target. A temporary shim needs an owner, an expiry condition (normally the Pi release that makes it unnecessary), a linked upstream issue or pull request when the gap belongs in Pi, and an automated regression test.

Two compatibility shims are registered for Pi 1.0.0; both were re-verified on it at the upgrade from 0.87.1 and kept. Both use only Pi's public exports, but depend on behavior Pi does not document as a contract. Owner for both: the PiShip maintainers. Expiry for both: the next Pi upgrade, which must re-verify each shim and then remove it, keep it with a new expiry, or replace it by a recorded decision. No upstream issue is filed yet; one is linked here when the gap is reported to Pi.

| Shim | What it relies on | Regression test |
| --- | --- | --- |
| Dispose hook (`packages/pi/src/commands/dispose-hook.ts`) | Pi ends an interactive session in `InteractiveMode.shutdown()` by awaiting `runtimeHost.dispose()` and then calling `process.exit(0)`, so the governance session must end inside `dispose()`, and a failed teardown can change the exit code only by replacing `process.exit`. | `packages/pi/src/compatibility.test.ts` pins the await-then-exit order in Pi's shipped source |
| Session file check (`packages/pi/src/launch/session-file.ts`) | Pi's on-disk session format: the header, entry `id` and `parentId`, and the fields of the entry types it knows (`firstKeptEntryId`, `targetId`, `fromId`). A damaged file is refused before Pi would load or rewrite it. An entry type the check does not know is accepted as long as it has an ID and a valid parent, so a newer Pi's entries do not make a valid session refused. | `packages/pi/src/launch/session-file.test.ts`, including an unknown entry type |

## Upgrade to Pi 1.0.0

The pin moved from 0.87.1 to 1.0.0 ([#176](https://github.com/tc3oliver/piship/issues/176) is resolved). v0.7.1 stays on 0.87.1; v0.8.0 and v0.8.1, the latter the [production-validation baseline](status.md#v081-production-validation-baseline), are on 1.0.0. The upgrade checked and changed:

- **Matrix.** `compatibility/pi.json` and the copy in `@piship/core` list 1.0.0 beside 0.87.1, each with `personal` `supported` and `managed`, `governance`, and `lifecycle` `candidate`. 0.87.1 stays so that releases built on it are still recognized; the launcher runs only the pinned 1.0.0. The Release qualifications of v0.8.0 and v0.8.1 ran on 1.0.0; the earlier ones on the [status page](status.md#recorded-evidence) ran on 0.87.1.
- **Redaction map (#176).** `AssistantMessage.thinkingLevel`, new in Pi 1.0 and optional, is the Pi thinking level the agent loop requested. It is classified `metadata` in `packages/pi/src/launch/redaction.ts`, beside `providerThinkingLevel`.
- **Built-in extensions.** Pi 0.99 and 1.0 add the built-in extensions `builtin:mcp`, `builtin:codemode`, `builtin:tool-search`, and `builtin:llama`. They are not loaded in PiShip sessions: only Pi's CLI adds them. PiShip builds sessions through the SDK with `noExtensions: true` and its own extension factories, and a compatibility test asserts that no `builtin:*` extension loads. A tool run through an extension's `ctx.executeTool` still emits `tool_call`, which PiShip's policy hook decides.
- **Shell result.** The governed `bash` follows Pi 1.0's result: it returns Pi's `structuredContent` (`output`, up to 1 MiB, and when it is longer its first and last 512 KiB; `truncated`; `full_output_path` when the output was truncated and saved; `exit_code`; `wall_time_seconds`), which codemode scripts receive, and a non-zero exit returns an `isError: true` result instead of throwing. The full output file still lives in PiShip's session-owned output store ([security](security.md#tools-shell-and-plan-mode)).
- **Pi defaults.** The switches above are new in this upgrade. Without them Pi 1.0 checks pi.dev for a newer version, reports the session to pi.dev as a fresh install (the in-memory settings are new on every launch), writes its crash log and downloads `fd` and `rg` under `~/.pi/agent`, and starts in fullscreen.
- **Lock integrity.** Pi 1.0's `npm-shrinkwrap.json` omits `integrity` for its own seven packages (`chord`, `pi-agent-core`, `pi-ai`, `pi-codemode`, `pi-mcp`, `pi-telemetry`, and `pi-tui` under `@earendil-works`). The npm lock records the registry's published sha512 for them, which `npm ci` verifies, because the release gate refuses a package without integrity ([artifact contract](release/artifact-contract.md#known-limitations)). The next Pi upgrade must re-check this.
- **Dependencies.** `brace-expansion` is still 5.0.9 in Pi 1.0.0's shrinkwrap, so the reviewed exception of [#129](https://github.com/tc3oliver/piship/issues/129) applies unchanged.
