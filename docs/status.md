# Project status

This page is the single source of truth for what current `main` supports and what evidence backs each claim. Other documents describe how things work and link here for status. When this page and another document disagree, this page wins; please report the mismatch.

v0.7.0 is published as a [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.7.0): the six example release archives from its Release qualification run, unchanged, with their SHA-256 files and GitHub artifact attestations. There is no npm release and no signed update channel operated by the project; no release key is pinned. v0.7.1 is published the same way as a [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.7.1) and is an earlier baseline. v0.8.0 is published the same way as a [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.8.0) and is an earlier baseline. v0.8.1 is published the same way as a [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.8.1) and is an earlier baseline. v0.9.0 is published the same way as a [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.9.0) and is the [previous baseline](#v090-previous-production-validation-baseline). v0.9.1 is published the same way as a [GitHub pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.9.1) and is the [production-validation baseline](#v091-production-validation-baseline), replacing v0.9.0. Every milestone below is a preview milestone.

## v0.9.1 production-validation baseline

v0.9.1 is the one PiShip baseline a production consumer pins for production validation, replacing [v0.9.0](#v090-previous-production-validation-baseline). A production consumer pins tag `v0.9.1` and installs its qualified release artifact directly; it does not track `main`. It is a patch milestone that collects the changes made on `main` after v0.9.0, on the same schemas and the same Pi; the [changelog](../CHANGELOG.md#v091) lists them.

- Qualification: tag `v0.9.1` is commit `a97ba4302f56e3a59464434084f38b2af9556123` (the squash of #215). [Release qualification run 37297400038](https://github.com/tc3oliver/piship/actions/runs/37297400038) passed on that exact commit, every job on its first attempt: CI on Ubuntu, macOS, and Windows, CodeQL, Portable E2E, Reference E2E, and Release candidate (two byte-identical builds per target, attestation, `verify-release`, tamper rejection, and install with the shipped script on fresh runners). The [pre-release](https://github.com/tc3oliver/piship/releases/tag/v0.9.1) carries that run's six attested archives (`acmecode` and `mypi` for each target), with their SHA-256 files; the digests are [below](#v091-archives) ([recorded evidence](#v091)).
- Changes since v0.9.0:
  - MCP plain HTTP and identity headers (#212): a `streamable-http` server may opt in to plain HTTP to a private or internal host with `httpTransport: http-allowed`, and may receive a claim of the signed-in OIDC identity as a request header with `headers` ([manifest](manifest.md#mcp-plain-http-and-identity-headers-v1alpha6)).
  - Plain HTTP to internal endpoints (#213): the gateway, the credential broker, the OIDC issuer, audit sinks, and the sandbox may each opt in to plain HTTP to a private or internal host with `httpTransport: http-allowed`; every other host keeps the loopback-only rule, and an opt-in request an inherited public `HTTP_PROXY` would carry is refused ([manifest](manifest.md#plain-http-to-internal-endpoints-v1alpha6), [security](security.md#plain-http-to-internal-endpoints)).
  - Bundled search tools (#214): `runtime.searchTools: { mode: bundled }` pins `fd` and `rg` per release target in the lock and ships them in the payload, so Pi's find and grep tools and `@` completion work on a managed machine without the network ([manifest](manifest.md#bundled-search-tools-v1alpha6)). The branded command now sets Pi's agent directory before Pi loads, so Pi no longer uses `~/.pi/agent/bin`.
  - Docs (#211): the agent setup guide asks its questions in batches, with a question tool when the agent has one.
  - Dependencies (#206): `undici` 8.11.2 and `@biomejs/biome` 2.5.15.
- PiShip version: `0.9.1` (every `@piship/*` package and `PISHIP_VERSION` in [`compatibility.ts`](../packages/core/src/compatibility.ts)); every example is relocked with it.
- Schemas: unchanged from v0.9.0 (manifest `piship/v1alpha6`, lock `piship-lock/v1alpha6`). The new fields (`httpTransport`, MCP `headers`, `runtime.searchTools`) are additive and optional, and no schema id changes ([version map](#version-map)).
- Pinned Pi: `@earendil-works/pi-coding-agent` 1.0.2, unchanged.
- Open issues at v0.9.1: the same two as at v0.9.0, [#64](https://github.com/tc3oliver/piship/issues/64) and [#139](https://github.com/tc3oliver/piship/issues/139), both upstream Pi. These two are the complete list of open issues; every other issue cited on this page is closed.
- Update channel: the project operates no signed update channel, and the example distributions pin no bootstrap trust root, so the published archives are update-disabled and cannot update through a channel. Key custody belongs to each distribution owner ([trust root](release/trust-root.md#examples)). A production consumer pins and installs the exact qualified artifact directly, and compares its SHA-256 and pinned update keys with the values the distribution owner published ([distribution bootstrap](release/trust-root.md#distribution-bootstrap)).
- Production evidence: the manual `Live provider` workflow has passed with a real upstream model provider through the reference stack ([after v0.7.1](#after-v071-on-main)). There is still no validation against a real company identity provider or company gateway in production; the [production validation protocol](production-validation.md) says how it is run and what a report may carry.
- Supported production-validation platforms: `linux-x64`, `darwin-arm64`, and `win32-x64` with Node.js 22.19.0 or later (qualified on Node 22.19.0), the release targets the Release candidate builds and the targets in [compatibility](compatibility.md); npm 11 or later on the machine that runs `piship lock` for a distribution that declares Pi packages. Native Windows has no sandbox adapter: a distribution that requires the sandbox fails closed there with `SANDBOX_UNAVAILABLE` ([sandbox backends](#sandbox-backends)).

## On `main` after v0.9.1

`main` has moved past v0.9.1. These changes are not in v0.9.1, the production-validation baseline, and are not released; the [changelog](../CHANGELOG.md#unreleased) lists them.

- Pi 1.0.3: `main` pins `@earendil-works/pi-coding-agent` exactly at 1.0.3, with its seven sibling packages pinned exactly. `compatibility/pi.json` and the copy in `@piship/core` list 1.0.3 beside 1.0.2, 1.0.0, and 0.87.1 with the same four surface statuses (`personal` `supported`; `managed`, `governance`, and `lifecycle` `candidate`), and the launcher runs only 1.0.3. v0.9.0 and v0.9.1 stay on 1.0.2. The statuses of 1.0.3 are carried over from 1.0.2, not earned again, and the production-validation baseline stays v0.9.1 on Pi 1.0.2 until a release is qualified on 1.0.3.

## Known limits and non-claims

Limits of v0.9.1 as shipped, with earlier releases named where a bullet says so, each checked against the code or document it cites. None of them is claimed as handled. Only the issues listed under the [baseline](#v091-production-validation-baseline), [#64](https://github.com/tc3oliver/piship/issues/64) and [#139](https://github.com/tc3oliver/piship/issues/139), are open; a closed issue cited here records where a limit was decided, not open work.

- Shell output is stopped at 64 MiB, but in v0.7.0 Pi still writes the complete output to its own `pi-bash-*.log` file in the OS temp directory: PiShip does not remove it after the session, and a full temp filesystem while Pi writes it is not contained. After v0.7.0 the agent's `bash` tool keeps its full output in a session-owned directory removed at close, and a full temp filesystem there is contained. A user's `!` command still goes through Pi's file: PiShip removes the files Pi recorded for the session at close and keeps the command's output within the free temp space, but a temp filesystem that fills anyway while Pi writes it is not contained, and a crash leaves the file. Closing that needs a change in Pi upstream (#64; [security](security.md#tools-shell-and-plan-mode)).
- `--smoke-model` classifies a failed request by the gateway's status, an aborted request as `REQUEST_CANCELLED`, and a managed endpoint's request that got no answer (refused or reset connection, DNS failure, deadline) as `GATEWAY_UNREACHABLE`. A stream that failed after it started, and a Pi-native provider's request that got no answer, are still `GATEWAY_PROTOCOL_ERROR`: Pi's message keeps no structured transport error, and PiShip owns the `fetch` only for a managed endpoint (kept as a known limit when #85 closed; [inference](inference.md#gateway-status)).
- On Windows, a governed child that writes the launcher's startup-failure marker to stderr has that output dropped and its exit reported as a startup failure (a low-severity review finding on #104, not tracked by an open issue).
- On Windows, the Job Object helper is compiled from C# for every governed child, which adds startup time to each one (a low-severity review finding on #104, not tracked by an open issue).
- On Windows, the request that carries a child's file, arguments, working directory, and approved environment travels base64-encoded in one environment variable of the launcher, so it is bound by Windows' 32,767-character limit for a variable (a low-severity review finding on #104, not tracked by an open issue).
- The native sandbox probe connects to 1.1.1.1:443 and to a host loopback listener in `deny` mode as negative probes: each must fail, and the probe never requires an address to be reachable. The positive control is in the boundary tests, where a sandbox with the network allowed does reach the loopback listener ([network denial](sandbox.md#network-denial)).
- E2B and CubeSandbox network denial is backend-attested, never verified; Kubernetes Agent Sandbox claims none, and a required `deny` sandbox on it fails closed.
- The reference container sandbox declares no network probe in v0.7, so its network denial is attested.
- Bubblewrap cannot guard a protected git file that does not exist yet, so git control is `not-verified` under it in every regular repository ([sandbox](sandbox.md#protected-git-paths)); Seatbelt can guard a missing file.
- The `Live provider` workflow is manual, uses a paid provider key held in the protected `live-provider` environment, and is never part of Release qualification. Its passing runs ([after v0.7.1](#after-v071-on-main)) show one model request from AcmeCode through the reference Keycloak, broker, and LiteLLM to a real upstream provider. They are not evidence for a company identity provider or gateway, and no such validation exists yet.
- PiShip refuses state, install, and bin homes that are equal or nested in one another, so an install home that contains the bin home is rejected with `CONFIG_INVALID`.
- Windows has no evidence for the host-side check of a `shared` or `synchronized` workspace. Of the 103 workspace tests ([`workspace.test.ts`](../packages/sandbox/src/workspace.test.ts) and [`governance-workspace.test.ts`](../packages/pi/src/governance-workspace.test.ts)), 63 are POSIX-only and skip on Windows: the two-way sentinel, the git control file checks, the sentinel location, the propagation and validity windows, and the governed session's workspace check. 7 more need a native sandbox, which Windows does not have. The 33 that run there cover declaration handling and helper logic. The only run against a real shared workspace is the reference container sandbox, on Ubuntu.
- Two security E2E files cover less on Windows than on Linux and macOS. [`lifecycle-credentials`](../tests/e2e/lifecycle-credentials.test.ts) locks the file store by removing POSIX permissions, which Windows ignores. So on Windows it does not test logout with a locked store, the discarded credential and identity records that logout leaves, or the rollback that clears them: logout runs with the store unlocked. [`security-sweep`](../tests/e2e/security-sweep.test.ts) runs the demo with the sandbox optional on Windows. It skips the four `bash` tool steps: reading a stored secret and the credential metadata with `cat`, listing the state directory, and a long output that Pi saves to a temp file. It also does not check that the run used its temp directory. Both files still pass on Windows and sweep for leaked secrets there.
- A system clock set forward cannot be told from a suspend and counts as elapsed time: the sandbox workspace check and a Kubernetes claim come due or expire early ([sandbox](sandbox.md#the-workspace-check)).
- Releases up to v0.8.1 ship `brace-expansion` 5.0.9, which Pi 0.87.1 and 1.0.0 pin in their `npm-shrinkwrap.json`; it has two high advisories (GHSA-qhr7-859c-m2p7, GHSA-6j4f-fj2g-mc7p: local stack-exhaustion DoS from crafted nested brace patterns) and one moderate (GHSA-q2hr-2g5m-vwhr). Their example manifests allow the two high IDs as a reviewed exception until 2026-12-31. In v0.9.0 and v0.9.1, Pi 1.0.2 pins 5.0.12, which fixes them, so the example manifests carry no `allow` entries and the release vulnerability gate passes with no findings (#129, [upgrade to Pi 1.0.2](compatibility.md#upgrade-to-pi-102)).
- The branded command has no non-interactive prompt, print, or RPC mode: without a terminal the interactive command fails at once, and headless runs (CI, automation, a workload identity) use `--smoke`, `--smoke-model`, and the subcommands (#135).
- Fixed in v0.7.1: a stray file in the installed payload is named and `piship repair` restores the release (#136); a corrupt versioned state file no longer blocks update and rollback (#143); the lifecycle lock and launch gate record process identity and host (#144); adapter and custom sandbox calls have deadlines (#145); Kubernetes sandbox commands may run past 300 seconds and an unknown outcome is never retried (#146); proxy and CA failures name the proxy or the TLS chain (#148); login explains a busy port, a provider client error, and SSH (#149); `validate` catches configuration certain to fail at launch (#142). Still open: an identity or credential failure inside the TUI shows PiShip's action, but Pi still adds its own `/bug` hint, which no public Pi API can turn off (#139).
- The v0.7.x follow-ups tracked under #125 (#157 to #162) are fixed in v0.7.1, and #125 is closed.
- The project operates no signed update channel. Installation trust state, sequential root refresh, root / channel role separation, threshold multi-signatures, and emergency channel-key revocation are implemented in v0.8.0 and covered by its [Release qualification](#v080), and again by that of [v0.8.1](#v081); the remaining gaps are partial root signing across machines and external signers ([trust root gaps](release/trust-root.md#gaps-and-follow-ups)).
- In v0.8.0, v0.8.1, v0.9.0, and v0.9.1, some Pi 1.x behavior has no public Pi switch, and PiShip does not patch Pi: the terminal title is still "π" (Pi's `APP_TITLE`); the exit hint still says `pi --session-dir ... --session ...`; Pi still adds its `/bug` hint (#139); and the built-in `/share` command uploads the session file as a GitHub gist through the user's own `gh` CLI, a child process outside PiShip's in-process network policy, so a session can leave the machine that way in managed mode too ([security](security.md#limits)).
- Session export has no Pi seam for `/share`'s gist fallback or `/export`, so `session.export` `public` and `local` are `unsupported` in v0.9.0 and v0.9.1, and `support` is `unsupported` in personal mode, where Pi's `/bug` upload is open; the lock and `doctor` always report them ([security](security.md#limits)).
- A managed distribution runs Pi offline (`PI_OFFLINE=1`), so Pi downloads no `fd` or `rg`. From v0.9.1, a `piship/v1alpha6` distribution can bundle them with `runtime.searchTools: { mode: bundled }`: they are pinned per release target in the lock, shipped in the payload, and found by Pi before `PATH`, without the network ([bundled search tools](manifest.md#bundled-search-tools-v1alpha6)). Without it, and in v0.8.0, v0.8.1, and v0.9.0, they must be on `PATH` for `@` completion and Pi's find and grep tools. A personal distribution without bundled tools lets Pi download its own `fd` and `rg`; in v0.9.0 and earlier Pi put them, and looked for them first, in `~/.pi/agent/bin` despite PiShip's agent directory, because Pi fixes that directory when it is imported. From v0.9.1 the branded command sets the agent directory before Pi loads, so they go to `<state>/agent/bin` ([security](security.md#secrets)).

Product milestones and schema versions are separate. A milestone is a unit of project work; a schema version changes only when the manifest or lock format changes.

| Milestone | Theme | Manifest schema | Lock schema |
| --- | --- | --- | --- |
| v0.1 | Portable personal distribution core | `piship/v1alpha1` | `piship-lock/v1alpha1` |
| v0.2 | Managed access and configuration | `piship/v1alpha2` | `piship-lock/v1alpha2` |
| v0.3 | Governance and security baseline | `piship/v1alpha3` | `piship-lock/v1alpha3` |
| v0.4 | Production release lifecycle | `piship/v1alpha4` | `piship-lock/v1alpha4` |
| v0.5 | Gap closure across governance, access, supply chain, and the personal profile | `piship/v1alpha4` (unchanged) | `piship-lock/v1alpha4` (unchanged) |
| v0.6 (implemented, frozen and qualified at `ab3e7f2`) | Project consolidation | `piship/v1alpha4` (unchanged) | `piship-lock/v1alpha4` (unchanged) |
| v0.7 (v0.7.0 at `4994eee`, the squash of #165; v0.7.1 at `bd4bc09`, the squash of #174) | Enterprise integration and qualification | `piship/v1alpha4` (unchanged) | `piship-lock/v1alpha4` (unchanged) |
| v0.8 (v0.8.0 at `8550282`, the squash of #193; v0.8.1 at `d069104`, the squash of #203) | Pre-production trust and validation hardening | `piship/v1alpha5` | `piship-lock/v1alpha5` |

All six manifest schemas are still accepted and all are experimental; only `piship/v1alpha5` and `piship/v1alpha6` can build a release, and `piship migrate` takes an older manifest step by step to v1alpha6 ([migration](manifest.md#migration)). Every example uses `piship/v1alpha6`. The schema details live in [manifest](manifest.md); the history lives in the [changelog](../CHANGELOG.md); what comes next is in the [roadmap](roadmap.md).
