# Portable personal payload decision

v0.1 uses a directory payload, assembled on each target from package-owned build inputs with `npm ci --omit=dev`. Optional packages whose npm lock `os`/`cpu` exclude the target are then removed: npm installs every platform build inside a shrinkwrapped dependency, so Pi's 26 esbuild binaries would otherwise all ship. The exact source `piship.lock` is the payload's only distribution lock. The payload also contains `piship.yaml`, `package-lock.json`, PiShip package builds, Pi's published npm package and its production dependency closure, package metadata and assets, declared resources, `metadata/target.json`, and `metadata/inventory.json`. The inventory covers `piship.lock` and every other static payload file. It is copied as one unit at install. The payload includes a `piship.mjs` management entry, and a platform-specific command shim points at its `bin/<command>` entry. The same payload directory is the input for later signing, update, and rollback work; the installer does not reconstruct a second runtime.

Node.js 22.19.0 or newer is a documented, separately installed prerequisite. Bundling Node would enlarge the already substantial Pi dependency closure and add patch, signing, native binary, and per-target installer responsibility now. A separate Node prerequisite preserves normal npm handling of Pi's dynamic TypeScript extension loader and native/WASM dependencies. The installed shim checks that Node exists; the launcher checks its minimum version and the payload verifier rejects an OS/CPU mismatch. Neither silently downloads Node or Pi. Installation itself needs no separate runtime install step once Node is present.

The runtime is copied per distribution, with no shared mutable cache. This costs disk space but makes uninstall ownership and isolation explicit. On local macOS arm64 with Node 24.21.0, the assembled personal example occupies about 140 MB (about 427 MB before foreign-platform optional packages were removed), and its release archive is about 34 MB. Each supported target runs one fresh production-path build and the installed lifecycle. The Ubuntu qualification path also compares `metadata/inventory.json` from two clean assemblies of the same copied example, canonical lock, packaged build input, and target on the same commit. This proves equality of declared static file paths and SHA-256 content hashes for that target. The CI checkout supplies the clean source for release evidence. OS/CPU metadata is deliberately target-specific; archive timestamps, filesystem metadata, and cross-target hashes are not claimed equal.

The relocation check moves the payload outside the checkout, then runs the real branded Pi SDK smoke: the pinned Pi (1.0.0) initializes, the declared TypeScript extension and skill load from relocated resources, Pi's read tool reads the packaged manifest, and a Pi session persists. On every supported target the installed management entry continues to inspect, diagnose, launch, and uninstall after the original artifact and manifest directory are deleted. Ubuntu qualification also builds a second distribution through relocated PiShip tooling to prove build inputs travel with the package, and reinstalls at a new path to check retained session identity and isolation. The managed demo lifecycle (login, policy, resume, logout against local fixtures) also runs on every supported target; the personal `local-secret` and `none` access modes, which each need another full build, run on the Ubuntu qualification path. The package inventory includes runtime JavaScript, package metadata, assets, themes, images, WASM/native files when provided by the target npm resolution, jiti, and transitive dependencies. `package-lock.json` and its exact resolved package versions/integrities are in the payload and `piship.lock`. Build-time registry access may be needed; install and launch use only the payload and do not fetch packages.

Default install locations are user-writable and do not edit profiles. Install fails on existing app ID, command, payload, or state by default; `--use-existing-state` is the explicit adoption path for a retained state directory. Uninstall deletes the recorded shim and payload and keeps user state. A separate `purge <id> --yes` removes PiShip-owned state after uninstall, and `uninstall <id> --purge --yes` removes the install and the state in one command, so a user whose only PiShip is the installed release (its `piship.mjs`) can remove everything. Opaque external provider credentials are outside that ownership boundary and may require manual revocation.

The personal targets are Ubuntu x64, macOS arm64, and Windows x64 with Node 22.19.0, subject to current-head Portable E2E and Pi compatibility qualification; the [status page](status.md) records the current evidence. Other CPU architectures are not implied. Following the [CI evidence tiers](../AGENTS.md#ci-evidence-tiers), pull requests run build, unit tests, and (for relevant paths) Pi compatibility on all three targets; the full installed Portable E2E described here runs on all three targets nightly and through `workflow_dispatch`, and is not a pull request gate. No standalone binary, npm publication, signature, SBOM, or live authenticated request is claimed in v0.1; later milestones add release archives with an SBOM ([release](release.md)).
