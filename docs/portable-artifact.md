# Portable personal payload decision

v0.1 uses a directory payload, assembled on each target from package-owned build inputs with `npm ci --omit=dev`. The exact source `piship.lock` is the payload's only distribution lock. The payload also contains `piship.yaml`, `package-lock.json`, PiShip package builds, Pi's published npm package and its production dependency closure, package metadata and assets, declared resources, `metadata/target.json`, and `metadata/inventory.json`. The inventory covers `piship.lock` and every other static payload file. It is copied as one unit at install. The payload includes a `piship.mjs` management entry, and a platform-specific command shim points at its `bin/<command>` entry. The same payload directory is the input for later signing, update, and rollback work; the installer does not reconstruct a second runtime.

Node.js 22.19.0 or newer is a documented, separately installed prerequisite. Bundling Node would enlarge the already substantial Pi dependency closure and add patch, signing, native binary, and per-target installer responsibility now. A separate Node prerequisite preserves normal npm handling of Pi's dynamic TypeScript extension loader and native/WASM dependencies. The installed shim checks that Node exists; the launcher checks its minimum version and the payload verifier rejects an OS/CPU mismatch. Neither silently downloads Node or Pi. Installation itself needs no separate runtime install step once Node is present.

The runtime is copied per distribution, with no shared mutable cache. This costs disk space but makes uninstall ownership and isolation explicit. On local macOS arm64 with Node 24.21.0, the assembled personal example occupied about 429 MB before the current changes. Each supported target runs one fresh production-path build and the installed lifecycle. The Ubuntu qualification path also compares `metadata/inventory.json` from two clean assemblies of the same copied example, canonical lock, packaged build input, and target on the same PR HEAD. This proves equality of declared static file paths and SHA-256 content hashes for that target. The CI checkout supplies the clean source for release evidence. OS/CPU metadata is deliberately target-specific; archive timestamps, filesystem metadata, and cross-target hashes are not claimed equal.

The relocation check moves the payload outside the checkout, then runs the real branded Pi SDK smoke: Pi 0.87.1 initializes, the declared TypeScript extension and skill load from relocated resources, Pi's read tool reads the packaged manifest, and a Pi session persists. On every supported target the installed management entry continues to inspect, diagnose, launch, and uninstall after the original artifact and manifest directory are deleted. Ubuntu qualification also builds a second distribution through relocated PiShip tooling to prove build inputs travel with the package, and reinstalls at a new path to check retained session identity and isolation. The managed demo lifecycle (login, policy, resume, logout against local fixtures) also runs on every supported target; the personal `local-secret` and `none` access modes, which each need another full build, run on the Ubuntu qualification path. The package inventory includes runtime JavaScript, package metadata, assets, themes, images, WASM/native files when provided by the target npm resolution, jiti, and transitive dependencies. `package-lock.json` and its exact resolved package versions/integrities are in the payload and `piship.lock`. Build-time registry access may be needed; install and launch use only the payload and do not fetch packages.

Default install locations are user-writable and do not edit profiles. Install fails on existing app ID, command, payload, or state by default; `--use-existing-state` is the explicit adoption path for a retained state directory. Uninstall deletes the recorded shim and payload and keeps user state. A separate `purge <id> --yes` removes PiShip-owned state after uninstall. Opaque external provider credentials are outside that ownership boundary and may require manual revocation.

The supported personal targets are Ubuntu x64, macOS arm64, and Windows x64 with Node 22.19.0, subject to current-head portable E2E and Pi compatibility qualification. Other CPU architectures are not implied. PR CI and Pi compatibility run on all three targets; portable E2E runs on Ubuntu for PRs that may affect the distribution contract, and on all three targets for pushes to `main` and `workflow_dispatch` runs. No standalone binary, npm publication, signature, SBOM, or live authenticated request is claimed in v0.1.
