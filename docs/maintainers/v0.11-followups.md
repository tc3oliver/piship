# v0.11.0 follow-ups

What the v0.11 [security review](../security.md#v011-security-review) and the [qualification matrix](v0.11-qualification-matrix.md) leave for other pull requests or for the first qualification run. The tests below belong on the branches that introduce the code they test: the review read those branches (`v011/footprint` at `44034484`, `v011/contracts` at `78f42010`) and did not edit them. When a pull request lands, move its tests out of this file or delete the line.

## Tests to add on `v011/footprint` (dependency sharing and closure bundling)

1. **A changed shared file fails verification.** In `tests/e2e/developer-profile.test.ts` (or a unit test over a built fixture payload), change a file under `pi-packages/.shared/<name>@<version>-<digest>/` and one forwarding module beside a package's `package.json`; expect `doctor` and `verify-release` to report `INTEGRITY_FAILED` for each. The security review states this as a guarantee ("every file in the inventory") and no test names it.
2. **The SBOM and notices do not change when a closure is bundled.** `closure.test.ts` "bundles below the extension files and leaves them byte for byte" asserts that `package.json` and the license of a bundled dependency stay on disk, but not what `listPayloadPackages`, `generateSbom`, and `generateNotices` say before and after `bundleClosure`. Add the assertion `dedupe.test.ts` "lists the same payload packages before and after sharing" makes for sharing, with the SBOM's source and integrity from each package's `package-lock.json` (`supply-chain.ts`, `vendoredLockPackages`) included.
3. **The SBOM of a deduped payload is the SBOM of the full one.** Extend `dedupe.test.ts` "lists the same payload packages before and after sharing" to compare `generateSbom` and `generateNotices` output, not only `listPayloadPackages`. `supply-chain.test.ts` "the logical dependency graph under a smaller file layout" does this for a hand-built layout on `main`; the real output of `dedupePiPackages` is the better fixture.
4. **Same bytes, different registry integrity are not shared.** The group key is `integrity\0digest`; a test where two copies have identical content and different lockfile integrity expects both to stay package-local.
5. **The shared directory name.** It carries the first 12 hex digits of the content digest (`dedupe.ts`). A collision fails the build because the rename lands on a non-empty directory; use the full digest, or add a test that two different sets of one name and version with the same prefix fail closed and do not mix.
6. **A path-length budget for Windows.** `.shared/<name>@<version>-<digest>/<file>` adds a directory level and a long segment to every shared file's path, and each stand-in forwards to it by a relative specifier. Assert the longest installed path of the developer release (install home plus `apps/devcode/<version>/pi-packages/...`) stays under a stated limit, and run the developer end-to-end test with a long install home on Windows.
7. **An update and a rollback of a deduped payload.** Extraction of a hidden `.shared` directory and of forwarding modules is exercised by the install job of Release candidate (`install`, `--smoke`, `doctor`) once the branch merges; an update test belongs with the developer update gap below.
8. **The footprint budgets for `linux-x64` and `win32-x64`.** `scripts/performance-budgets.json` records `darwin-arm64` only, and a platform without a record passes. After the first Release qualification run on the merged code, record both from the `install` job's "Report the installed file count" summaries and the benchmark artifacts, and make the missing record a failure on a platform that has a Release candidate target.

## Tests to add on `v011/contracts` (`piship/v1`, `piship-lock/v1`, migration)

1. **No runtime credential in a migration artifact.** Spec B3 says a runtime credential never enters a migration artifact and is never restored by a rollback. Add a CLI test that runs `piship migrate --check` and `--write` with a credential-looking value in the environment and a stored credential in the state, and scans the output, the written manifest, and the backup for it (`packages/cli/src/index.test.ts`, with the scan helpers of `tests/helpers/security.ts`). The rollback half is `tests/e2e/lifecycle-credentials.test.ts` on `main`.
2. **A developer example on `piship/v1`.** `lifecycle-schema-compat.test.ts` installs, updates, and rolls back a `piship/v1alpha6` and a `piship/v1` release of a small fixture. The developer example's lock and its six Pi package lock files are relocked by the contracts branch; a test that builds `examples/developer` from its migrated manifest and compares its payload inventory with the `piship/v1alpha6` build (they must be equal but for the schema id and lock digests) would prove that freezing changes no payload.
3. **`piship diff` across the migration.** The branch documents what `piship diff` reports across v1alpha6 to v1; assert it on the two locks of one example.

## Gaps that need a decision or a measurement

1. **Developer update and rollback.** No test updates and rolls back `devcode`. It needs the shared fixture builder in `tests/helpers/lifecycle.ts` to build a second developer release (a relock and a `piship release` with the per-package audits, per target), which is minutes of registry traffic and CPU per target and has not been validated on Windows. If a qualification run shows the developer payload's update path differs from the personal one, add a `DEVELOPER` distribution beside `PERSONAL` there and a `developer-lifecycle` entry in `tests/helpers/e2e-shards.ts`.
2. **Registry signatures for vendored Pi packages.** `npm audit signatures` runs once over the runtime closure. Running it in each `pi-packages/<id>` root needs npm's hidden lockfile (`node_modules/.package-lock.json`) to be current; npm treats it as stale once a directory under `node_modules` is newer, which dependency sharing guarantees. Check each root before it is shared or bundled (the build already installs it with `npm ci`), and record the verdict per package beside its audit record in `vulnerabilities.json`.
3. **Require a verified registry signature in Release candidate.** `scripts/check-release-evidence.mjs` fails on a signature verdict that audited no package and prints an `unavailable` verdict (registry or Sigstore trust root unreachable) as a warning. After the first qualification run shows `passed` on all nine distribution and target combinations, make `unavailable` a failure too (a `--require-signatures` flag), so a qualified release cannot ship without a checked signature.
4. **Project trust and permission rules on Windows.** The provider probes (`tests/helpers/developer-probe.mjs`) assume POSIX paths. Porting them gives Windows the rule-by-rule evidence that Linux and macOS have.
5. **A real provider for the personal and developer examples.** The `Live provider` workflow routes the reference stack to a real provider; no workflow sends a request from `mypi` or `devcode` to one.
