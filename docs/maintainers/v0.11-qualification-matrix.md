# v0.11.0 qualification matrix

Which automated test proves each step of the three production qualifications of v0.11.0 (spec tasks C1, C2, and C3) and each supply-chain item (D2), and which workflow runs it. The matrix is the traceability table behind the [release checklist](release-checklist.md): it says what a green [Release qualification](../../CONTRIBUTING.md) run does and does not show. It claims nothing a workflow does not run. A step with no automated proof is a **gap**, listed with its reason at the end; it is not covered by a manual run unless a gap says so.

## Tiers

| Tier | Workflow | Runs | What it is |
| --- | --- | --- | --- |
| Fast gate | `CI` | every pull request and `main` push, Ubuntu, macOS, Windows | build, unit tests, Pi compatibility, live platform secret store |
| Portable E2E | `Portable E2E` | nightly, manually, and in Release qualification, Ubuntu, macOS, Windows | the installed branded command against loopback fixtures (`tests/e2e`) |
| Reference E2E | `Reference E2E` | nightly, manually, and in Release qualification, Ubuntu only | the AcmeCode reference distribution against a live Keycloak, credential broker, and LiteLLM (`examples/enterprise-reference`, `tests/enterprise-reference`) |
| Release candidate | `Release candidate` | manually and in Release qualification, one runner per target | two builds, reproducibility, attestation, `verify-release`, tamper rejection, install with the shipped script, and for `mypi` and `devcode` the installed offline `--smoke` and `doctor` |
| Live provider | `Live provider` | manually only | the reference stack routed to a real model provider; never part of qualification |

"Clean machine" in this matrix means what the tests build: an empty temporary home, state directory, install home, bin home, secret store, and (where used) shared file store, on a CI runner or a developer machine. It is not a freshly imaged operating system, and no automated run reaches one.

## C1 — managed

The flow is [`tests/e2e/managed-clean-machine.test.ts`](../../tests/e2e/managed-clean-machine.test.ts), "runs from install to uninstall as one flow on one machine" (Portable E2E, three targets, the demo company against loopback fixtures: an identity provider, a credential broker, and a gateway that is not a model), and, on Ubuntu, the same steps against the live stack in [`examples/enterprise-reference/tests/distribution-flow.test.ts`](../../examples/enterprise-reference/tests/distribution-flow.test.ts) (Reference E2E).

| Step | Portable E2E (fixtures, three targets) | Reference E2E (live stack, Ubuntu) | Release candidate (three targets) |
| --- | --- | --- | --- |
| install | the flow's `install`: archive verified, then the shipped script on a machine with nothing of the distribution; `lifecycle-install.test.ts` | "is installed, and refuses to launch before sign-in" | `install` job: shipped `install.sh` or `install.ps1`, then `acmecode version` |
| launch | the flow's `launch`: `--smoke` and `models` refuse signed out before any service is contacted | the same test | version only: a managed launch needs a sign-in |
| login | the flow's `login`: Authorization Code with PKCE, the test acting as the browser (no form, no second factor); `security-controls.test.ts` identity cases | "signs Alice in on the Keycloak authorization page with PKCE and a loopback redirect" | none |
| credential acquire | the flow's `credential acquire`: the fixture broker turns the access token into a runtime credential kept in the platform secret store | "exchanges the identity for a credential scoped to Alice's models..." | none |
| model request | the flow's `authenticated model request`: `--smoke-model` to the fixture gateway, which answers only the brokered credential | "sends a model request through LiteLLM with the brokered credential" (mock upstream) and "renews a credential the gateway rejected" | none |
| session resume | the flow's `session resume`; `lifecycle-rollback.test.ts` keeps the session across a rollback | the flow, as a whole | none |
| doctor | the flow's `doctor`: every group reports the state the flow produced | "reports the identity, credential, gateway, and secret store in doctor" | none (needs a sign-in) |
| update | the flow's `update` through a signed loopback channel; `lifecycle-update.test.ts`, `lifecycle-integrity.test.ts` (tampered archive, forged metadata) | "updates through a signed channel and keeps the session, the identity, and the credential" | none |
| rollback | the flow's `rollback`; `lifecycle-rollback.test.ts`; `lifecycle-credentials.test.ts` (a revoked secret is never restored) | "rolls back keeping the session, and the credential the gateway still accepts" | none |
| logout | the flow's `logout`: revokes at the broker and the provider, clears the store, keeps sessions | "signs out: revokes the credential and the identity tokens, and clears the secret store" | none |
| uninstall | the flow's `uninstall` and `purge`: the machine has nothing of the distribution again | "uninstalls, keeping the user's sessions, and purges the state, leaving the machine as it was" | none |

What the flow does not prove: an interactive terminal session (every launch is Pi's headless acceptance run; the TUI needs a terminal); a second factor or a sign-in form (the Reference E2E signs in on Keycloak's own page, but not with a human or MFA); a real company identity provider or gateway (the production validation protocol, outside CI); a real model (the stack's upstream is a mock). Sandboxed commands run on Linux and macOS only; on Windows the flow asserts the sandbox is reported as not required and runs no command, because Windows has no sandbox adapter.

## D2 — supply chain, every distribution on every target

`Release candidate` builds `acmecode`, `mypi`, and `devcode` for `linux-x64`, `darwin-arm64`, and `win32-x64`. Every row is a job with that matrix, guarded by `tests/ci-guards.test.ts` ("release candidate supply-chain evidence"), so removing one fails the unit tier.

| Item | Where | Proof |
| --- | --- | --- |
| reproducibility | `build` (first and second build on separate runners, same `SOURCE_DATE_EPOCH`) and `reproducibility` | `piship reproducibility` exits non-zero unless every payload file is equal; the report is uploaded per distribution and target |
| verify-release | `verify` on a fresh runner that never built the archive | `piship verify-release --sha256`: archive, checksums, every payload file against the inventory, manifest and lock, SBOM completeness, notices coverage, recorded scan and test results |
| tamper rejection | `verify` | a flipped archive byte, a wrong digest, and a modified payload file, `release.json`, SBOM, and `checksums.txt` each fail with `INTEGRITY_FAILED` at the layer that can prove it, and the exact bytes are restored |
| SBOM | built and self-checked in `piship release` (`verifySbom`); checked again by `verify-release` and by `scripts/check-release-evidence.mjs` in `verify` | the SBOM lists the logical dependency graph, from the lock, the bundle record, and each vendored Pi package's lockfile, not the files on disk ([security](../security.md#v011-security-review)); `supply-chain.test.ts` "the logical dependency graph under a smaller file layout" |
| notices | same | every SBOM package has a notices entry and its license text; same test |
| vulnerability scan | `piship release` (`npm audit` over the runtime lock and over each vendored Pi package's lockfile) | a finding at or above `failOn` fails the build; the verdict and per-package records travel in `release.json` and `vulnerabilities.json`; `check-release-evidence.mjs` requires `passed` and one audit record per vendored Pi package |
| registry signature | `piship release` (`npm audit signatures` over the runtime closure) | an invalid signature or attestation fails the build. Until this pull request the check reported "found no dependencies to audit" on every release candidate and verified nothing; it now runs ([security](../security.md#v011-security-review), finding F1). `check-release-evidence.mjs` fails on a verdict that audited no package and prints an `unavailable` verdict (the registry or the Sigstore trust root unreachable) as a warning. The vendored Pi packages are not signature-checked (a documented limit) |
| provenance and attestation | `attest` (`actions/attest-build-provenance` on the first build of each target) and `verify` (`gh attestation verify --signer-workflow --source-ref`, and that it rejects a tampered archive) | Sigstore keyless provenance bound to the workflow and the ref; verified on a runner that did not build it |
| install | `install` job | the shipped script installs the archive; `mypi` and `devcode` then run offline `--smoke` and `doctor` |

## Gaps

Each is a step with no automated proof, or less than its row says, with the reason. None is claimed as covered by a manual run.

1. **Developer update and rollback.** No test installs `devcode` 1.0.0, updates to 1.1.0 through a signed channel, and rolls back. It needs two relocked developer releases (two `piship lock` runs against the registry and two `piship release` builds with the per-package audits) on every target, which is the heaviest fixture in the suite and could not be validated on Windows here. The update path is distribution-agnostic and is proven on `mypi` and `acmecode`; what the developer payload adds is the shared dependency directory and a larger tree. Follow-up in [v0.11-followups.md](v0.11-followups.md).
2. **Windows file-count budget.** `scripts/performance-budgets.json` (footprint pull request) records `darwin-arm64` only, and a platform without a record passes. The Windows figures for the developer release are not measured in CI; the Release candidate `install` job now prints them for every target so a first qualification run can record `win32-x64` and `linux-x64` budgets. Until then a Windows file-count regression fails nothing.
3. **Project-trust and permission rules on Windows.** The provider probes use POSIX paths and skip on Windows, so project trust and the rule-by-rule permission cases are proven on Linux and macOS only. The Windows run proves the capability is effective and locked.
4. **Personal and developer model requests against a real provider.** MyPi and MyPi Local talk to a stand-in server. The manual `Live provider` workflow exercises the reference stack, not the personal or developer examples.
5. **Interactive terminal.** Every launch in every tier is Pi's headless acceptance run (`--smoke`, `--smoke-model`); no test drives the TUI.
6. **Managed on Windows: sandbox.** No adapter exists, so the sandbox step is not run; the refusal of a required sandbox is asserted in `governance.test.ts`.
7. **A real identity provider, gateway, MDM, EDR, or proxy of a company.** The Reference E2E is the nearest automated evidence; the [production validation protocol](../production-validation.md) is the rest, outside CI.
8. **A real clean machine, and an air-gapped one.** The flows use isolated temporary homes on a runner that has network access. They prove that install and launch contact nothing but the declared hosts (`personal-lifecycle.test.ts` and `shared-store.test.ts` use a trap proxy and the update host's request log); they are not a packet-level offline proof.
9. **Registry signatures of vendored Pi packages.** Only the runtime closure is checked; see the artifact contract's known limitations.
