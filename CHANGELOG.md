# Changelog

All notable changes to this project are documented in this file. Each section is a project milestone; the manifest and lock schema each milestone uses is listed in the [version map](docs/status.md#version-map). No milestone has been published to npm or as a GitHub Release, and every package is still versioned `0.1.0`.

## Unreleased (v0.7)

Preview milestone; not published to npm.

### Added

- The HTTP audit sink wire contract, `piship-audit-batch/v1`, is published with a JSON Schema in the [enterprise integration contract](docs/enterprise-integration.md#audit-collector-piship-audit-batchv1): request, readiness probe, batching, retries, de-duplication, and privacy. A unit test validates every batch the sink sends, with every field at its limit, against the schema in the doc, and fails if either names a property the other lacks.
- Enterprise networking is qualified through the real launcher on loopback, with no compose stack: the proxy path (every managed request goes through the inherited proxy, and a proxy that refuses the traffic stops the launch), the `NO_PROXY` path, the custom CA path (a bundle without the server certificate fails the request), private endpoints under private-only, `publicFallback: deny` (an undeclared public host is refused before any proxy or connection), and TLS that is never disabled or downgraded. The docs now state that `network.privateOnly` matches hostnames only: it ignores ports and schemes and does not check that a host is a private address.
- The personal `local-secret` and `none` access-mode E2E scenarios (`identity.mode: none` with an OpenAI-compatible endpoint) now run on every Portable E2E target instead of only on the Ubuntu qualification path, in their own file, `tests/e2e/personal-access-modes.test.ts`. They took 13 s and 9 s on Ubuntu in the last Release qualification, and a comparable build takes 19 s on macOS and 47 s on Windows. They, `personal-local-model`, and new unit tests also check that binding credentials to a principal changes nothing for a personal distribution: no `identity/principal.json` is written, a local secret stored by an earlier release stays usable, and `login`, `logout`, and `login` again keep the same model selection (the E2E scenarios also assert that the same session resumes).
- Test infrastructure: the managed E2E scenarios run on the live platform secret store on every Portable E2E target (macOS Keychain in a temporary keychain the job creates and deletes, Windows Credential Manager, and the Linux Secret Service under an unlocked GNOME Keyring on a private D-Bus session), not only on the file fallback that the E2E helpers forced before. A new scenario, `tests/e2e/lifecycle-secret-store.test.ts`, covers store, load, replace, delete, credential and identity refresh, update, rollback, logout, and purge with an identity token bundle large enough to be split across platform items on every OS; `user-switching` also runs on both storages. After each step the platform store holds exactly the references the metadata names, and the file fallback directory never exists for a distribution that declares `system` storage. The system-storage scenarios run only with `PISHIP_LIVE_SECRET_STORE=1`, which the Portable E2E workflow sets for its E2E step alone; elsewhere they report as skipped with the reason.
- Two workspace packages for adapter authors, `@piship/adapter-sdk` and `@piship/adapter-conformance`, built to a publishable shape but private and unpublished ([decision 21](docs/decisions.md)). The SDK ships in every payload, which grows by the SDK's own files only (its dependencies were already there); the conformance package never does. `@piship/contracts` now defines `AdapterContext` and `ResolvedEndpoints`, which `@piship/core` still re-exports unchanged. The committed example locks change in `npmLockSha256` and, for the stored sandbox credential's state class, in `runtime.stateSchemas`.
- The [adapter SDK](docs/adapter-sdk.md) surface, a preview: `defineIdentityAdapter`, `defineCredentialAdapter`, and `defineAuditSink` return their argument unchanged; `defineSandboxAdapter` returns a factory whose backend has passed `customBackend()`, the check PiShip's loader applies; `withTimeout` composes a timeout with the caller's cancellation. Everything else is a curated re-export of `@piship/contracts` and `@piship/sandbox` (context and provider types, `SecretValue` and redaction, the `ManagedFetch` type, `PiShipError` and `parseRetryAfter`, the audit batch contract, and sandbox capability declarations), which a unit test pins and checks for internal or Pi imports. `defineAuditSink` types the collector behind the built-in `http` audit sink; a distribution still cannot declare its own sink type. Adapters are single files: `packages/adapter-sdk/examples/` has one of each kind, each importing only the SDK and `node:` built-ins.
- Workspace consistency for sandbox backends ([workspace](docs/sandbox.md#workspace)). A remote backend declares whether its sandbox sees the files PiShip's file tools edit: `shared`, `synchronized`, or `snapshot`, the default. Before the first command that reaches the sandbox (never at activation, in Plan mode, or from `doctor`), PiShip verifies a shared or synchronized claim with a two-way sentinel in a directory it owns inside the project's git directory, and reports the weaker mode the evidence supports when a direction is delayed or missing. Only a verified shared or synchronized workspace, or a local backend, counts as a complete coding-agent workspace; a snapshot never does. The result is checked again after 30 minutes or when the backend reports a new environment through the optional `SandboxInstance.epoch()`, which the Kubernetes backend implements with its claim name. `doctor`'s Workspace group now shows the consistency, the declared mode, the verification state, whether the workspace is complete, and how the git control files are protected.
- An [audit sink conformance kit](docs/adapter-sdk.md#audit-sink-conformance-kit), `testAuditSink` in `@piship/adapter-conformance`. Before, an adapter author had no way to check an `AuditSink` against `piship-audit-batch/v1` other than reading the contract. The kit connects the sink to a fake collector it controls and reports `passed`, `failed`, or `skipped` with a reason for ten behaviors: metadata-only defaults, secret redaction, identity attribution, session correlation, event id stability, delivery failure, buffer behavior, the fail-closed policy, shutdown flush, and duplicate handling. The buffer and shutdown checks apply to a sink that holds events itself (`flush`, `status`, `close`) and are skipped for a plain one. The kit imports only `@piship/adapter-sdk`. Its tests pass a reference plain sink and a reference buffering sink, and fail sinks seeded with one defect each, such as a leaked credential, a swallowed failure, a new ID on every write, an unbounded buffer, or a skipped flush on close.
- The credential conformance kit, `testCredentialAdapter` in `@piship/adapter-conformance`: it runs a credential adapter against a fake broker it owns, through the adapter's managed `fetch`, and reports acquire, refresh, expiry, revoke, 401, 403, 429, 5xx, timeout, abort, redaction, concurrent refresh, retry behavior, and idempotency as passed, failed, or skipped, with a reason that never holds a secret. Each behavior is a contract statement an adapter author can read in the [adapter SDK](docs/adapter-sdk.md#credential-conformance-kit) docs; a behavior the adapter cannot show, such as revoke without `revoke()`, is skipped, never passed. The kit's own tests pass a reference adapter and fail a seeded-bad variant of it for every behavior.
- A governed session records each workspace verification in the local `metrics.json` as a new `workspace` entry: the declared and effective modes, the verification state, and its time, never a path, sentinel token, or reason; a value PiShip does not define is stored as `UNKNOWN`. The field is additive within `piship-metrics/v1`. While `doctor`'s own verification is pending, its Workspace group shows the last result a session recorded under the same declaration. When the effective mode is lower than the declared one, the session raises one notice per session, a warning that does not fail the launch; `GovernanceSession.attachNotices()` routes it to the UI. `LocalMetrics.recordWorkspace()` is the new recorder.
- The identity conformance kit, `testIdentityAdapter` in `@piship/adapter-conformance`. Before, an identity adapter author could check the contract only by reading it. The kit runs an interactive or workload (`interactive: false`) identity adapter against a fake identity service it owns, through the adapter's managed `fetch`, and reports login, refresh, expiry, logout, claim normalization, revoked session, secret redaction, and service outage as passed, failed, or skipped, with a reason that never holds a token; a `respond` hook encodes the service's answers in the adapter's own protocol. PiShip does no JWT cryptography, so invalid issuer, invalid audience, invalid signature, the token validity window, and revoked tokens are checked only with a harness whose `mint` hook the adapter author supplies; without one they are skipped with `needs harness`, never passed ([adapter SDK](docs/adapter-sdk.md#identity-conformance-kit)). The kit's tests pass a reference device-style adapter and a reference workload adapter, with and without a harness, and fail a seeded-bad variant for every behavior.
- A [sandbox conformance kit](docs/adapter-sdk.md#sandbox-conformance-kit), `testSandboxAdapter` in `@piship/adapter-conformance`. Before, a company writing a custom sandbox backend could check its claims only by reading the contract, and PiShip's own outside check proves the environment and network claims only. The kit runs the backend as PiShip does and checks each claim by running commands inside it: a file planted on this host must stay unreadable, a loopback listener unreachable with the network denied, a planted launcher variable absent, the credential out of every result, error, and logged line, and a timed-out or cancelled command must not write the marker it would write later. It reports availability, capabilities, prepare, execute, environment filtering, secret leakage, filesystem claims, network claims, timeout, cancellation, cleanup, dispose, and fail-closed behavior, and for a declared `shared` or `synchronized` workspace PiShip's two-way sentinel, the git control probe, and the re-check after the validity window or an `epoch()` change, as passed, failed, or skipped with a reason that never holds a secret. A snapshot backend's workspace checks are skipped with `declares snapshot`, never passed; `cleanup` and the epoch check take hooks the adapter author provides (`sandboxes`, `replaceEnvironment`) and are skipped without them. The kit imports only `@piship/adapter-sdk`. Its tests pass reference backends that run real commands under Seatbelt or bubblewrap (local, snapshot, shared, synchronized, and one that returns output only at the end), and fail a reference seeded with one defect for every behavior.
- A sandbox credential for remote sandbox backends ([sandbox credentials](docs/sandbox.md#credentials)). Before, an e2b-compatible endpoint that requires `X-API-Key`, or a Kubernetes API that requires a bearer token, could be authenticated only when it sat on the inference gateway's origin (`credential: runtime`). `sandbox.credential: stored` sends the API key or token a person stores with the new `<command> sandbox login`, which reads it only from a no-echo prompt or the first line of a piped stdin (no flag, no environment variable, no file, no in-session command); `<command> sandbox logout` deletes it. It is kept in the configured secret store under `piship:<id>:sandbox#<n>`, with non-secret metadata in `credentials-metadata/sandbox.json` (`piship-sandbox-credential-metadata/v1`, a new state class), bound to the principal that stored it and to the origins of the endpoint (and Kubernetes router) it was stored for. Before its secret is read, one of another principal is deleted and refused, a rejected one is refused, and every URL it would reach must be one of those origins, so pointing the endpoint variable elsewhere fails closed and sends nothing. A custom adapter module may instead export `sandboxCredential`, a `CredentialProvider` that PiShip acquires per launch with the signed-in identity, holds in memory only, renews before expiry and once after a rejection, and revokes when the session ends. Audit records `credential.acquire` and `credential.revoke` with `purpose: "sandbox"`, never the secret, origin, or endpoint.
- `doctor` reports the stored sandbox credential in its Sandbox group. Before, nothing showed whether one was stored, rejected, or bound to someone else, until a launch failed. For a manifest that declares `sandbox.credential: stored`, doctor shows `sandbox credential <state> (<source>, <kind>) in <store>` and whether it is bound to the current principal and whether its recorded origin matches the configured endpoint. A credential the sandbox service rejected is a warning that names `sandbox login`; an absent credential, another user's, or one stored for another endpoint fails a required sandbox. Doctor reads only the non-secret metadata: never the secret, its reference or ID, or the recorded origins, and it deletes nothing.
- The [adapter SDK guide](docs/adapter-sdk.md#the-sandbox-credential) documents the sandbox credential a custom backend receives. Before, it said `CustomBackendContext.credential` came only from `sandbox.credential: runtime` and did not mention `credentialOrigins` or `credentialRejected`. It now lists the three sources (`runtime`, `stored`, and the module's `sandboxCredential` export), the origins each may be sent to, and what `credentialRejected()` does for each. `SandboxCredentialAccess` stays out of the SDK: a backend never sees it, and a module's own credential is a plain `CredentialProvider`, which the SDK already exports.

### Changed

- **Contract change:** a new error code, `CREDENTIAL_DENIED`, reports an authorization denial (HTTP 403) from the credential broker, for acquire, refresh, and revoke. A 403 used to share `CREDENTIAL_ACQUIRE_FAILED` with transport failures. Broker errors also carry a non-secret `detail` with `operation` (`acquire` or `revoke`), `reason` (`unreachable`, `timeout`, `cancelled`, `authentication`, `denied`, `rate-limited`, `unavailable`, `rejected`, or `contract`), and the HTTP `status` when the broker answered, so callers can tell the retry classes apart where they share a code.
- **Behavior change:** a failed credential renewal keeps the failure's `retryable`, `retryAfterMs`, and `detail`. It used to be rewrapped as `CREDENTIAL_EXPIRED` or `CREDENTIAL_REVOKED` that were never retryable, so a broker outage or rate limit during renewal read as "sign in again".
- **Behavior change:** a caller's `CredentialContext.signal` now composes with the broker's 30 s timeout instead of replacing it, so a signal that never fires can no longer leave a broker request waiting forever. A cancelled request is reported as a non-retryable cancellation instead of a retryable timeout, and the timeout now also covers reading the response body.
- **Behavior change:** broker revocation goes through the same transport as acquisition: it has the same timeout and cancellation, a transport failure is a retryable `CREDENTIAL_REVOKED` instead of an uncoded error, a 403 is `CREDENTIAL_DENIED`, and a 429 or 5xx carries `Retry-After`. A broker 5xx on acquire also carries `Retry-After` now. A network or TLS policy refusal from the managed fetch keeps its own code (`NETWORK_DENIED`, `TLS_POLICY_VIOLATION`) instead of becoming a retryable `CREDENTIAL_ACQUIRE_FAILED`.
- **Behavior change:** the credential broker client no longer builds an error from a transport error's own message, which for an invalid header value can contain the token that was being sent; it reports the system error code (`ECONNREFUSED`) or `network error`, and the managed fetch does the same. An identity access token or a broker credential that holds CR, LF, or NUL is refused before it is put in a header (`IDENTITY_INVALID` for the access token, a `contract` failure for the credential). The answer status now decides the classification before any body is read, so a broker that answers 403 and never finishes the body is `CREDENTIAL_DENIED` and not a timeout, a success body larger than 64 KiB is a `contract` failure, and an early renewal that the broker refuses with 403 fails with `CREDENTIAL_DENIED` instead of continuing on the credential that is still valid.
- **Behavior change:** an OIDC token endpoint 5xx (including a proxy's HTML error page) or a `server_error` / `temporarily_unavailable` response now fails with a retryable `GATEWAY_UNREACHABLE`, and a 429 with a retryable `GATEWAY_RATE_LIMITED`, both with the server's `Retry-After`. They used to fail with a non-retryable `IDENTITY_INVALID` ("Contact your administrator"). `invalid_grant` is still `IDENTITY_EXPIRED`.
- **Behavior change:** the Linux Secret Service store now splits a value whose stored form exceeds 8000 characters across part items named `<ref>+<n>`, with `chunks:<count>:<write>` in the primary item (the macOS and Windows stores use `chunks:<count>`), and each part carries the `parent` and `write` attributes, and fails when `secret-tool` warns `password is too long`. `secret-tool store` keeps only the first 8192 bytes of a secret and still exits 0, so a value of about 6 KB or more, such as an OIDC token bundle with large tokens, was stored truncated without an error. Values of 8000 characters or fewer are stored and read exactly as before. The `CI` check job on Ubuntu now installs GNOME Keyring and runs the live secret-store test against it on every pull request, next to Keychain on macOS and Credential Manager on Windows; the Linux store had only a command-runner test before, which is why the truncation went unnoticed. New tests also pin that the Linux store fails closed, with no plaintext fallback, when `secret-tool` cannot reach a session bus. Each part item now carries its primary's reference as a `parent` attribute, so `put` clears every earlier part before it writes, a failed `put` leaves no part behind (an earlier chunked value it could not replace is removed rather than served half old and half new; an earlier plain value stays), `get` fails closed on a missing or extra part, and `delete` clears parts by attribute and reports an error when the item or any part is still there afterwards.
- **Contract change:** every audit event now carries an `id`, a random UUID assigned once when it is emitted and kept when a failed batch is resent, so a collector can drop an event it has already stored. Before, events had no ID or sequence and a retried batch could be stored twice without a way to tell. The field is additive: the event schema stays `piship-audit/v1` and the batch schema `piship-audit-batch/v1`, and the file sink writes it too. `@piship/contracts` adds `AuditEvent.id` (optional in the type, since events written before it have none), `AUDIT_BATCH_SCHEMA` (moved from `@piship/audit`, which no longer exports it), `AuditBatch`, and `AuditSink`, the interface the file and HTTP sinks implement.
- **Behavior change:** a required audit sink no longer loses events silently when a governed session ends. Before, `GovernanceSession.close()` ignored the result of the final flush, so events a required sink had not taken by the 5-second deadline, or had dropped earlier from a full buffer, disappeared without a report; a failing MCP or sandbox cleanup could also skip the flush entirely. Now the final flush always runs, a required sink is retried until the deadline, and `close()` returns the final `AuditStatus` or, after all cleanup, throws `AUDIT_UNAVAILABLE` with the pending and dropped counts per sink. A launch or `--smoke` run whose required sink loses events therefore exits with that error (`doctor` prints its whole report first and then fails with `CONFIG_UNAVAILABLE`), and closing takes up to 5 seconds longer while a required sink is down. A launch that fails for another reason keeps its error and counts `AUDIT_UNAVAILABLE` in the local startup failures instead. `@piship/audit` adds `requiredAuditLoss(status)`; an event emitted after `AuditLog.close()` now counts as dropped instead of being ignored.
- **Behavior change:** `login`, `logout`, `update`, and `rollback` honor a required audit sink. Before, their events were best effort even for a required sink: an unreachable sink or undelivered events printed a warning and the command succeeded. Now the command fails with `AUDIT_UNAVAILABLE` after the operation, which is not undone (signing out still signs out); a refused `update` or `rollback` keeps its own error and prints the audit failure. Distributions with only optional sinks keep the warning.
- **Behavior change:** a `login` that fails after it changed state, such as a broker refusal after the new identity was stored, now records what happened; the audit ran only after a success before. The login error stays the command's error even when the audit also fails, and `logout` prints its revocation warnings before the audit that can fail the command. The session commands (`--smoke`, `--smoke-model`, the interactive launch) also end every teardown step even when an earlier one failed: a failing runtime dispose used to skip closing the governance session, and a close that lost required audit events used to replace the session's own error and skip saving metrics and clearing the published context. The session's error is kept, and a teardown failure is raised only when the session itself succeeded.
- **Behavior change:** in a managed distribution, commands the agent runs through the `bash` tool receive only the network environment the distribution's policy approves. Proxy variables are passed when `network.proxy.inheritEnvironment` is true, never a proxy URL that embeds credentials, and `NODE_EXTRA_CA_CERTS` is set from a single declared `network.tls.additionalCA` bundle. An uncontained command used to inherit every network variable; it now loses `ALL_PROXY`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `GIT_SSL_CAINFO`, `GIT_SSL_NO_VERIFY`, and `NODE_TLS_REJECT_UNAUTHORIZED`, and an ambient proxy URL with credentials. A command in an enforced sandbox that allows the network received none of these and now receives the approved ones; a sandbox that denies the network and a remote backend still receive only what `sandbox.environment.allow` lists. A distribution that relied on an ambient CA variable in agent commands declares the bundle in `network.tls.additionalCA` instead. Only managed distributions are affected: a personal distribution keeps the proxy and CA variables of the user's shell in its commands, exactly as before, and so does a distribution with no network policy (`piship/v1alpha1`).
- **Behavior change:** a model request is refused while a required audit sink has lost events and its buffer is full, before anything is sent to the gateway, with `AUDIT_UNAVAILABLE`. Tool calls were already refused in that state, but a prompt, which can carry workspace content, still left; Pi swallows an error thrown from its `before_provider_request` hook, so the check sits in the model runtime that PiShip wraps, on every request path.
- **Behavior change:** an interactive session now ends its governance session when Pi shuts down. Pi ends a session by awaiting its runtime disposal and then calling `process.exit()` (Ctrl+D, `/quit`, SIGTERM, SIGHUP), so the code after the interactive loop never ran: the session recorded no `session.end`, skipped the final audit flush, and lost any event a required sink had not yet taken without a report. Teardown now runs inside that disposal; if it fails the error is printed and the exit code is 1. `AUDIT_UNAVAILABLE` also outranks a cleanup error in `--smoke` and `--smoke-model`, and a failed login records the identity that was stored, or none when the distribution has no identity provider, and a failed session start is counted in the local startup failures.
- **Behavior change:** in a managed distribution, a proxy, CA, or TLS-verification variable that `sandbox.environment.allow` names no longer reaches a sandboxed command that has no network to configure (`network.mode: deny`) or a remote backend; before, only a local sandbox that allowed the network dropped them, so a proxy URL with credentials could reach the command through an allowlist entry. The set of dropped variables also covers the proxy, trust, and verification settings of npm and yarn, pip, git (`GIT_CONFIG_*`), Cargo, Deno, curl and wget, and Java, and `NODE_OPTIONS` when it changes trust roots. A proxy URL is passed to a child only as a host and port; one with a path, query, fragment, or backslash is withheld. If Pi ever stops giving the agent's `bash` tool an environment, the process environment is its base, so it is never left unrestricted.
- **Behavior change:** the Linux Secret Service store treats a locked keyring as an error. `secret-tool lookup` answers a locked keyring with exit 1 and no message, exactly as it answers a missing item, so a locked keyring read as an absent secret, a delete reported success while the items stayed, and the caller then cleared the metadata that pointed at them. A miss is now confirmed with `secret-tool search`. Each stored part also carries the id of the write that made it, so two writers of one reference can no longer leave a value made of both, and a reference may not start with a dash.
- **Contract change:** `CredentialContext` adds an optional `idempotencyKey`, and the `http-broker` acquire request sends it as an `Idempotency-Key` header. `CredentialManager` generates a random UUID for each acquire or renewal it sends, never derived from the identity or a token, unless the caller passes one. Before, a credential request carried nothing a broker could use to recognize a retry, so retrying after a lost answer could issue a second credential. Broker acquire errors now carry the key in `detail.idempotencyKey`, so a caller can retry the same acquire with it, and a failure without an answer (`timeout`, `unreachable`, `cancelled`) carries `detail.outcome`: `not-sent` when the request never left PiShip, `unknown` when the broker may already have issued a credential. A 409 or 422 to an acquire that sent a key is a non-retryable `CREDENTIAL_ACQUIRE_FAILED` with `reason: idempotency-conflict`; a 409 or 422 without a key is still `rejected`. A caller key that is not 1 to 255 visible ASCII characters is refused before anything is sent. PiShip still retries no credential request automatically; the [enterprise integration contract](docs/enterprise-integration.md#idempotency-and-retries) now tells broker authors how to honor the key and which failures are safe to retry.
- **Behavior change:** when revoking a credential, a secret store that cannot be read is a `failed` revocation with a problem entry (`revocation: the stored credential could not be read (<code>)`), so `logout` shows it, and an `update` or `rollback` that clears a credential the target cannot read warns that it was not revoked remotely. It used to be a silent `skipped`, which hid a credential that could still be valid at the broker. A store that holds no secret for the credential is still `skipped`.
- **Behavior change:** `doctor` reports enterprise state in its own groups, printed in one fixed order ([doctor report](docs/manifest.md#doctor-report)). Gateway, Secret Store, Network, Audit, Release, and Workspace are new groups; the old Access, Security, and "MCP and audit" sections are gone (their lines moved to Identity, Credential, Network, MCP, and Audit), and the release line moved from Supply Chain to Release. Network now says whether a proxy is active (as `scheme://host:port`), whether `NO_PROXY` is set, how many CA bundles are declared, and which network variables a managed distribution's agent commands receive or have withheld, by name and reason (the line is labeled `agent commands`); for a personal distribution it says they are not restricted. Audit lists each sink with its target (`local file` or the HTTP host, never the URL path or query), state, and delivered, pending, and dropped counts. Sandbox adds the isolation (`local`, `remote`, or `none`) and the containment summary; Workspace says `not reported` until sandbox backends report workspace consistency. Identity no longer shows the signed-in user's display name or subject, only whether a session is signed in and the configured issuer. Every line, including passed checks, is now sanitized: URL credentials, queries, and fragments are removed and token shapes redacted. `doctor`'s governed session now uses the distribution's network policy, child network environment, and signed-in principal, as a launch does, and records credential lifecycle events from its activation; it used to run with the default network policy and no principal. When that session's close finds events a required audit sink did not take, `doctor` reports `AUDIT_UNAVAILABLE` in the Audit group and exits non-zero after printing the whole report instead of losing it.
- **Contract change:** `@piship/contracts` adds the normalized principal: `PrincipalKey` (`issuer` and `subject`), `principalKey`, `samePrincipal`, `principalId` (one unambiguous string for attribution), and `principalDigest` (a directory-safe digest). Email, display name, and username stay attributes. Credential metadata (`piship-credential-metadata/v1`, additive) records the `principal` its credential and entitlement were issued to, and `@piship/identity` adds `assertSamePrincipal`.
- **Behavior change:** a runtime credential is used only by the principal `(iss, sub)` it was issued to. Before, credential metadata named no principal, so user B signing in after user A, or over A without a logout, could launch on A's credential and entitlement; `login` also stored B's identity before it cleared A's credential and only printed a notice when that failed, so a crash or a store failure in between left B's identity with A's credential. Now a credential bound to another principal, or to none while an identity is signed in, is revoked where supported (`credential.revoke` with reason `principal-change`) and deleted before anything uses it. `login` deletes the previous credential and confirms the deletion before it stores the new identity; on a change of principal it also revokes and deletes the previous identity session and clears the model selection (`model` and `models.allowed` in preferences; other preferences stay). A new `identity/principal.json` records the principal that owns the state; `logout` keeps it, so a change of user after a logout is recognized, and `identity.login` events carry `principalChange: true` when the user changed. In a distribution with an identity provider, credential metadata written before this release has no principal and is replaced once at the first launch or login (without an identity provider it is kept as it is): a broker or adapter credential is reacquired automatically, and a `local-secret` distribution with identity asks for its key again at `login`.
- **Behavior change:** a secret-store deletion is confirmed by reading the reference back, and a deletion that fails or cannot be confirmed (a locked keyring) is an error, never taken as done. Metadata whose secrets could not all be deleted is replaced by a discarded marker (`piship-credential-discarded/v1`) that lists them and that no release uses as a credential; the next launch or login deletes them first and fails closed with `SECRET_STORE_UNAVAILABLE` while it cannot, and `login` fails before storing the new identity. Before, clearing unusable metadata ignored deletion errors and removed the metadata that pointed at the secrets, and `logout` removed identity and credential metadata even when their secrets were still stored; `logout` now reports the failure and keeps the metadata so the next login or logout retries.
- **Behavior change:** a failed remote revocation no longer blocks the next sign-in or keeps the local secret, and it is no longer only a warning: it is recorded, without the secret, in `credentials-metadata/revocation-retry.json`, the `credential.revoke` event carries `retryPending: true`, every `login` repeats it as a notice until the credential expires, and `DistributionAccess.pendingRevocations()` returns the count and ages for `doctor`. The revocation itself cannot be re-sent, because the broker authenticates it with the deleted credential.
- **Behavior change:** an identity refresh that returns another issuer or subject fails with `IDENTITY_INVALID` for identity adapters as well as the built-in OIDC provider, and the stored session is kept; before, an adapter's refresh could replace the signed-in user. With identity configured, a request-time credential now also requires a signed-in identity. Provider messages copied into renewal, revocation, and logout problems are redacted.
- **Behavior change:** the `http-broker` client accepts only visible ASCII in the identity access token it sends and in the credential the broker returns, and only 1 to 256 characters from `A-Za-z0-9._:-` in `credential_id`; anything else is refused before it is sent or stored (`IDENTITY_INVALID` for the access token, a `contract` failure for the answer). Before, only CR, LF, and NUL were refused, so a credential with another control character or a space was stored and then failed every request as a retryable network error, and any string was accepted as a credential ID, which is shown, audited, and sent back on revoke. The same rule now applies to every credential provider: a runtime credential an adapter or the local-secret provider returns, as a string or a `SecretValue`, that holds a space, a control character, or a non-ASCII character is refused with `CREDENTIAL_ACQUIRE_FAILED` before it is stored.

- **Behavior change:** the entitlement of a runtime credential is re-read after the gateway denies a model. Before, a credential without `expires_at` was never renewed, so the `models` the broker returned at acquire stayed in force until the next `login`: a model the organization added was not offered and a withdrawn one was still offered. `DistributionAccess.refreshEntitlement()` now renews a broker or adapter credential through the existing refresh path after a gateway 403 (`MODEL_DENIED`), at most once per credential generation, so a denial of the renewed credential re-issues nothing; a failed renewal keeps the current credential. The new entitlement applies from the next launch and, like every entitlement, only narrows the distribution allowlist. `login` still re-reads it, since it always replaces the credential. New tests pin the model catalog rules: the allowlist is the ceiling, the entitlement, the live gateway listing, and a user preference only remove models, an enforced model does not override a narrower entitlement, and allowlist `A, B` with entitlement `B, C` and gateway `B, C, D` yields exactly `B`.

A waiter takes a lock over only after it has seen the same holder token with the same mtime for the stale interval (75 s for the credential and identity lock, 30 s for the audit rotation lock) on the monotonic clock, and the caller's 90 s wait is monotonic. The audit rotation lock alone has two more ways out that need no waiter that watches, because its holder keeps it for milliseconds: the process in its token no longer exists on this host, or its mtime is over an hour old by the wall clock (a reused process ID). Before, a forward clock jump (NTP correction, a manual change, a resumed VM) let a second process break a live holder's lock and run a credential refresh or a rotation concurrently, and a backward jump kept an abandoned lock and stretched the wait indefinitely. A crashed holder's lock is now recovered after the stale interval whatever its mtime says; one left behind an hour "in the future" was never recovered. `CredentialManagerOptions.lockTiming` and `AuditRotation.lockStaleMs` set the intervals (tests shorten them); `withFileLock` moved to its own module and is still exported from `@piship/credentials`.
- **Behavior change:** damaged credential or identity metadata no longer loses ownership of the secrets it names. The references (and the neighboring generations a readable file would give) are now also read from the file's text, deleted with confirmation, and kept in a discarded marker while they cannot be deleted; a file too damaged to name any reference is cleared with a notice saying a secret may remain. A first credential or identity generation is named by a discarded marker before its secret is written, so a process that stops before the metadata commit no longer leaves an untracked secret. `@piship/credentials` exports `secretRefsFromText` and `metadataFileSecretRefs`.
- **Behavior change:** a change of `credential.storage.provider` (`file` to `system`, or `system` to `file`) between the active and the target release is a credential transition in `update` and `rollback`. The system, global, and environment config (`/etc/gitconfig`, `~/.gitconfig`, `$XDG_CONFIG_HOME/git/config`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM`) and the files only they include were protected only when they lay inside the project, so under a manifest that lets commands write `~` a sandboxed command could add a `core.hooksPath` to `~/.gitconfig`, which the user's next `git` command outside the sandbox runs. ### Security

- Base URLs are trimmed of trailing slashes in linear time; the previous regular expression was polynomial on long runs of `/` in a configured gateway or broker URL.
- **Behavior change:** In managed mode, user policy rules in `<state>/config/policy.json` are narrowing only, like team and project rules. A user `allow` rule is ignored and reported in `doctor` and `policy explain` and recorded as a `policy.violation` audit event. User `ask` and `deny` rules join the strictest-effect comparison, so they can tighten a decision but never relax a distribution default or `policy.default`. Personal mode is unchanged: there, a matching user rule still takes the place of the distribution default.
- **Behavior change:** Project resource directories (`.pi/skills`, `.agents/skills`, `.pi/prompts`, `.pi/extensions`, `.pi/themes`, `.pi/agents`, `.piship/providers`) are now walked, following links that stay inside the project root, up to 50,000 entries and 32 levels deep. A directory is treated like a top-level link that leaves the root when any link inside it leaves the root, or when it is too large or too deep to check: executable items are denied, and other items are evaluated as unknown origin. `doctor` names the offending entry or limit. The walk runs at launch and does not detect links created afterward.
- If the `tool_call` policy decision throws (for example, because the audit buffer is full), the tool call is blocked. The model sees a sanitized reason that names only the error code, and the block is recorded as `tool.denied`. Before this fix, Pi 0.87.1 already refused the call but passed the unredacted error message to the model. A compatibility test now pins Pi's refusal.
- **Behavior change:** `@piship/contracts` now holds the only redaction pattern set. `redact` now also removes GitHub, GitLab, Slack, AWS, and Google API tokens, standalone `Basic` credentials whose value looks like base64 (so text like "basic authentication" is kept), JWT shapes without the `eyJ` prefix, and PEM private keys. Before, only audit events removed these shapes. JWT matching starts only at the beginning of a token run, so adversarial output can no longer make redaction quadratic. As a result, MCP tool results sent to the model, stderr, error messages, `doctor`, and `config explain` are also redacted more thoroughly. `redactValue` redacts `token`, `cookie`, `passwd`, `client_secret`, and `bearer` keys too (new export `SECRET_KEY_PATTERN`). `scrubText` in `@piship/audit` is now the same function as `redact`.
- **Behavior change:** A `credential: runtime` Streamable HTTP MCP server receives the runtime credential only when its URL has the same origin (scheme, host, and port) as `inference.baseUrl`, the gateway the credential is issued for. A server on any other origin fails to start with `MCP_UNHEALTHY` before the credential is read. A required server therefore fails the launch.
- **Behavior change:** In managed mode, `network.publicFallback: deny` is now enforced. Managed mode requires `deny`, so every managed launch is private-only, whatever `network.privateOnly` says. The managed fetch and the Pi process's default dispatcher accept only the issuer, broker, and gateway hosts, `network.allowHosts`, and, for update commands, the `updates.source` host. ### Fixed

- Two audit writers no longer rotate `logs/audit.jsonl` twice for one full file. A writer could read the generation a concurrent rotation had just advanced, yet measure the old file before it moved, and then shift the new file out as well, dropping retained events early. Under the rotation lock, the writer now re-measures the current file and rotates only if it is still full ([#27](https://github.com/tc3oliver/piship/issues/27)).
- Filesystem enforcement is reported as sandbox-enforced only when a sandbox backend reports both `filesystem-read-deny` and `filesystem-write-allowlist`. A custom backend that declares only one of them no longer makes `policy explain` or file-tool denials say `sandbox`, and `doctor` says the path rules are only partly enforced ([#25](https://github.com/tc3oliver/piship/issues/25)).
- **Behavior change:** `update` validates the resolved `updates.source` (after `${NAME}` resolution) and `--from` with the same rules as the manifest: `https`, or `http` on `127.0.0.1`, `localhost`, or `[::1]`, with no credentials, query string, or fragment. Other schemes (`ftp:`, `file:`, public `http:`) are refused with `NETWORK_DENIED` instead of being read as a local directory. A local directory resolved from `updates.source` must be absolute; `--from` still accepts a relative directory. The manifest validation hint now lists the accepted forms.

Manifests already migrated keep what they declare.

- **Behavior change:** identity claims returned by an identity adapter are filtered to the same allowlist as OIDC (`sub`, `iss`, `aud`, `azp`, `exp`, `iat`, `auth_time`, `name`, `preferred_username`, `email`, `email_verified`, `groups`; scalar or string-array values only) before they are written to `identity/session.json`.

The holder refreshes the lock as a heartbeat and before each blocking secret-store command; only a lock left unrefreshed for 75 s is broken (moved aside atomically and re-checked first), a holder releases only its own lock, and a waiter that runs out of time fails with a retryable `CREDENTIAL_ACQUIRE_FAILED`.
- `policy explain` no longer claims that non-allow decisions on the `audit-only` plane are "observed and recorded"; it states that no runtime hook evaluates the action, so it is not enforced.
- **Behavior change:** Launch-time payload verification throws `PiShipError` instead of a plain `Error`: a payload file that differs from the inventory fails with `INTEGRITY_FAILED`, and a lock that no longer matches the packaged manifest or npm lock fails with `LOCK_INVALID`, as at the release gate. - Signed update channels: `piship keygen` and `piship sign-channel` write `stable`, `candidate`, or `dev` metadata signed with Ed25519, with expiry and a monotonic sequence that clients use to refuse replays.
- Branded `update [--check] [--channel] [--from] [--accept-review]` and `rollback`, also reachable as `piship update|rollback <id>`: signature, digest, and release verification, a launch check, and a non-mutating migration check before one atomic activation; a retained known-good release; non-secret state snapshots; credentials cleared and reacquired, never snapshotted or restored. `piship migrate-check` runs the migration check alone.
- Supply Chain and Update sections in `doctor`, `runtime.update` and `runtime.rollback` audit events, lifecycle outcome counters in local metrics, and the `UPDATE_FAILED` and `ROLLBACK_FAILED` error codes.
- A release-candidate CI workflow that builds each evidenced target twice, verifies on a fresh job, and creates and verifies GitHub artifact attestations; artifacts stay as workflow artifacts and nothing is published.

### Changed

- The demo company example is a managed `piship/v1alpha4` distribution with a governed handbook MCP server, Plan/Build workflow, a required sandbox, and stable and candidate update channels read from `ACMECODE_UPDATE_SOURCE`; it pins no release key.
- Installation uses a versioned `piship-install/v1` receipt, a per-distribution `launch.mjs` that starts the active release, and one directory per retained release. `piship install` also accepts a release directory or archive. Installs made by earlier versions still run and uninstall, but need a reinstall for update and rollback.
